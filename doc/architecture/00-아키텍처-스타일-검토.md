# 아키텍처 스타일 검토 — 지금 구조는 MSA인가?

- 작성일: 2026-09-01
- 관련: 이슈 #121, ADR-003 §3, ADR-006 §0, ADR-010 §3, `doc/portfolio-roadmap.md`
- 계기: Phase 3(K8s 운영화) 착수 전, "컨테이너를 나눴으니 MSA"라는 초기 프레이밍이 정확한지 점검

---

## 0. 결론 먼저

**현재 구조는 MSA가 아니다. "모듈러 모놀리스(Node backend) + 근거 있게 추출한 서비스 1개(ai-server) + 공유 인프라"다. 그리고 이 규모에서는 그게 맞는 선택이다.**

- **고칠 것은 코드가 아니라 문서의 용어다.** ADR-003·ADR-006에 "3-tier 컨테이너 분리"를 "MSA"라고 부른 곳이 있다. n-tier ≠ MSA.
- 로드맵은 이미 "MSA 전환 같은 대수술은 하지 말 것"(4장)이라고 못박아 뒀다. 구조 자체는 그 방침과 일치한다 — 다만 그 방침을 **명시적 결정으로** 어디에도 안 적어 뒀다.
- Phase 3은 "backend 모놀리스 1개 + ai-server 1개 + 인프라"를 운영화하는 작업이다. MSA 전제 인프라(서비스별 파이프라인 등)는 필요 없고, 오히려 스코프가 명확해진다.

---

## 1. MSA의 정의 — 무엇이 MSA를 MSA로 만드는가

마이크로서비스 아키텍처는 다음을 **전부** 만족해야 한다:

| 조건 | 뜻 |
|---|---|
| 비즈니스 능력 단위 분해 | 서비스 경계 = bounded context (주문 / 결제 / 배송…). 기술 계층(웹/앱/DB)이 아니다 |
| Database per service | 각 서비스가 자기 데이터를 소유하고, 남의 DB에 직접 붙지 않는다 |
| 독립 배포 | 한 서비스를 고쳐도 다른 서비스를 재배포하지 않는다 |
| 독립 스케일·장애 격리 | 서비스마다 replica 수·리소스가 다르고, 하나가 죽어도 나머지가 산다 |
| 네트워크 경계로만 통신 | 프로세스 내 함수 호출이 아니라 HTTP/gRPC/이벤트 |

**핵심**: "컨테이너를 여러 개로 나눴다"는 MSA의 필요조건도 충분조건도 아니다. 전형적인 3-tier(nginx + WAS + DB)도 컨테이너 3개지만 WAS가 모놀리스면 그냥 모놀리스다.

## 2. 현재 구조 실측

`docker-compose.yml` 기준 15개 컨테이너를 역할별로 묶으면:

| 컴포넌트 | 컨테이너 | 책임 | 소유 데이터 | 배포 단위 | 판정 |
|---|---|---|---|---|---|
| **Node backend** | `backend_1~4` (4 replica) | 인증 + 과목 조회 + 관심과목 + 시간표 + **실시간 수강신청**(대기열 + Redis 원자연산) + AI 챗봇 프록시 | `db`(MySQL: User·Class·ClassSchedule·CourseInterest·Registration·Timetable), `redis`(대기열 Sorted Set·좌석 카운터) | **단일 코드베이스·단일 이미지**. 4개는 수평 확장일 뿐 | **모놀리스** (모듈러) |
| **worker** | `worker_1~2` | RabbitMQ `registration.persist` 소비 → Redis에서 확정된 신청을 MySQL에 반영 | backend와 `db`·`redis` **공유** | **backend와 같은 이미지, `command`만 다름** (`node src/worker.js`) | 모놀리스의 비동기 잡 프로세서 |
| **ai-server** | `ai-server` (Python/FastAPI) | 시간표 생성 알고리즘 + AI 상담 챗봇(RAG + Function Calling) | `db-chat`(MySQL, Alembic), `redis-chat`, `qdrant` — **전부 자기만 씀** | 독립. 다른 언어·다른 데이터스토어·HTTP 경계 | **진짜 MSA 서비스** ✅ |
| 메시지 브로커 | `rabbitmq` | `registration.persist` 큐 | (인프라) | | 공유 인프라 |
| 큐/캐시 | `redis` | backend·worker 공유 | (인프라) | | 공유 인프라 |
| 프레젠테이션 | `frontend`(정적 서빙) + `nginx`(단일 진입점) | React SPA 서빙, `/api`·`/api/ai` 라우팅 | 없음 | 독립 | SPA + 리버스 프록시 (K8s Ingress 대응) |

### 2-1. "수강신청"은 독립 서비스가 아니다

ADR-006 §0은 "1.2만 명 트래픽을 처리할 **마이크로서비스**를 구축해야 한다"로 시작해서, Spring Boot 별도 서비스를 검토했다가 **"폴리글랏 오버헤드 회피"로 기각하고 기존 Node backend에 라우트로 추가**했다:

```
src/routes/registrationRoutes.js   ← 실시간 수강신청
src/routes/queueRoutes.js          ← 대기열
src/routes/authRoutes.js           ← 인증
src/routes/courseRoutes.js         ← 과목
...전부 같은 app.js에 app.use()로 마운트, 같은 sequelize 인스턴스, 같은 db
```

즉 **인증·과목·수강신청이 한 프로세스·한 DB에 산다.** `registrationController`가 `Class` 모델을 함수 호출로 직접 읽고, 같은 트랜잭션 경계를 공유할 수 있다. 이건 정의상 모놀리스다 — 잘 나뉜(모듈러) 모놀리스지만.

### 2-2. worker는 별도 서비스가 아니라 별도 프로세스다

`worker.js`는 backend와 **같은 코드·같은 모델·같은 DB**를 쓰고 `command`만 다르다. 이건 "모놀리스 + 비동기 잡 프로세서" 패턴(Rails+Sidekiq, Django+Celery worker와 동일 성격)이다. 정상적인 설계고, MSA와는 무관하다.

### 2-3. ai-server만 MSA 원칙을 따른다

챗봇 설계(ADR-010 §3, 2026-08-21 재검토)에서 **의식적으로** "완전 MSA 분리"로 갔다:
- bounded context: "AI" (시간표 생성 + 상담)
- Database per service: `db-chat`·`redis-chat`·`qdrant`를 자기가 소유, Node는 접근 안 함
- HTTP 경계: Node는 인증 후 `x-user-id` 헤더로 프록시만
- 독립 스케일: `ai-server`는 `replicas: 1`, backend는 4

**추출 근거가 진짜였다** — 다른 언어(Python), 다른 데이터(벡터 DB), 다른 스케일 프로필(LLM 호출은 I/O 바운드·저빈도), 다른 장애 도메인(Gemini API). 이게 MSA를 "제대로" 하는 방식이다: 모놀리스에서 시작해, 분리할 진짜 이유가 생긴 조각만 뗀다.

## 4. 이게 잘못된 선택인가 — 아니다

### 4-1. MSA의 비용

- **분산 트랜잭션**: "좌석 차감 + 신청 기록"이 두 서비스에 걸치면 2PC 또는 saga(보상 트랜잭션)가 필요하다. 지금은 한 Lua Script + 한 DB 트랜잭션으로 끝난다.
- **서비스 간 통신 장애**: 네트워크 홉마다 타임아웃·재시도·서킷브레이커. 함수 호출엔 없는 실패 모드.
- **운영 오버헤드**: 서비스마다 CI/CD 파이프라인·모니터링·배포·버전 관리·스키마 진화. 1인 개발에서 N배.
- **데이터 정합성**: DB per service면 조인이 불가능해 API 조합 또는 CQRS·이벤트 소싱으로 간다.

### 4-2. 이 프로젝트의 제약

- 1인 개발, 프론트 클라이언트 1개, 도메인이 "수강신청" 하나로 응집.
- 트래픽 특성이 "특정 서비스만 몰림"이 아니라 "전체가 동시에"(ADR-006 §1.3 "경쟁의 단위가 과목이 아니라 사이트 진입 그 자체"). 서비스별 독립 스케일의 이점이 작다.

### 4-3. 프로젝트 자체 원칙과 일치

- 로드맵 4장: **"하지 말 것: MSA 전환 같은 대수술."**
- ADR-009, ADR-008: "선증명 후개선", "규모에 안 맞는 복잡도는 안 들인다"를 반복 적용.
- ADR-006 §0: 폴리글랏(Spring Boot 추가) 기각도 같은 논리.

### 4-4. 업계 컨센서스와도 일치

"Monolith First"(Martin Fowler) — 대부분의 성공적인 MSA는 모놀리스에서 출발해 필요한 조각을 뗐다. Shopify·GitHub·Basecamp 등이 대규모에서도 모듈러 모놀리스를 유지한다. **"처음부터 MSA"는 대체로 안티패턴이다.**

→ 지금 구조는 "MSA를 흉내내지 못한 것"이 아니라 **"규모에 맞는 스타일을 골랐고, 분리할 진짜 이유가 있는 ai-server만 뗀 것"**이다. 이건 포트폴리오에서 **약점이 아니라 판단 근거로 쓸 서사다.**

## 5. 고칠 것 — 문서 용어

| 위치 | 지금 | 고칠 방향 |
|---|---|---|
| ADR-003 §3 제목 "왜 MSA 전체가 아니라…" | n-tier 분리를 "MSA"로 지칭 | "왜 3-tier 컨테이너 분리 중 frontend↔backend 경계만…" |
| ADR-006 §0 "…처리할 마이크로서비스를 구축해야 한다" | 결정은 "별도 서비스 안 만들고 backend에 통합"이었는데 제목이 "마이크로서비스 스택 선정" | "수강신청 로직을 별도 서비스로 뺄지 vs 기존 backend에 통합할지" — 결정 내용(Node 통합)은 그대로, 프레이밍만 |
| 로드맵 / 이 문서 | 아키텍처 스타일이 여러 곳에 암묵적 | **이 문서를 아키텍처 스타일의 명시적 기록으로 삼는다.** 로드맵 0장에 한 줄 링크 |

**코드 변경은 없다.** ai-server 분리(ADR-010 §3)는 이미 MSA 원칙을 정확히 따르고 있고, 나머지를 더 쪼갤 이유는 없다.

## 6. Phase 3에 주는 영향

이 검토로 Phase 3 스코프가 **명확해진다**:

- K8s 배포 대상 = **Deployment 2개**(backend 모놀리스, ai-server) + StatefulSet(MySQL×2, 큐/캐시) + Ingress. "서비스 메시", "서비스별 배포 파이프라인" 같은 MSA 인프라는 대상이 아니다.
- **Probe·resource·HPA는 전부 "backend 모놀리스를 잘 운영하는" 작업.** HPA는 backend에 붙고(폴링 부하가 여기 집중 — ADR-007), ai-server는 저빈도라 `replicas: 1` 고정 또는 별도 완만한 HPA.
- **DB 마이그레이션 도구**(P6, `sequelize.sync()` 제거)는 backend 하나만 대상. ai-server는 이미 Alembic으로 자기 스키마를 관리한다 — 여기서도 "ai-server가 자기 데이터를 소유"가 실질적 이점으로 작동.
- **엣지 rate limit**은 Ingress 한 곳(모든 트래픽의 단일 진입점).

즉 "부분 MSA"라서 Phase 3이 복잡해지는 게 아니라, **모놀리스라서 K8s 매니페스트가 단순하다.**

## 7. 선택지 (구조를 바꾸고 싶다면)

| 안 | 내용 | 평가 |
|---|---|---|
| **A. 유지 + 문서 정정** | 모듈러 모놀리스임을 명시하고, 모듈 경계(라우트/컨트롤러/서비스 계층)를 깔끔히 유지하는 데 집중 | **추천.** 로드맵 원칙과 일치, 포트폴리오 서사로 사용 가능 |
| B. registration을 별도 서비스로 추출 | 진짜 MSA 서비스를 하나 더 | auth·courses와 DB·트랜잭션을 공유해서, 떼려면 데이터 분리(saga 또는 API 조회)부터. 규모 대비 과함. 로드맵 4장 위반 |
| C. worker를 독립 서비스로 승격 | worker에 자기 DB·자기 배포 | worker의 일이 "backend가 만든 걸 backend의 DB에 쓰는 것"이라 분리할 경계가 없다. 무의미 |

**A를 전제로 Phase 3을 진행한다.**

## 부록. 포트폴리오 서사 초안

> "1.2만 명 규모의 수강신청 트래픽을 다루면서 MSA를 검토했지만, 1인 개발·단일 프론트·응집된 도메인이라는 제약에서 분산 트랜잭션·운영 오버헤드의 비용이 이점을 넘는다고 판단했다. 대신 **모듈러 모놀리스**로 코어를 유지하고, 언어(Python)·데이터스토어(벡터 DB)·스케일 프로필·장애 도메인(외부 LLM API)이 모두 다른 **AI 서비스만 네트워크 경계로 분리**했다. 이때 ai-server가 자기 데이터(대화 이력 MySQL, 작업 메모리 Redis, 벡터 DB)를 완전히 소유하도록 설계해, 'Database per service'를 그 하나에 대해서는 엄격히 적용했다 — 그 덕에 K8s 배포에서도 ai-server는 독립 Deployment로 자연스럽게 떨어지고, 스키마 진화도 backend와 독립적이다."
