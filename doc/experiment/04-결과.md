## 2. 측정 배경 — 왜 재는가

Stage 1-1(#87)에서 강의계획서 청킹 규칙을, 1-2(#100)에서 18청크를 Qdrant에 적재,
1-3(#102)에서 `search_syllabus`·`get_syllabus` Tool을 챗봇에 결합했다. 여기까지는
"돌아간다"는 스모크 테스트만 했고, **정량 수치가 없었다.**

이 프로젝트의 로드맵 원칙(`portfolio-roadmap.md`)은 "문제 정의 → 측정 → 개선 → 재측정,
Before/After 정량". RAG는 새 기능이라 비교 대상이 없어 보이지만, Stage 1-1 정독 과정에서
**이 프로젝트의 옛 `/recommend` 엔드포인트가 "전체 과목 텍스트를 프롬프트에 주입"하는
방식**임을 확인했다. 그게 naive 베이스라인(Before)이고, RAG(top-3 검색)가 After다.
naive는 가상의 대조군이 아니라 "우리가 실제로 하던 방식"이다.

## 3. 측정 방법

### 3-1. 세 가지 실행 모드

| `--mode` | 무엇을 하나 | 목적 | reps | 비용 |
|---|---|---|---|---|
| `retrieval` | 에이전트 없이 `search_syllabus` 로직만 35회 호출 | 순수 검색 hit rate@1/3/5. 임베딩은 결정론적이라 reps=1 | 1 | 임베딩 35회 |
| `agent` | 질문마다 에이전트 호출, tool_calls·retrieved·답변 채점 | 실제 챗봇 동작 (라우팅·할루시네이션·오선택) | 3 | 162 invoke |
| `naive` | 강의계획서 18청크 전문(17,114자) + 질문 단일 LLM 호출, Tool 없음 | Before 베이스라인 | 3 | 126 invoke |

### 3-2. 채점 로직 (`eval/rag_scoring.py`, 순수 함수 + 단위테스트 16개)

| `expect_kind` | 채점 축 |
|---|---|
| `hit` (의미검색) | 정답 `course_code`가 `search_syllabus` top-k에 (`hit_at_1/3/5`) + `search_syllabus` 호출 여부 + 답변 할루시네이션 없음 |
| `not_registered` (미등록) | `answer_must_not_include` 위반 없음 / "미등록"이라 답함 |
| `out_of_scope` (범위밖) | `search_syllabus`·`get_syllabus` 둘 다 호출 안 함 |
| `routing` (라우팅) | `expect_tool` 일치 + 강의계획서 Tool 호출 안 함 (1-3 회귀) |

naive 모드는 Tool·retrieved가 없어 답변 레벨로만 채점 — `hit`은 답변이 정답 과목명을
언급했는지(공백 무시 substring), `not_registered`는 할루시네이션 없는지.

### 3-3. 테스트 케이스 예시

```
[hit] rag-01  "동적 계획법이랑 그리디 알고리즘 배우는 수업 있어?"   → 21000549 (알고리즘)
[hit] rag-31  "시험 없이 프로젝트만으로 평가하는 데이터사이언스 수업?" → 21105803
[미등록] rag-35 "프로그래밍개론 강의계획서 평가 비중?"  answer_must_not_include: [중간, 기말, %]
[범위밖] rag-42 "알고리즘 21000549-1 잔여석 몇 개야?"   → 강의계획서 Tool 부르면 오선택
[라우팅] rag-52 "자바프로그래밍 나 대신 신청 좀 해줘"    expect_tool: none (거절, 조회도 안 함)
```

### 4-1. retrieval 모드 — 검색 계층 (35문항, reps 1)

| | 값 |
|---|---|
| **hit@1** | **97.1%** (34/35) |
| **hit@3** | **100%** |
| **hit@5** | **100%** |

### 4-3. naive 모드 — 전문 주입 (42문항 × 3 = 126 rows, Before)

| 카테고리 | n | pass | 세부 |
|---|---|---|---|
| 의미검색 | 105 | **100%** | 답변이 정답 과목명 언급 100% |
| 미등록 | 21 | **100%** | 할루시네이션 **0%** · "미등록" 답변 100% |
| **전체** | **126** | **100%** | 전 rep pass **42/42**, flaky **0** |

- corpus: 17,114자 (18청크 = 개요+목표+선수+평가+주교재+주차별)
- latency: p50 **1,195 ms** (Tool 왕복 없는 단일 호출)
- 토큰: 총 1,173,407 · 의미검색 turn당 평균 **9,332**
- 범위밖·라우팅은 Tool이 있어야 의미 있어 naive에선 채점 제외

> ⚠️ 1차 자동 채점에서 naive 의미검색이 97.1%로 나왔으나, `rag-19` 3회 모두 모델이
> 정답 "소프트웨어의이해"를 **"소프트웨어의 이해"**(공백 삽입)로 표기해 substring
> 매칭이 실패한 채점 아티팩트였다. 채점기를 공백 무시로 고치고 raw를 재채점(`--rescore`)
> → **100%**. `rag_scoring._nospace` + `test_rag_scoring`.

### 4-4. threshold 결정 — 두지 않음

1-3에서 `search_syllabus`는 유사도 cutoff 없이 top-3를 반환한다. 이번 측정에서 점수 분포:

| | n | min | p25 | median | max |
|---|---|---|---|---|---|
| 의미검색 정답 top1 relevance | 105 | 0.649 | 0.675 | 0.705 | 0.773 |
| 미등록 질문에서 `search_syllabus` 오호출 시 top1 | 9 | 0.630 | — | 0.685 | 0.721 |

**두 분포가 겹친다 (갭 없음).** 정답이 0.649까지 내려가고, 무관한 질문의 top1이 0.721까지
올라간다. 0.65~0.70 사이 어디에 threshold를 박아도 정답을 자르거나 노이즈를 통과시킨다.
게다가 미등록·범위밖 pass rate가 이미 100% — **에이전트 추론이 낮은 relevance를 이미
걸러내고 있다.** → threshold 도입 보류. 코퍼스가 커져 오탐이 실제로 발생하면 재검토.

## 5. 결과 해석

### 5-1. 이 규모에서 RAG의 정확도 우위는 없다 (예상대로)

18청크(17,114자)는 `gemini-3.1-flash-lite` 컨텍스트에 통째로 들어간다. naive도
의미검색 100%, 할루시네이션 0%. RAG가 "정확해서" 이기는 게 아니다.

### 5-2. RAG가 오히려 느리다

p50 **2,431 ms vs 1,195 ms**. RAG는 `임베딩 → search_syllabus → LLM 추론 → (26%는)
get_syllabus → LLM 추론`의 왕복이 있고, naive는 단일 호출. 작은 코퍼스에서는 검색
오버헤드가 컨텍스트 축소 이득보다 크다.

### 5-3. RAG의 실질 이득 = 토큰 2.2× + 확장성 + 아키텍처

- **토큰**: naive는 매 메시지 corpus 5~6k 토큰을 통째로 실어보낸다. 의미검색 turn당
  9,332 vs 4,268. 대화가 길어질수록, 사용자가 많을수록 격차가 벌어진다.
- **확장성**: 강의계획서가 소프트웨어학부 18개 → 전학부 수백 개로 늘면 naive는 컨텍스트
  한도 초과 + 비용 선형 폭증 + "needle in haystack" attention dilution. RAG는 평탄.
- **아키텍처**: ADR-010 §7의 "정답이 하나인 값(잔여석·시간표)은 Tool, 자연어 매칭이
  필요한 것(강의계획서 본문)만 RAG". naive는 잔여석·시간표를 답할 수 없어 **어차피
  기존 Tool 에이전트 위에 얹어야** 하고, 그러면 corpus(5~6k) + Tool 스키마 + 히스토리로
  naive-hybrid가 순수 naive보다도 무거워진다. RAG는 강의계획서도 Tool 인터페이스로
  통일돼 분리가 깔끔하다.

### 5-4. 1-3 가드레일은 회귀를 만들지 않았다

Tool 2개(4개로) 추가 + SYSTEM_PROMPT 2문장(A안, 최소)이 기존 라우팅을 안 깼다.
라우팅 21 rows 100%, 범위밖 15 rows에서 강의계획서 Tool 오호출 0%. "신청 대행 거절 시
조회 Tool도 안 부른다"(Stage 3-1 정책)도 rag-52에서 유지 확인.

### 5-5. hit@1 미스 1건의 교훈

rag-14는 질문에 정답이 아닌 과목명("자바")이 강하게 들어가면 임베딩이 그쪽으로
쏠린다는 걸 보여준다. top-3를 반환하고 에이전트가 판단하는 현재 구조가 이걸 흡수한다
(agent 모드 rag-14는 `search_syllabus` → `get_syllabus`로 선수과목 확인 후 정답).

## 7. 용어

| 용어 | 뜻 |
|---|---|
| **RAG** (Retrieval-Augmented Generation) | 질문을 벡터로 바꿔 관련 문서를 검색한 뒤, 그 문서를 근거로 LLM이 답하게 하는 방식. "먼저 찾고, 찾은 것만 보고 답한다" |
| **임베딩 (embedding)** | 텍스트를 의미를 담은 고차원 숫자 벡터로 변환한 것. 의미가 비슷하면 벡터도 가깝다. 여기선 `gemini-embedding-001`, 3072차원 |
| **비대칭 임베딩 (asymmetric)** | 문서는 `RETRIEVAL_DOCUMENT`, 질문은 `RETRIEVAL_QUERY` task_type으로 각각 다르게 임베딩. "질문 ↔ 답이 되는 문서"가 가까워지도록 학습된 방식 |
| **코사인 유사도 (cosine similarity)** | 두 벡터가 이루는 각도로 잰 유사도. −1~1, 클수록 비슷. 여기 `relevance` 값 |
| **hit rate@k** | 정답 문서가 검색 결과 상위 k개 안에 든 질문의 비율. `hit@3` = top-3 안에 있으면 성공 |
| **청크 (chunk)** | 검색·임베딩의 최소 단위. 여기선 "과목 1개 = 1청크" (강의계획서 개요+목표+주차별을 합친 ~300토큰) |
| **top-k / cutoff(threshold)** | top-k = 상위 몇 개를 반환할지. threshold = 유사도가 이 값 미만이면 "관련 없음"으로 버릴지의 기준값 |
| **naive 베이스라인** | RAG 없이 "관련 문서 전부를 프롬프트에 통째로 넣고 답하게" 하는 단순 방식. 비교 대조군 |
| **routing (라우팅)** | 사용자 질문에 대해 LLM이 어떤 Tool을 호출할지(또는 안 할지) 고르는 것 |
| **할루시네이션 (hallucination)** | 근거(Tool 응답·검색 결과) 없이 그럴듯하게 지어낸 답. 여기선 "강의계획서 없는 과목의 평가 비중을 만들어 답함" |
| **회귀 (regression)** | 기능을 추가했더니 원래 잘 되던 게 망가지는 것. 여기선 "RAG Tool 추가 후 잔여석 라우팅이 틀리는가" |
| **reps / flaky** | reps = 같은 질문 반복 횟수(LLM 비결정성 때문). flaky = rep마다 결과가 갈리는 시나리오 |
| **recursion_limit** | LangGraph 에이전트가 한 턴에 Tool을 호출할 수 있는 최대 횟수 (무한 루프 방지) |
