## 0. 이 문서의 위치

이슈 #50은 Active 인원수(`ACTIVE_GATE_LIMIT`)를 감이 아니라 근거 있게 정하기 위한 3단계 실험(Step 1 λ_max 측정 → Step 2 Little's Law 가설 → Step 3 Valve Tuning 실측)이다. 이 문서는 Step 1을 실행하는 과정에서 **Step 2의 원래 설계(Little's Law로 N을 역산하는 방식)가 개념적으로 성립하지 않는다는 걸 발견**하고, 다른 방식(Stage 1 실측 데이터 직접 활용)으로 방향을 전환한 전체 과정을 기록한다. "계산이 깔끔하게 성공했다"가 아니라 "계산을 시도하다가 틀렸다는 걸 발견하고 더 나은 방법으로 바꿨다"는 이야기라, 실패한 시도를 포함해 그대로 남긴다.

## 1. 배경 — 왜 이 실험이 필요한가

수강신청 오픈 순간 1.2만 명이 동시에 접속하면 서버가 감당하지 못한다(Stage 1에서 이미 실측 — 동시 1,000~3,000명대부터 `handled_rate` 붕괴). 그래서 대기열(Redis Sorted Set, 이슈 #46)로 "몇 명(N)까지만 동시에 수강신청 화면에 들여보낼지"를 조절한다. 이 N이 너무 작으면 서버 여유를 낭비하며 불필요하게 오래 기다리게 하고, 너무 크면 대기열을 만든 의미 없이 서버가 다시 무너진다. 이 실험 시리즈의 목적은 이 N을 실측 근거로 정하는 것이다.

## 2. 용어 설명

| 용어 | 의미 |
|---|---|
| `req/s` (처리량, Throughput) | 서버가 초당 몇 개의 요청에 응답했는가 |
| `p95` | 요청 100개를 보내면 그중 95개가 이 시간 안에 끝났다는 지표. 평균(avg)은 소수의 극단값에 덜 민감해 실제 "느림" 체감과 괴리가 있어, 성능 테스트에서는 p95/p99를 표준으로 쓴다 |
| `p95 500ms` (SLO) | ADR-006 4.2가 정한 목표 — "신청하기 버튼 클릭부터 응답까지"가 95%의 사용자에게 500ms 이내여야 한다. 실측 조사가 아니라 일반 UX 응답속도 기준(닐슨 등)을 참고해 설계 초기에 잡은 잠정 목표(이슈 #52에서 배포 후 재검토하기로 별도 추적) |
| `λ_max` | SLO(p95 500ms)를 만족하는 최대 처리량. 원래 `T_max`로 표기했다가 Little's Law의 표준 기호(`λ`)와 통일하기 위해 정정(§5 참고) |
| Little's Law | `L = λ × W` — 어떤 시스템에 평균적으로 머무는 개체 수(L)는 도착률(λ)과 평균 체류 시간(W)의 곱과 같다는 큐잉 이론의 일반 법칙 |
| `N_초기` | Little's Law(또는 다른 방법)로 도출한 Active 게이트 정원의 초기 가설값. 최종값(`N*`)이 아니라 시작점 |

## 4. Step 1 실험 과정 — λ_max 측정

### 4-1. 기존 데이터 재확인: 스윕 간격이 성기다

Stage 1 Group C 스윕(이슈 #29)은 50/100/300/500/1,000/3,000/12,000 간격으로 진행됐다. p95 500ms 기준으로 다시 보니:

| VU | p95 | 판정 |
|---|---|---|
| 100 | 265ms | 통과 |
| 300 | 614ms(5회 평균) | **초과** |

경계가 100~300 사이 어딘가에 있는데 이 구간이 비어있었다. 이건 Stage 1이 원래 주목했던 "handled_rate 붕괴 지점"(VU 1,000~3,000대, 인프라 공용 한계)과는 전혀 다른, 훨씬 낮은 지점이다.

### 4-2. 1차 추가 측정(VU 150/200/250) — 노이즈 발견

같은 조건으로 VU 150/200/250 구간을 5회씩 추가 측정했다. 결과가 예상보다 훨씬 들쭉날쭉했다 — 같은 VU=150인데 반복마다 p95가 449ms~1,422ms까지 3배 차이 났다.

원인을 조사한 결과, **이 프로젝트와 무관한 컨테이너들이 같은 머신에서 CPU를 나눠 쓰고 있었다**:
- `sugang-control-plane`/`sugang-worker`/`sugang-worker2` — Phase 3 때 쓴 kind(K8s) 클러스터가 idle 상태로 계속 떠 있었음(합쳐서 CPU ~14%)
- `biostream_api`/`biostream_mcp`/`biostream_qdrant`/`biostream_db` — 완전히 무관한 다른 프로젝트 컨테이너

로컬 Docker Desktop이 **CPU 2코어**뿐이라는 걸 Stage 1(트러블슈팅 05)에서 이미 확인한 바 있는데, 이번엔 그 2코어를 이 실험 스택 외에 저 컨테이너들과도 나눠 쓰고 있었던 것이 변동성의 원인으로 추정된다. 1차 측정 원본은 `doc/experiment/raw/noisy-run-20260819/`에 보존했다(재현 불가능한 값이라 폐기하지 않고 원인 분석용으로만 남김).

### 4-3. 정리 후 2차(클린) 재측정

무관한 컨테이너를 전부 `docker stop`(정지, 삭제 아님 — 나중에 복구 가능)한 뒤 VU 150/200/250을 재측정했다. 여전히 소폭의 변동은 있었지만(아래 §5), 이전만큼 극단적이진 않았다.

## 5. 결과

### 5-1. VU별 p95 (클린 재측정, n=5)

| VU | p95 값(5회) | 중앙값 | 판정 |
|---|---|---|---|
| 150 | 319 / 460 / 315 / **627** / 205 | 319ms | 4/5 통과 |
| 200 | 317 / 300 / 466 / 423 / 456 | 423ms | 5/5 통과 |
| 250 | 395 / 401 / 387 / **683** / 258 | 395ms | 4/5 통과 |
| 300(Stage 1 기존 데이터, 이슈 #29) | 538 / 617 / 703 / 642 / 570 | 617ms | **0/5 통과** |

VU=150과 VU=250에서 각각 1건씩(공교롭게 둘 다 "4번째 반복") 500ms를 크게 넘는 값이 나왔다. 나머지 값들과 패턴이 다르고(부하 수준과 무관하게 튐), 반복적으로 재현되지 않는 단발성이라 부하 자체보다는 환경적 요인(짧은 GC 정지, Docker Desktop 자체 백그라운드 작업 등 국지적 요인)으로 추정한다 — 완전히 특정하지는 못했다(§7 한계 참고).

반면 **VU=300은 5회 전부, 그것도 여유 있게(538~703ms) 500ms를 넘는다.** 노이즈로 보기 어려운 일관된 결과다.

### 5-2. λ_max 결론

VU 250까지는 대체로 SLO를 만족하고, VU 300은 일관되게 위반한다. 즉 **λ_max의 경계는 VU 250~300 사이**(실측 처리량 기준 약 450 req/s 부근)다. 더 좁혀서(예: VU 275) 정밀하게 특정하는 대신, 이 정도 정밀도로 충분하다고 판단하고 중단했다 — 이유는 §6에서 이어진다.

## 6. Step 2 시도와 발견한 문제 — Little's Law 적용의 개념적 오류

### 6-1. 원래 계획대로 계산해봤더니

실험계획서 02의 Step 2 공식: `N_초기 = λ_max × 평균 체류 시간`

```
N_초기 = 450(req/s) × 600(초, 이슈 #48에서 정한 ACTIVE_TTL_SECONDS) = 270,000명
```

**전체 재학생이 1.2만 명인데 27만 명이 나왔다.** 원래(수정 전) TTL인 120초로 계산해도 `450 × 120 = 54,000명`으로 여전히 전체 학생 수의 4배가 넘는다 — TTL 값을 바꾼 게 문제가 아니라 계산 방식 자체가 잘못됐다는 뜻이다.

### 6-2. 원인 분석

Little's Law `L = λW`에서 `λ`는 **"시스템에 새로 들어오는 속도"**여야 하는데, 우리가 측정한 `λ_max`는 **"신청하기 버튼 클릭 API가 처리되는 속도"**였다. 이 둘은 다른 개념이다:

- Active 상태로 들어온 한 사람은 600초 동안 머무르면서, 그 안에서 "신청 클릭"을 여러 번 할 수 있다(1지망 마감 → 2지망 시도 → 3지망 시도…). TTL을 120초에서 600초로 늘린 이유 자체가 "한 세션에 여러 과목을 시도한다"는 전제였다.
- 즉 "방(Active 게이트)에 입장하는 속도"(Little's Law가 필요로 하는 λ)와 "그 사람들이 방 안에서 누르는 클릭의 총합 속도"(우리가 측정한 λ_max)는 서로 다른 양인데, 실험계획서 02의 Step 1→Step 2 설계가 이 둘을 같은 것으로 취급하고 있었다.

한 사람이 세션당 평균 여러 번 클릭한다고 가정해 나눠봐도(예: 3회) `150 × 600 = 90,000`으로 여전히 비상식적이다 — 나눗셈으로 보정될 수준의 오차가 아니라 애초에 잘못된 입력을 넣고 있었다는 뜻이다.

## 7. 방향 전환 — 의사결정

**λ_max 기반 Little's Law 계산을 포기하고, Stage 1이 이미 실측한 "안전한 동시 접속 규모"를 N_초기의 직접 근거로 쓰기로 했다.**

Stage 1 Group A/B/C 스윕(정합성 스윕, 좌석 차감 API 대상)은 다음을 이미 실측으로 보여줬다:

| VU | handled_rate |
|---|---|
| 500 | 100% |
| 1,000 | ~97% |
| 3,000 | ~32~35% |

이건 "동시에 N명이 서버를 두드려도 서버가 안 무너지는가"를 직접 재는 데이터라, "방에 N명이 앉아있다"는 질문과 훨씬 더 직접적으로 맞아떨어진다(방 안 사람들이 대략 비슷한 시간대에 클릭할 수 있는 상태이므로). 500명까지는 완전히 안전하니, 그보다 충분히 낮게 **300명**으로 잡는다.

흥미로운 점은, 이 300이라는 값은 이미 이슈 #48에서 (이번 Little's Law 계산 이전에) 같은 논리("Stage 1 500명 실측 대비 충분히 낮게")로 잠정 설정했던 값과 정확히 같다는 것이다. 즉 이번 실험은 새로운 숫자를 만들어낸 게 아니라, **이미 직관적으로 옳았던 선택("Stage 1 데이터를 근거로 삼는다")을, 대안(Little's Law 계산)을 실제로 시도해보고 그게 왜 틀렸는지 확인함으로써 더 확실하게 검증한 과정**이었다.

`λ_max`(~450 req/s)는 폐기하지 않는다 — "N=300명이 각자 클릭을 시도해도 그 클릭 자체를 처리하는 능력은 충분히 여유가 있다"는 걸 보여주는 보조 근거로 남긴다(300명이 설령 동시에 클릭해도 300 < λ_max 여유 구간 안에 들어온다).

## 8. 결론

1. **`N_초기 = 300`으로 확정**(이슈 #48에서 이미 설정한 값과 동일, 근거를 Little's Law 계산에서 Stage 1 실측 재활용으로 교체) — `queueService.js`의 `ACTIVE_GATE_LIMIT` 기본값은 변경 없이 유지
2. **`λ_max` ≈ 450 req/s(VU 250~300 경계)**로 확인 — N_초기 확정의 직접 근거는 아니지만, 300명 규모의 클릭 처리 여유를 보여주는 보조 데이터로 유효
3. **실험계획서 02의 Step 1→Step 2 설계(λ_max로 Little's Law 역산)는 이 시스템에 적용할 수 없다** — Step 1이 측정하는 것(엔드포인트 처리량)과 Step 2가 필요로 하는 것(입장 속도)이 다른 양이기 때문. 이 결함은 문서에 정정 기록을 남겼다(`02-대기열-방어-실험계획.md`, 향후 유사 설계 시 "λ가 정확히 무엇의 도착률인지"를 먼저 명확히 해야 한다는 교훈)

## 9. 해석 — 이 경험에서 배운 것

계산 공식이 있다고 해서 그 공식에 넣는 입력이 올바르다는 보장은 없다. Little's Law 자체는 틀리지 않았다(그 법칙 자체는 항상 성립한다) — 틀린 건 "우리가 측정한 λ_max가 이 공식이 요구하는 λ와 같은 것"이라는 전제였다. 계산 결과(27만 명)가 상식과 명백히 어긋난다는 걸 알아챈 게 이 오류를 잡아낸 유일한 방법이었다 — **결과의 타당성(sanity check)을 항상 먼저 봐야 한다**는 걸 재확인한 사례다.

## 12. Step 3(Valve Tuning) 실행 — 하네스 안정화

이슈 #57로 Step 3 k6 하네스(`loadtest/scripts/queue-valve-tuning.js`, `run-valve-tuning-round.sh`)를 구축하고 `N_초기=300`, `VUS=12,000`으로 Round 1을 처음 실행했으나, 대기열 특유의 부하 패턴(1.2만 명이 최대 30분간 3~5초 주기로 지속 폴링)에서 로컬 인프라 문제 3건이 연쇄로 드러나 먼저 정리해야 했다. 상세 진단 과정은 별도 트러블슈팅 문서에 남겼다:

- [트러블슈팅 07](../troubleshooting/07-대기열-지속-폴링-부하에서-nginx-업스트림-병목.md): nginx keepalive 풀 부족(64→2048), health check 과민(`max_fails=10 fail_timeout=3s`)
- [트러블슈팅 08](../troubleshooting/08-validate3k-잔여노이즈-원인-docker-desktop-cpu-캡.md): Docker Desktop이 호스트 실스펙(16코어/32GB) 대비 2 vCPU/10GB로 캡핑돼 있었던 문제(`.wslconfig` → 8 vCPU/16GB로 상향)

두 수정을 검증(`validate2k`/`validate3k`/`revalidate3k`, 3,000 VU까지 완전 클린 확인)한 뒤에야 12,000명 규모 Round 1을 신뢰할 수 있는 조건에서 실행할 수 있었다.

## 13. Round 1 — 붕괴 확인 (`ACTIVE_GATE_LIMIT=300`, `VUS=12,000`, backend 2대)

인프라 문제를 다 정리한 상태에서 처음 돌린 Round 1은 판정 기준(등록 API p95 500ms 이내 AND 에러율 0.1% 미만)을 크게 위반했다.

| 지표 | 값 |
|---|---|
| 총 소요시간 | 30분 56초 |
| `http_req_failed`(전체 요청) | 4.89% |
| `checks` | 95.13% |
| `registration_success` | 7,090명(59.1%) |
| `registration_rejected`(정상적 비즈니스 거절) | 564명(4.7%) |
| `registration_server_error` | 341건(2.8%) |
| `queue_dropout`(TTL 30분 초과 이탈) | **4,005명(33.4%)** |
| `registration_duration` p95 | **11.1초** |
| `queue_wait_duration` p95 | 29.2분(거의 `MAX_WAIT_S` 상한) |
| `enter: 200` 체크(최초 대기열 진입) | 78% — 시작 순간부터 21.7% 실패 |

12,000명 중 1/3이 대기열에서 자연 이탈했고, Active 게이트를 통과한 사람의 등록 처리조차 p95 11.1초(목표의 22배)로 심각하게 느렸다.

### 원인 분석

`docker stats`를 부하 시점과 겹쳐 재확인했다(트러블슈팅 08과 같은 방법론). 이번엔 트러블슈팅 08과 다른 그림이 나왔다 — VM 전체 CPU 합계는 최대 83%(667%/800%)로 여유가 있었는데, **`backend_1`/`backend_2`가 각각 110~116%(프로세스당 사실상 천장)에 머물러 있었다.** Node 이벤트 루프가 프로세스당 코어 1개 남짓을 쓰는 게 한계라, VM에는 여유가 있어도 백엔드 프로세스 자체가 이미 포화 상태였다는 뜻이다. 대기 중인 11,700명이 3~5초마다 쏟아내는 `/api/queue/status` 폴링(초당 약 1,100건, 30분 내내 지속)이 이 2개 프로세스의 처리 한계를 넘어선 것으로 판단했다.

### 검토한 대안과 결정 (사용자와 협의)

| 대안 | 채택 여부 | 이유 |
|---|---|---|
| Active 게이트 값을 더 낮춘다 | 기각 | 이미 300으로 계획서의 "-1,000명 단위" 조정 규칙이 기계적으로 안 맞고, 원인이 Active 크기가 아니라 폴링 총량을 받아낼 처리 용량이라는 게 실측으로 확인됨 — Active를 낮춰도 폴링 트래픽 자체는 줄지 않음 |
| 폴링 주기(3~5초)를 늘린다 | 기각(현 단계) | 실제 프론트엔드 폴링 주기와 통제변수로 일치시켜야 하는 값(ADR-006 1.4, 실험계획서 02 §5) — 부하테스트에서만 늘리면 실제 조건을 대표 못함. UX 트레이드오프를 동반하는 제품 결정이라 이번 인프라 튜닝 범위 밖 |
| 지금 K8s로 옮겨 HPA/Ingress로 처리 | 기각(현 단계) | 로드맵 Phase 순서(Phase 2 동시성 완료 후 Phase 3 K8s 운영화)를 건너뜀. docker-compose→K8s 전환은 네트워크·로드밸런싱·리소스 격리 방식이 한꺼번에 바뀌어 "인스턴스를 늘려서 좋아진 것"과 "K8s 자체 특성 때문에 좋아진 것"을 분리할 수 없어 실험이 오염됨 |
| **backend 인스턴스 2→4대 수평 확장** | **채택** | 트러블슈팅 05가 이미 확립한 패턴(backend_1/backend_2)의 자연스러운 연장. 바뀌는 변수가 "인스턴스 개수" 하나뿐이라 가설("프로세스당 CPU 천장이 원인")을 가장 깨끗하게 검증 가능. CPU 여유(83%→아직 17% 남음)도 충분 |

상세 결정 기록: [ADR-007](../ADR/ADR-007-대기열-부하-backend-인스턴스-수평-확장.md)

## 14. Round 1b — backend 4대로 재실행 (`ACTIVE_GATE_LIMIT=300`, `VUS=12,000`)

`docker-compose.yml`에 `backend_3`/`backend_4`를 추가(기존 `backend_2`와 동일 구성, `seedData.js`는 여전히 `backend_1`만 담당), `nginx/default.conf` upstream pool에 반영한 뒤 동일 조건으로 재실행했다.

| 지표 | r1 (backend 2대) | r1b (backend 4대) | 변화 |
|---|---|---|---|
| 총 소요시간 | 30분 56초 | 23분 46초 | -23% |
| `http_req_failed` | 4.89% | **0.06%** | 목표(0.1% 미만) 달성 |
| `checks` | 95.13% | 99.93% | |
| `registration_success` | 7,090명(59.1%) | **11,935명(99.5%)** | |
| `registration_server_error` | 341건(2.8%) | 65건(0.54%) | |
| `queue_dropout` | 4,005명(33.4%) | **0명** | 완전 해소 |
| `registration_duration` p95 | 11.1초 | **4.4초** | 2.5배 개선, 목표(0.5초) 미달 |
| CPU 합계 최댓값(8 vCPU=800% 기준) | 667%(83%) | 684%(85%) | 거의 동일한 천장 재확인 |
| backend 인스턴스별 CPU | 110~116%(×2) | 100~108%(×4) | 프로세스당 천장은 그대로, 개수로 처리량 확장 |

가설이 확인됐다 — 인스턴스를 늘린 만큼 정확히 처리 용량이 늘어 TTL 이탈이 완전히 사라지고 전체 에러율도 목표치 안으로 들어왔다. 다만 계획서가 최종 판정 기준으로 삼는 **등록 API 자체의 p95(4.4초)는 여전히 목표(500ms)의 8.8배**로, 완전한 통과는 아니다.

## 15. 여기서 멈추기로 한 결정

backend 4대 상태에서 VM 전체 CPU 여유가 15%(684%/800%)로 줄어, 로컬 Docker Desktop 환경에서 추가로 인스턴스를 늘리는 건 수확 체감·물리적 한계에 가깝다고 판단했다. 사용자와 논의 후, 이번 Step 3 실험은 **"Active 게이트 크기가 아니라 backend 처리 용량이 실제 병목이었다"는 사실을 실측으로 규명하고, 로컬 환경에서 유효한 방향(수평 확장)까지 확인한 시점에서 마무리**하기로 했다. p95 500ms를 완전히 채우는 것은 로컬 단일 Docker Desktop VM의 물리적 CPU 한계를 넘어서는 확장(K8s CronHPA 사전 확장 + HPA 병행, Phase 3 범위 — [ADR-011](../ADR/ADR-011-CronHPA-HPA-병행-확장-구조.md))이 필요하다고 결론짓는다.

## 16. 최종 결론

1. **`N*(Active 게이트 인원) = 300 유지`** — Step 1/2에서 확정한 `N_초기=300`을 그대로 최종값으로 채택한다. Round 1/1b 모두 붕괴·개선의 원인이 Active 크기가 아니라 backend 처리 용량이었다는 게 실측으로 확인됐으므로, Active 값 자체를 조정할 근거가 없다.
2. **backend 인스턴스를 2대→4대로 확장하는 것을 실질적 해법으로 채택** — `docker-compose.yml`/`nginx/default.conf`에 반영(이슈 #57). TTL 이탈 33.4%→0%, 전체 에러율 4.89%→0.06%(목표 달성)로 개선.
3. **등록 API p95 500ms SLO는 로컬 환경에서 완전히 달성하지 못했다(4.4초)** — 정직하게 미달로 기록한다. 완전한 달성은 Phase 3(K8s 운영화 — CronHPA 사전 확장 + HPA 병행, [ADR-011](../ADR/ADR-011-CronHPA-HPA-병행-확장-구조.md))로 명시적으로 이월한다.
4. ADR-006(1.1~1.4)에는 이 결론(N*=300, backend 확장이 필요조건, 완전한 SLO는 Phase 3 이월)을 반영한다.

## 17. 한계

- p95 500ms SLO는 로컬 환경에서 미달성 상태로 실험을 마쳤다 — "N*을 확정했다"기보다 "Active가 병목이 아님을 확인하고, 남은 병목(backend 처리 용량)의 방향성과 로컬 한계를 규명했다"는 게 더 정확한 요약이다.
- backend 5~6대 등 더 늘렸을 때 p95가 500ms에 도달하는지는 검증하지 않았다(로컬 CPU 여유 15% 시점에서 의도적으로 중단) — Phase 3에서 K8s CronHPA+HPA 병행 구조([ADR-011](../ADR/ADR-011-CronHPA-HPA-병행-확장-구조.md))로 재검증할 여지를 남긴다.
- 폴링 주기 조정(3~5초→더 길게)이라는 대안은 검토만 하고 실측하지 않았다 — 실제 프론트엔드 폴링 주기를 함께 바꿔야 하는 제품 결정이라 이번 실험 범위 밖으로 명시적으로 남겨둠
