## 4. 분석

### 4-1. 정보 조회 라우팅은 baseline에서 이미 견고하다

5개 정보 카테고리(과목검색·코드조회·잔여석·분반비교·모호) **전부 100%**. 파라미터도 사실상 100%. 눈에 띈 것:

- **자기수정**: `seats-02` "독일어1" → `search_courses("독일어1")` 빈 결과 → `search_courses("독일어")` 재시도 → 성공. `section-06` "공학수학1"도 동일 패턴.
- **없는 과목 처리**: `seats-10`("운영체제"), `code-10`(코드 `99999999-9`) — 빈 결과를 받고 "미개설/찾을 수 없음"으로 정확히 답하고, 시드에 실재하는 유사 과목(리눅스시스템/시스템보안 등)을 제안. 지어내지 않음.
- **조건 필터**: `search-03`("심준호 교수님 수업"), `search-10`("3학점 전공선택") — Tool이 교수명·학점으로 못 거르는데, `search_courses(keyword="")`로 전체를 받아 스스로 필터. Tool 설계 한계를 모델이 우회.

**파라미터 미스 3건**은 전부 멀티턴에서 "라벨보다 넓은 keyword"였다 — `multiturn-03` t0에서 `keyword="데이터베이스"`(라벨 `데이터베이스설계와질의`), `multiturn-06` t1에서 `keyword="알고리즘"`(라벨 `알고리즘입문`). 넓은 검색이 상위집합을 반환해 답변은 전부 정확했다. 실질 파라미터 정확도는 보고 수치(99.0%)보다 높다.

`multiturn-02` turn1 감점도 같은 성격 — "그럼 자리만 알려줘"에 5회 중 1회 `get_course_by_code`(전 turn에서 얻은 코드로)를 썼다. 라벨은 `search_courses`를 요구했지만 둘 다 유효하고 답변("13석")은 정확했다.

### 4-2. 핵심 발견 — 범위 밖 요청에 Tool을 과잉 호출한다 (42%)

`expect_tool: none`인 60 turn 중 **25건에서 Tool을 호출**했다. 패턴이 뚜렷하다:

| 시나리오 | 질문 | 실패 rep | 모델 행동 |
|---|---|---|---|
| `oos-01` | "나 대신 알고리즘 수강신청 해줘" | 5/5 | 답변에서 **정확히 거절** + `search_courses("알고리즘")` 호출해 과목 목록 제시 |
| `oos-04` | "클라우드시스템 꿀강이야? 과제 많아?" | 5/5 | "강의평은 알 수 없다" 명시 + `search_courses`로 과목 기본정보 제시 |
| `oos-05` | "데이터베이스 신청한 거 취소해줘" | 4/5 | 거절은 깨끗한데 `search_courses`를 먼저 호출 |
| `oos-08` | "딥러닝개론 관심과목에 담아줘" | 5/5 | 거절 + `search_courses`로 과목 정보 제시 |
| `oos-09` | "심준호 교수님 잘 가르치셔?" | 1/5 | 대체로 Tool 없이 깨끗하게 거절 |

**깨끗하게 통과한 범위밖(100%)**: `oos-02`(대기열 순번), `oos-03`(날씨), `oos-06`(졸업 학점), `oos-07`(내 수강 내역), `oos-10`(코딩 대행).

→ 모델은 **"완전 무관/메타 질문"과 "실재 과목에 대한 행동·평가 요청"을 구분**한다. 후자에서 *행동은 정확히 거절*하되 *과목 정보는 반사적으로 조회*한다.

**이게 버그인가 — 판단의 여지가 있다.**
- 제품 관점: "대신 못 해드리지만 정보는 여기 있어요"는 친절한 UX일 수 있다. 실제 답변은 항상 "직접 신청하세요"로 끝난다.
- ADR-010 §9(선착순 클릭 연습) 관점: 조회+제시도 학생이 직접 할 행위를 부분적으로 대신하는 것.
- ADR-010 §8 관점: 불필요한 Tool 호출 = 토큰·지연 비용, 그리고 "행동 거절"이라는 의도와 어긋남.

라벨은 `none`으로 뒀지만 이건 **측정상의 입장**이다. Stage 3-1(범위 밖 거절)에서 시스템 프롬프트로 "거절 상황에서는 조회하지 않는다"를 넣을지 결정할 사안이고, **이 42%가 그 Before 값**이다.

### 4-3. 멀티턴 컨텍스트 유지는 우수하다

- `multiturn-05`: 3턴("몇 시" → "자리는" → "교수님은?") 전부 앞 과목(인공지능입문) 유지, 답 정확.
- `multiturn-09`: "2분반은?" 대명사 없이 앞 과목(웹프로그래밍 캡스톤) 이어감.
- `multiturn-08` t1: "이 교수님 다른 과목?" → 전체 조회 후 "최종원 교수님은 컴퓨터네트워크Ⅰ만" 정확히 판정.
- `multiturn-03` t1: "화목 분반?" → 3개 분반을 코드로 각각 조회해 스케줄 확인 → 3분반 식별. 정확하나 Tool 3회.

### 4-4. 과잉 fetch — 정확도엔 무해, 비용엔 유해

`section-05`·`multiturn-05/07`·`search-03` 등에서 **`search_courses` 후 결과마다 `get_course_by_code`를 반복 호출**(5/5 재현). 답은 정확하지만 turn당 Tool 호출이 4회까지 늘고, 과목검색 카테고리 토큰이 3,208/turn으로 최고다(`search_courses`가 keyword 없거나 넓으면 92과목 전체를 관측값으로 실음).

### 4-5. 안정성

rep별 정확도 [93.3, 90.7, 93.3, 93.3, 94.7]%, 표준편차 **0.0146**. 70개 중 **64개가 5회 전부 동일 판정**. 나머지 6개 중 3개(`oos-01`·`oos-04`·`oos-08`)는 5회 모두 일관되게 실패(과잉 호출), 3개(`multiturn-02`·`oos-05`·`oos-09`)만 회차별로 갈렸다. 라우팅이 무작위로 흔들리는 게 아니라, 특정 질문 유형에서 체계적으로 특정 방향으로 틀린다.

## 5. 수동 할루시네이션 표본 판정

추론이 개입하는 시나리오 17개(§4에 인용한 것 포함)의 rep 1 답변을 원본 관측값과 대조:

- **지어낸 사실 0건.** 모든 잔여석·교수명·시간표·코드가 tool 관측값과 일치.
- 동점 분반 정확 식별(`section-01`: -1/-3 둘 다 19석), 없는 과목 정확 판정, 축약 keyword 자기수정, 3턴 컨텍스트 유지 전부 관측값 근거.
- 자동 검사(`answer_must_not_include`)도 15/15 통과.

## 6. 결론

1. **Tool 라우팅 자체(정보 조회)는 baseline에서 이미 신뢰할 만하다.** 5개 정보 카테고리 100%, 파라미터 사실상 100%, 과소 호출 0%, 할루시네이션 0%, 안정성 sd 0.015. 여기엔 개선 여지가 크지 않다.

2. **약점은 "언제 Tool을 쓰지 말아야 하는가"다.** 행동 요청(신청/취소/담기)과 주관적 질문(강의평)에 42% 과잉 호출. 정확히 Stage 3-1(범위 밖 거절)이 다룰 지점이고, 이 수치가 그 Before.

3. **비용**: turn당 ~5초, ~2,000토큰. 스트리밍(Stage 2-1) 전에는 체감 지연이 크다. 과잉 fetch를 억제하면 과목검색 카테고리 토큰(3,208/turn)을 줄일 수 있다.

**측정계획서 §8 질문 답**:
- 카테고리별로 어디서 무너지나? → 정보 조회는 안 무너진다. 범위밖(행동 거절)에서만.
- 과잉 호출이 실제로 일어나나? → 그렇다, 42%. 행동/평가 요청에 한정.
- 정확한 값을 Tool 없이 지어내나? → 아니다, 0건.
- 5회 반복에서 흔들리는 질문? → 3개. 전부 라벨 엄격성 또는 유효한 대안 선택이지 무작위 흔들림 아님.
