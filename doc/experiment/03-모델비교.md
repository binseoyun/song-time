## 4. 분석

### 4-1. 핵심 발견 — 정확도가 모델 크기와 역상관한다

가장 작고 오래되고 싼 `gemini-3.1-flash-lite`가 완벽(100%, 전 rep, 과잉 호출 0). 이유는 **이 태스크의 변별력이 "절제"에 있었기 때문**이다.

**과잉 호출 — flash 계열이 "친절 과잉":**

| 시나리오 (`expect: none`) | 3.6-flash | 3.7-flash | 3.5-flash-lite | 3.1-flash-lite |
|---|---|---|---|---|
| `oos-01` 신청 대행 | 5/5 조회 | 5/5 조회 | 0 | 0 |
| `oos-04` "꿀강이야?" | 5/5 조회 | 4/5 조회 | 5/5 조회 | **0** |
| `oos-05` 취소 대행 | 4/5 조회 | 0 | 0 | 0 |
| `oos-08` "관심과목 담아줘" | 5/5 조회 | 5/5 조회 | 5/5 조회 | **0** |
| `multiturn-02` 신청대행 후속 | 5/5 조회 | 5/5 조회 | 0 | 0 |

- **flash 계열(3.6/3.7)**: 거절은 정확히 하되 `search_courses`를 같이 호출해 과목 정보를 보여줌 ("못 해드리지만 정보는 여기").
- **`gemini-3.1-flash-lite`**: 거절해야 할 땐 **아예 Tool을 안 부른다.** `oos-04`에서도 "꿀강 정보는 없습니다. 과목 코드를 알려주시면 조회해 드릴게요"로 되물음 — Tool 호출 0.
- flash-lite는 "덜 나서고 시킨 것만" 하는 성향. 절제가 중요한 라우팅 태스크엔 정확히 맞아떨어졌다.

### 4-2. 측정 데이터의 한계·오류 예시

이 실험이 완벽하게 측정한 게 아니다. 실측 데이터에서 확인된 문제:

**(a) 답변 제외 검사 false positive** — `gemini-3.7-flash` `seats-10` rep5. 라벨: `answer_must_not_include: ["30명", "40명", "자리가 있습니다"]`. 모델은 `"운영체제" 과목은 개설되어 있지 않습니다`라고 **정확히** 답하고, 유사 과목으로 클라우드시스템(정원 40명)·리눅스시스템 등을 제시. 조잡한 부분문자열 검사가 실재 대체 과목의 `"40명"`을 잡아 오답 처리 → **할루시네이션 아님. `gemini-3.7-flash`의 실질 답변 제외 검사는 100%.**

**(b) 답변 포함 검사가 다른 걸 측정해버림** — `search-03` / `multiturn-04` = "심준호 교수님 수업" 질문. `search_courses`는 교수명으로 못 거른다.
- **flash 계열**: `search_courses(keyword="")` → 전체 92과목 받아서 → 스스로 "심준호 = 데이터베이스설계와질의" 필터 → 정답 (Tool 한계를 우회).
- **flash-lite 계열**: `search_courses(keyword="심준호")` → `[]` → "못 찾았어요, 과목명으로 다시 검색해 주세요"로 되물음.
- `answer_must_include: ["데이터베이스설계와질의"]`는 "답변에 이 과목이 나오는가"를 재려 했으나, 실제론 **"Tool의 교수명 필터 부재를 모델이 우회하는가"**를 쟀다. flash-lite의 77.8%는 라벨 실패가 아니라 **실제 능력 차이** — 다만 오답을 지어내지 않고 정직하게 되물었으므로(할루시네이션 0), 오답이 아니라 마찰이다. **Tool description에 professor 필터를 넣거나 시스템 프롬프트로 "교수명 질문이면 전체 조회 후 필터"를 지시하면 해소 가능(Stage 3 범위).**

**(c) 파라미터 정확도 라벨 엄격성** — `gemini-3.6/3.7-flash`의 파라미터 미스 3건은 전부 "라벨보다 넓은 keyword". 예: `multiturn-03`에서 `keyword="데이터베이스"`(라벨 `"데이터베이스설계와질의"`), `search-08`에서 `keyword=""` + 각 분반 코드 조회(라벨 `"자바"`). 넓은 검색이 상위집합을 반환해 **답변은 전부 정확**. flash 계열 파라미터 정확도도 실질 100%.

**(d) 좌석 수 드리프트 (실제로는 발생 안 함)** — baseline은 15:28, sweep 3종은 16:52에 실행. 그 사이 연습 앱 신청으로 좌석이 바뀔 수 있었으나, 대조군 과목(`21003183-1` 등)은 두 시점 모두 "정원 60 / 신청 41"로 동일 관측. 라벨이 교수명 위주라 무관.

**(e) 완전한 동일 조건은 아님** — baseline은 단독 실행(`--sleep 1`), sweep 3종은 3-way 병렬(`--sleep 3`). 질문 세트·하네스·채점·시드는 동일. LLM 비결정성으로 재현 시 ±1~2%p 변동 가능(baseline sd 0.015).

### 4-3. `gemini-3.7-flash` — latency가 불규칙하다

baseline(3.6) 대비 과잉 호출은 개선(42%→32%)이지만:
- p95 latency **14.0초**, max **31.6초** (3.6-flash는 p95 8.0초 / max 12.4초). 일부 turn이 매우 느림 — 추론에 시간을 더 쓰는 것으로 보임.
- 과잉 fetch 74/410으로 최다. 토큰도 turn당 2,388로 최고.
- 스트리밍(Stage 2-1) 전에는 실서비스 UX에 부담.

### 4-4. 비용

`gemini-3.1-flash-lite`는 baseline(`gemini-3.6-flash`) 대비:
- turn당 비용 **1/8.5** ($0.00038 vs $0.00326)
- latency **1/3** (p50), p95는 **1/3.4**
- 토큰 **1/2.4**

## 5. 결론 (Gemini 기준, 잠정)

<!-- OpenAI 3종 추가 후 최종 확정 -->

**`gemini-3.1-flash-lite`가 이 태스크에 가장 적합.**
- Tool 라우팅 완벽: 100%, 전 rep 통과, 과잉 호출 0, 파라미터 100%
- 가장 빠르고(p95 2.4초) 가장 쌈(turn당 $0.0004, baseline의 1/8.5)
- 할루시네이션 0
- **유일한 약점**: "교수명으로 검색" 같은 Tool 한계 우회를 안 하고 "못 찾음 + 되물음". 오답은 아니고 마찰. Tool description 개선(professor 필터) 또는 시스템 프롬프트 지시로 해소 가능 — Stage 3에서 다룸.

**차선: `gemini-3.5-flash-lite`** — 거의 비슷하나 과잉 호출 17% 잔존(`oos-04`/`oos-08`), 약간 느리고 비쌈.

**`gemini-3.6-flash`(현행) / `gemini-3.7-flash`는 이 태스크엔 오히려 불리** — "친절 과잉"으로 거절 상황에서도 Tool을 부르고, 3~8배 비싸고, 2~6배 느리다. flash의 강점(Tool 한계 우회 능력)은 이 앱에선 Tool description으로 대체 가능한 수준.

**단, OpenAI(GPT 3종)를 재고 나서 최종 확정.** GPT nano/mini가 flash-lite보다 나을 가능성은 낮아 보이나(가격 비슷~더 비쌈, GPT-5 reasoning은 latency 부담) 측정으로 확인.
