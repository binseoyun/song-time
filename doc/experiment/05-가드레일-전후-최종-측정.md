## 3. 새 약점: RAG 결합이 만든 과목검색 오라우팅

### 3-1. 무엇이 일어났나

전 rep(5/5) 결정적으로 실패한 시나리오 5개 (sd 0.0 — 흔들림 아님):

| 시나리오 | 발화 | 기대 | 실제 |
|---|---|---|---|
| search-02 | "리눅스 들어가는 수업 알려줘" | `search_courses` | `search_syllabus("리눅스")` |
| search-04 | "모바일 관련된 과목 있어?" | `search_courses` | `search_syllabus("모바일")` |
| search-06 | "논리 들어가는 과목 목록 좀 뽑아줘" | `search_courses` | `search_syllabus("논리")` |
| search-09 | "네트워크 관련 강의 뭐뭐 열렸어?" | `search_courses` | `search_syllabus("네트워크")` |
| ambiguous-09 | "시스템 들어가는 수업 중에 자리 있는 거" | `search_courses` | `search_syllabus("시스템")` → `get_course_by_code` ×3 |

**패턴:** keyword가 과목명 조각이면서 동시에 "학문 토픽"처럼 읽히는 경우(리눅스·모바일·논리·네트워크·시스템)
flash-lite가 "내용·주제로 찾기" = `search_syllabus`로 판단한다. 반면 keyword가 명백히 과목명 토큰이면
(데이터베이스·자바·컴퓨터·프로그래밍·심준호) `search_courses`를 정확히 고른다.

### 3-2. 왜 이게 문제인가 (답변 품질 저하)

오라우팅 자체보다 **결과가 나빠진다**:

- **search-09** "네트워크 관련 강의": `search_syllabus` top-3이 네트워크보안 / 학생개설:블록체인 / 딥러닝개론을
  반환 → 답변이 **블록체인·딥러닝을 "네트워크 강의"로 제시**하고, 정작 **컴퓨터네트워크Ⅰ은
  강의계획서가 없어 누락**된다. (답변 포함 검사 실패의 원인)
- **search-06** "논리 들어가는 과목": 답변이 컴퓨터특강을 "논리 과목"으로 포함(약한 의미 유사도).
- **search-02/04**: 답은 맞지만(리눅스시스템/모바일소프트웨어) 강의계획서가 있는 분반 하나만 보여주고
  다른 분반·잔여석·시간표를 놓친다.

즉 `search_courses`는 "이름에 그 단어가 든 과목을 빠짐없이" 주는데, `search_syllabus`는
"의미가 가까운 top-3"만 주므로 **목록형 질문에 부적합**하다.

### 3-3. baseline과의 대비

Before(3.6-flash)는 과목검색 100%였다 — Tool이 2개뿐이라 "과목 찾기"의 갈림길이 없었다.
[ADR-012 §한계](../ADR/ADR-012-챗봇-LLM-모델-선정.md)가 예고한 그대로다: *"RAG 결합(Stage 1) 후
3-Tool 체제에서는 난이도가 달라지므로 같은 세트로 재측정이 필요하다."*

Stage 1-4 에이전트 레벨 측정(라우팅 회귀 세트)에서는 이게 0%로 잡혔는데, 그 세트가 7문항으로
얕았기 때문이다(1-4 결과 §해석). 74문항 전수에서 드러났다.

## 5. E2E latency (실 SSE 경로)

`raw/03-e2e-latency-113.json` — `POST /api/ai/chat`를 nginx(:8090) → Node 프록시 → ai-server SSE로
호출, 15종 질문 × 3라운드 = 45건. `run_tool_eval`의 latency는 `agent.invoke` 구간만이라 Node 인증·
프록시·SSE·`db-chat` 기록이 빠져 있어 별도 측정.

| | time-to-first-token | time-to-done (전체 답변) |
|---|---|---|
| p50 | 1,949 ms | 2,268 ms |
| p95 | 2,890 ms | 3,196 ms |
| mean | 1,924 ms | 2,260 ms |
| max | 3,290 ms | 3,769 ms |

- **스트리밍 UX에서 체감을 좌우하는 건 first-token** — 사용자는 첫 토큰이 뜨면 "응답 중"임을 안다. p50 1.9초 / p95 2.9초.
- 전체 답변 완료까지의 Node 프록시 + SSE + nginx 왕복 오버헤드는 **약 0.3초**(§1 에이전트 invoke p50 2,003ms → E2E full p50 2,268ms, p95 2,910 → 3,196). 작고 일정하다.
- Tool을 안 부르는 거절/단순 코드조회는 first-token ~1.0초, `search_syllabus`(임베딩 왕복)가 끼면 ~3.3초로 가장 느리다.

## 6. 교정 — 무엇을 왜 어떻게

### 6-1. 문제 정의

"개념어 + '수업/과목 (목록) 알려줘'" 발화가 `search_courses`(이름 매칭, 빠짐없이) 대신
`search_syllabus`(의미검색, top-3)로 라우팅된다. 답변이 불완전하거나 관련 없는 과목이 섞인다.

### 6-2. 후보와 결정

| 방향 | 내용 | 리스크 |
|---|---|---|
| (a) 교정 | Tool description / 시스템 프롬프트에 "목록형 → `search_courses` 우선" 신호 | flash-lite 과적합(ADR-012), 진짜 의미검색 케이스 방해 가능 |
| (b) 수용 + 문서화 | 트레이드오프로 기록만 | "네트워크 강의" 물으면 엉뚱한 과목 답하는 게 실사용에서 눈에 띔 |

**결정: (a) — 단, Tool description만, `SYSTEM_PROMPT`는 안 건드림.**
근거: ① 답변 품질 저하가 실사용에서 명백한 문제, ② Stage 3-1의 교훈("교수명 검색은 프롬프트 곡예가
아니라 Tool을 유능하게" — 라우팅 신호는 Tool description 계층에서 가장 강함), ③ `SYSTEM_PROMPT`에
"목록형이면 `search_courses`"를 넣으면 "동적계획법이랑 그리디 배우는 수업" 같은 진짜 의미검색 요청까지
흔들 수 있음(flash-lite는 프롬프트 지시에 특히 민감), ④ 최소 변경 + 5회 재측정으로 회귀 확인.
