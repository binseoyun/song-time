# 실험계획서 01: 수강신청 동시성 제어 — "진퇴양난의 늪" 3그룹 대조 실험

- 작성일: 2026-08-10
- 상태: 계획 확정, Group A 실행 전
- 관련: [ADR-006](../ADR/ADR-006-실시간-수강신청-설계.md) 2.1(동시성 제어 대안 비교), [구현계획](../실시간-수강신청-구현계획.md) Stage 0/1

> 이 실험은 단순히 "느리다/빠르다"를 보여주는 게 아니라, **"정합성을 지키면 서버가 죽고, 서버를 살리면 데이터가 망가지는 딜레마"** 를 실측으로 증명하는 것이 목적이다. ADR-006 2.1에서 이론적으로 비교했던 대안들(비관적 락 vs Redis 원자적 연산)을 실제로 재현해, 최종 결정(Redis 원자적 연산)이 "정답을 미리 알고 골랐다"가 아니라 "다른 대안들이 실제로 어떻게 실패하는지 보고 나서 선택했다"는 근거를 만든다.
>
> 세 그룹 모두 **하나의 실험**으로 미리 설계한다. Group A/B(Stage 0)만 먼저 실행하지만, Group C(Stage 1)를 나중에 따로 설계하면 조건이 은근슬쩍 달라져(사후 합리화) 비교가 무의미해진다.

## 0. 실험 범위 (이 실험이 다루는 것 / 다루지 않는 것)

이 실험은 **대기열(Waiting Room)을 거치지 않고, 수강신청 차감 API의 동시성 메커니즘 자체를 시스템에서 분리해 스트레스 테스트**한다. 6장의 스윕 시나리오가 12,000명까지 동시 요청을 올리는 것은 "실제 운영 시 이 API가 12,000명을 동시에 받는다"는 뜻이 아니라 — 실제로는 ADR-006 1.1~1.4의 대기열이 트래픽을 Active 인원(설계상 예시 5,000명 수준)으로 걸러낸 뒤에만 이 API에 도달한다 — **동시성 제어 메커니즘 자체의 파괴점(breaking point)을 부하 강도에 대해 폭넓게 탐색**하기 위함이다. 독립변수를 "동시성 제어 메커니즘" 하나로 유지하기 위해, 대기열이라는 두 번째 변수를 이 실험에 섞지 않는 것은 의도적인 격리다.

**대기열 자체가 트래픽을 실제로 걸러내는지(Phase 1: 대기열 방어 테스트 — 1.2만 VU가 순번 조회 API를 3초 간격으로 폴링할 때 Node.js/Redis Sentinel이 버티는지)와, 대기열을 통과한 Active 수준의 트래픽이 여기서 검증된 안전 범위 안에 들어오는지(Phase 2: 대기열 이후 동시성 검증)는 Stage 2에서 대기열이 실제로 구현된 뒤 별도 실험계획서로 설계한다.** 지금 이 문서에서 결론 내는 "Group C가 N명까지 안전하다"는 결과가, 그 Stage 2 실험에서 대기열의 Active 임계값을 정하는 입력값으로 쓰인다.

## 1. 실험 개요

동일한 "수강신청" 도메인 문제(정원이 있는 자원에 대한 동시 선착순 신청)를 세 가지 동시성 제어 방식으로 각각 구현하고, 동일한 조건에서 부하를 가해 (a) 데이터 정합성, (b) 처리량/지연시간, (c) 장애 양상을 비교한다.

## 2. 실험 목적 및 가설

**목적**: "동시성 제어를 아예 안 하면 데이터가 깨지고, RDBMS 락으로 확실히 막으면 서버가 죽는다"는 딜레마를 실측으로 증명하고, Redis 원자적 연산이 이 딜레마를 어떻게 동시에 해결하는지(혹은 어떤 한계 속에서 해결하는지) 정량적으로 보여준다.

**가설**
- **H1 (Group A, 무방비/No Lock)**: 락 없이 애플리케이션 메모리에서 "읽고 → 계산하고 → 쓰는" 방식은, 정원을 초과하는 동시 요청 하에서 최종 DB 상태 기준 좌석 수가 **음수** 또는 등록 건수가 `capacity`를 초과한다. 반면 락이 없으므로 처리량(TPS)은 세 그룹 중 가장 높게 측정될 것이다("거짓된 성공").
- **H2 (Group B, 비관적 락)**: `SELECT ... FOR UPDATE`로 행 잠금을 걸면 최종 데이터는 절대 `capacity`를 넘지 않는다(정합성 100%). 반면 Sequelize 기본 커넥션 풀(`max: 5`, 4장 참고)이 대기 요청으로 빠르게 고갈되어, 목표 규모(1.2만 명)에 근접할수록 타임아웃과 5xx 에러율이 급격히 치솟고 p95 지연시간이 폭증할 것이다.
  - **예상 반론 방어**: "풀 크기를 500, 1000으로 늘리면 해결되는 것 아닌가?"라는 지적이 나올 수 있다. 두 가지로 방어한다. ① DB 커넥션은 메모리·컨텍스트 스위칭 비용이 드는 값비싼 자원이고, MySQL 서버 자체의 `max_connections` 상한도 있어 무한정 늘릴 수 없다. ② 설령 풀을 늘려도, 문제의 본질은 "동일 과목(row) 하나"에 대한 행 잠금 경합이므로 그 row를 얻으려는 요청들은 여전히 한 줄로 직렬화되어 대기한다 — 풀 크기는 "얼마나 많은 요청을 동시에 대기시킬 수 있는가"만 늘릴 뿐, "한 과목을 얼마나 빨리 처리하는가"는 그대로다. (선택 확장: 풀 크기를 키운 조건을 추가로 한 번 더 측정하면, 붕괴 지점이 뒤로 밀릴 뿐 사라지지는 않는다는 것을 실측으로 보여줄 수 있다 — 11장 참고)
- **H3 (Group C, Redis 원자적 연산 — ADR-006 최종 채택안)**: 정합성(H2 수준)과 처리량(H1에 근접하는 수준)을 **동시에** 만족한다. 다만 RDBMS를 거치지 않는 대신 "Redis 판정 성공 이후 DB 반영 실패" 리스크가 구조적으로 남는다는 점(ADR-006에서 이미 지적된 한계)도 이 실험에서 함께 관찰한다.

## 3. 변수 설계

### 독립변수 (IV)
**동시성 제어 메커니즘** — 3-way

| Level | 이름 | 구현 |
|---|---|---|
| **Group A** | 무방비(No Lock) | 애플리케이션에서 `SELECT`로 잔여좌석을 읽어 JS 변수에 담고, `> 0`이면 그 값을 계산해 `UPDATE`로 블라인드 SET (락/트랜잭션 없음) |
| **Group B** | 비관적 락(Pessimistic Lock) | 동일 로직을 `sequelize.transaction` + `lock: t.LOCK.UPDATE`(`SELECT ... FOR UPDATE`)로 감쌈 |
| **Group C** | Redis 원자적 연산 | ADR-006 2.1/2.2 — Lua Script로 `DECR`+검증을 원자 처리 후 RabbitMQ로 비동기 영속화 |

> ⚠️ **구현 시 반드시 지켜야 할 것 (Group A)**: Sequelize의 `instance.decrement('col')`은 SQL 레벨에서 `UPDATE ... SET col = col - 1`로 변환되어 **그 자체로 원자적**이라 레이스가 재현되지 않는다. Group A는 반드시 "현재 값을 애플리케이션 메모리로 읽어들인 뒤, 그 값을 기준으로 계산한 새 값을 블라인드 `SET`"하는 방식으로 구현해야 고전적인 lost-update 레이스가 실제로 재현된다.

### 종속변수 (DV)

| 구분 | 지표 | 비고 |
|---|---|---|
| Primary (정합성) | 최종 좌석 상태 | `capacity − 최종 잔여좌석` vs 실제 `registrations` 행 수 — 둘의 불일치 여부와 초과/음수 여부 |
| Primary (성능) | Throughput (TPS) | k6 `http_reqs` rate |
| Primary (성능) | API 응답 Latency p50/p95/p99 | k6 `http_req_duration`. **Group C는 이 값이 "Redis 판정까지 걸린 시간"일 뿐, DB에 실제로 확정되기까지의 시간이 아니다** — 아래 "E2E 리드 타임" 참고 |
| Primary (성능, Group C 전용) | E2E 메시지 처리 리드 타임(Lead Time) p50/p95/p99 | RabbitMQ에 발행(publish)한 시각과 워커가 DB `INSERT`를 완료한 시각의 차이. 메시지 payload에 `publishedAt` 타임스탬프를 싣고, 워커가 `INSERT` 완료 시점에 `insertedAt − publishedAt`을 계산해 로그(또는 Prometheus 히스토그램)로 기록한다. API 응답이 빨라도 이 값이 크면 "실제 확정은 느리다"는 뜻이므로, Group C 성능을 "API 응답이 빠르다"만으로 주장하지 않기 위한 지표. |
| Primary (장애) | 에러율 및 에러 유형 | 5xx 비율, 타임아웃 비율, DB 커넥션 획득 실패 비율 (Group B 핵심 관찰 지표) |
| Secondary | DB 커넥션 풀 대기 큐 길이(peak) | Group A/B만 해당. Sequelize pool 이벤트 또는 `SHOW PROCESSLIST`로 관찰 |
| Secondary | Redis/RabbitMQ 지연, 큐 최대 깊이 | Group C만 해당 |
| Primary (어뷰징 내성) | 불법 데이터 건수 | 매크로 다중클릭으로 인한 중복 등록 건수, 시간표 겹침 상태로 등록된 건수 (6장 어뷰징 시나리오) |
| Primary (멱등성) | 워커 강제 종료 후 중복 삽입 건수 | Group C만 해당. 카오스 시나리오(7장) 실행 후 동일 `(user_id, class_id)` 조합이 2건 이상 존재하는지 |
| Primary (구조적 한계 실증) | 유령 차감(Ghost Decrement) 건수 | Group C만 해당. `(초기 Redis 좌석 − 최종 Redis 좌석) − (최종 registrations 행 수 + 아직 처리 중인 in-flight 메시지 수)`. 0보다 크면 "DECR은 됐지만 DB에도 큐에도 흔적이 없는" 유령 차감이 실제로 발생했다는 뜻. Producer 카오스 절차(7장) 실행 후 측정. |
| Secondary (참고, 판정 기준 아님) | PK(auto_increment) 건너뜀(Gap) 관찰 | Group C만 해당. `INSERT IGNORE`는 실패해도 InnoDB의 auto_increment 카운터를 이미 소모한다. 부하 종료 후 `information_schema.tables`의 `AUTO_INCREMENT` 값과 실제 행 수 차이를 기록 — 이 시스템에 기능적 악영향은 없는 정상적인 부수 현상이며, H3 판정에는 영향을 주지 않는 순수 관찰 항목이다. |

### 통제변수 — 세 그룹 간 반드시 동일

- **대상 과목**: 동일 `class_id`, 동일 `capacity`
- **DB 커넥션 풀 크기**: `max: 5` (Sequelize 기본값)로 **명시적으로 고정**하고 문서에 박아둔다 — 지금 `config/database.js`에 pool 옵션이 없어 암묵적 기본값에 의존 중인데, 재현성을 위해 실험에서는 이 값을 코드에 명시적으로 지정한다.
- **부하 프로파일**: 동일 k6 스크립트(호출 엔드포인트만 스위치), 동일 VU 수, 동일 ramp 패턴, 동일 실행 시간
- **테스트 계정 풀**: 동일한 사전 시딩 스크립트로 생성된 동일 수·동일 속성의 학생 계정
- **실행 환경**: 동일 머신, 동일 docker-compose 리소스 제한 (backend 컨테이너 CPU/메모리 limit 명시)
- **DB 초기 상태**: 매 회차 실행 전 대상 과목의 좌석 카운터를 `capacity`로 리셋, `registrations` 행 전부 삭제 (Group C는 Redis 카운터도 함께 리시딩)
- **반복 횟수**: 그룹당 최소 5회 반복 → 평균·표준편차 보고
- **실행 순서**: A→B→C→A→B→C… 교차 실행 (순서 효과/워밍업 편향 방지)
- **k6 클라이언트 타임아웃**: API 서버의 타임아웃 임계치(구현 시 명시적으로 설정 — 예: Node.js `server.timeout` 또는 리버스 프록시 타임아웃)와 동일한 값으로 k6 `timeout` 옵션을 고정한다. Group B는 락 대기로 응답이 크게 지연될 수 있는데, k6가 서버보다 먼저 연결을 포기하면 "서버의 한계"인지 "클라이언트가 지쳐서 끊은 것"인지 원인이 모호해진다.

### 혼입 변수 — 반드시 인지하고 통제

**응답 모델이 그룹 간 다르다.** Group A/B는 완전 동기(요청 자체가 최종 성공/실패를 반환)지만, Group C는 Redis 판정 시점에 응답하고 실제 DB 반영은 RabbitMQ 워커가 비동기로 수행한다. **정합성 판정 기준은 API 응답이 아니라, 부하 종료 후 일정 대기(Group C는 RabbitMQ 큐 깊이가 0이 될 때까지 폴링) 뒤의 "최종 DB 상태"로 통일한다.**

## 4. 테스트 환경 및 인프라 구성

- **실행 위치**: 로컬 `docker-compose` (Stage 2/3에서 kind K8s로 재현 예정 — 이번 실험 범위 아님)
- **구성 요소**
  - 공통: backend(Node.js), MySQL — **커넥션 풀 `max: 5`로 명시 설정**
  - Group C 전용: Redis, RabbitMQ, 비동기 워커(**최소 2개 replica로 구성** — 7장 카오스 절차에서 워커 1대를 죽여도 나머지 워커가 재전송된 메시지를 실제로 받아 처리하는 상황을 만들기 위함. 워커가 1대뿐이면 "재전송을 다른 워커가 받는지" 검증이 불가능하고 단순 재시작 테스트가 되어버린다)
  - 측정 도구: k6, Prometheus, Grafana (ADR-006 4.2)
- **리소스 제한**: backend 컨테이너 CPU/메모리 limit 명시 (실제 K8s 배포와 유사한 조건으로 통제)
- **서버 타임아웃**: 현재 Node.js 서버에 명시적 타임아웃 설정이 없다 — 구현 시 명시적으로 값을 지정하고(예: `server.timeout`), 그 값을 k6 클라이언트 타임아웃(3장)과 동일하게 맞춘다.
- **한계 인정**: 부하 발생기(k6)와 대상 서버가 같은 머신을 공유한다 — k6 자체의 CPU 사용량도 함께 기록해 해석 시 참고한다.

## 5. 그룹별 상세 설계

세 그룹 모두 **동일한 API 계약**(`POST /api/registrations`, 요청 바디 `{ classId }`, 성공 시 201)을 갖는다 — 클라이언트(k6 스크립트)는 어느 그룹을 호출하는지 몰라야 순수 비교가 된다.

| | Group A (무방비) | Group B (비관적 락) | Group C (Redis) |
|---|---|---|---|
| 좌석 확인 | `SELECT`로 읽어 JS 변수에 저장 | `SELECT ... FOR UPDATE` | Redis `DECR` |
| 원자성 | 없음 | 트랜잭션+행 잠금으로 보장 | Lua Script 단일 실행으로 보장 |
| 차감 방식 | JS에서 계산한 값을 블라인드 `UPDATE` | 트랜잭션 내 `UPDATE` (락 보유 중) | Redis 인메모리 `DECR` |
| 락 보유 중 대기 요청 | 없음(대신 데이터가 깨짐) | DB 커넥션을 쥔 채 대기(풀 고갈 위험) | 없음(Redis 싱글스레드가 순간 직렬화, 커넥션 점유 없음) |
| 영속화 | 동기 `INSERT` | 동기 `INSERT` (트랜잭션 내) | Redis 판정 → RabbitMQ → 워커 `INSERT IGNORE` (비동기) |
| 예상 실패 양상 | 데이터 정합성 붕괴 (음수 재고) | 처리량 붕괴 (커넥션 풀 고갈, 타임아웃) | 워커 장애 시 중복 삽입 여부, **Producer(API 서버) 장애로 인한 유령 차감(Ghost Decrement, 아래 참고)** |

> ⚠️ **Group C의 구조적 한계 — Ghost Decrement**: API 서버가 Redis `DECR`을 성공시킨 직후, RabbitMQ에 `Publish`하기 직전(찰나의 순간)에 죽으면(OOM, 프로세스 크래시 등) 좌석은 이미 깎였는데 그 신청 내용은 MQ에도 DB에도 영원히 들어가지 않는다. 이건 워커 장애(재전송으로 복구됨)와 달리 **재시도로 복구되지 않는 진짜 구조적 한계**다. 이 실험에서 정면으로 재현·측정한다 (7장 Producer 카오스 절차).

## 6. 테스트 시나리오

**기본 시나리오**: 정원 100석에 동시 500명 요청 (5배 압력) — Group A의 음수 재고를 뚜렷하게 재현하기 위한 규모.

**확장 시나리오(스윕, 핵심)**: 동시 사용자 수를 50 / 100 / 300 / 500 / 1,000 / 3,000 / 12,000명으로 늘려가며 각 그룹의 "붕괴 시작 지점"을 곡선으로 그린다.
- Group A는 비교적 **낮은 동시성부터** 이미 정합성이 깨지기 시작할 것으로 예상(락이 아예 없으므로).
- Group B는 낮은 동시성에서는 멀쩡하다가, 특정 지점(풀 `max:5` 대비 동시 요청이 훨씬 많아지는 지점)부터 **급격히** 타임아웃/5xx가 치솟을 것으로 예상 — 이 "붕괴 지점"이 어디인지 찾는 것 자체가 유의미한 결과.
- Group C는 전 구간에서 정합성/성능 모두 안정적일 것으로 예상 — 스윕 전체에서 예외가 있는지 확인.

**어뷰징 내성 시나리오 (Group C 중점)**: ADR-006 2.2의 Lua Script는 좌석 차감(`DECR`)뿐 아니라 중복 클릭 방지(`SISMEMBER`)와 시간표 겹침 검증(`SINTER`)까지 하나의 트랜잭션에서 처리한다. 이를 검증하기 위해 부하 시나리오에 다음 두 유형의 "악의적 VU"를 섞는다.
- **매크로 유저**: 동일 과목을 0.01초 간격으로 3회 연속 클릭
- **시간표 겹침 유저**: 대상 과목과 시간이 겹치는 과목을 이미 신청해둔 상태에서, 겹치는 신규 과목을 클릭 (사전에 해당 학생 계정에 겹치는 과목을 시딩해둬야 함)

측정: 부하 종료 후 최종 DB에 (a) 동일 `(user_id, class_id)` 중복 등록 0건, (b) 동일 유저의 시간대 겹치는 등록 조합 0건인지 검증.

> ⚠️ **결정 필요**: Group C는 ADR-006 설계상 이 검증을 필수로 포함한다. Group A/B는 3장에서 "좌석 정합성"만 격리해 테스트하도록 설계했는데, 공정한 비교를 위해 Group A/B에도 동일 수준의 중복/겹침 체크 로직을 넣어 3그룹 모두에서 어뷰징 시나리오를 실행할지, 아니면 이 시나리오는 (ADR-006 2.2가 애초에 Group C 전용 설계이므로) Group C만 검증하고 A/B는 좌석 정합성 비교에만 집중할지는 Stage 0/1 구현 착수 시 결정한다.

## 7. 실험 절차 (반복 가능한 순서)

1. DB 초기화: 대상 과목의 좌석 카운터를 `capacity`로 리셋, `registrations` 삭제 (Group C는 Redis 카운터·Set도 리시딩)
2. 테스트 계정 N명 사전 시딩 (회차마다 재사용 가능)
3. k6 스크립트 실행 (그룹별 대상 엔드포인트만 다르고 그 외 완전 동일)
4. 부하 종료 후: Group A/B는 즉시, Group C는 RabbitMQ **메인 큐**의 깊이가 0이 될 때까지 폴링 대기 **후, DLQ(Dead Letter Queue)에 쌓인 메시지가 없는지 별도로 확인**한다. 메인 큐 깊이만 보면, 처리 실패한 메시지가 DLQ로 격리되어 메인 큐에서는 사라졌지만 DB에는 반영되지 않은 "조용한 유실"을 놓친다 — DLQ가 비어 있어야만 H3(정합성)를 온전히 주장할 수 있다.
5. 최종 DB 상태(좌석 카운터, `registrations` 행 수) 조회 및 기록
6. k6 요약 결과(JSON) + Grafana 스냅샷을 `doc/experiment/raw/`에 저장
7. 1~6을 그룹당 5회 반복, A→B→C 교차 순서로 실행
8. 스윕 시나리오는 동시성 수준별로 1~7 반복

### Group C 전용 절차 — 카오스 엔지니어링(장애 주입)

**목적**: ADR-006 3.2가 설계상 "안전하다"고 주장하는 멱등성(복합 유니크 키 + `INSERT IGNORE`)이, 워커가 실제로 죽는 상황에서도 실측으로 유지되는지 증명한다. 지금까지의 절차는 모든 컴포넌트가 정상 동작하는 happy path만 가정하므로 이 절차가 반드시 필요하다.

0. (사전 조건) 워커가 최소 2개 replica로 살아있는 상태인지 확인한다 — 1대뿐이면 이 절차 전체가 무의미해진다(4장 참고).
1. Group C에 기본 시나리오(또는 스윕 중 임의의 한 수준)로 부하를 걸어 TPS가 피크에 도달한 시점을 확인한다.
2. 피크 도달 직후, 워커 컨테이너 중 **1개만** `docker kill`로 강제 종료하고, 나머지 워커(들)는 계속 살아서 소비 중인 상태를 유지한다.
3. RabbitMQ가 해당 워커의 미확인(un-acked) 메시지를 **살아있는 다른 워커**에게 재전송하는지 RabbitMQ 관리 콘솔/로그로 확인한다 (어느 워커가 최종 처리했는지 워커별 로그에 인스턴스 ID를 남겨 구분한다).
4. 부하 종료 및 4단계(DLQ 확인 포함) 완료 후, 최종 DB에서 동일 `(user_id, class_id)` 조합이 2건 이상 존재하지 않는지(`INSERT IGNORE`가 재전송된 중복 메시지를 실제로 막아냈는지) 검증한다.
5. 재현 절차, 관찰 로그, 최종 검증 쿼리 결과를 `doc/experiment/raw/groupC-chaos-worker-kill.md`에 기록한다.

## 10. 실행 순서와의 관계

이 실험은 [구현계획](../실시간-수강신청-구현계획.md)의 Stage 0(Group A, B 실행 = Before 측정)과 Stage 1(Group C 실행 + 어뷰징/카오스 시나리오 = After 측정)에 대응한다. **Stage 0의 범위가 "naive 버전 1개"에서 "Group A(무방비) + Group B(비관적 락) 2개 구현"으로 확장됨**을 구현계획 문서에도 반영해야 한다.

이 실험이 다루지 않는 "대기열이 실제로 트래픽을 걸러내는가"는(0장) [실험계획서 02](02-대기열-방어-실험계획.md)에서 다룬다 (Stage 2 대기열 구현 완료 후 실행).

**Active 인원 수는 별도로 실험하지 않고, 이 문서의 Group C 스윕 결과에서 바로 산출한다.** Group C는 가설(H3)상 동시성이 아무리 올라가도 정합성이 깨지지 않아야 하는 그룹이므로, Active 인원의 상한을 "정합성이 깨지는 지점"으로 잡을 수 없다 — 대신 **"목표 지연시간(예: p95 500ms) 이내로 유지되는 최대 지속 가능 TPS"** 가 진짜 상한이다. 이 TPS가 나오면 ADR-006 1.5에 이미 정의된 Little's Law 공식(Active 인원 ≈ 지속 가능 TPS × 평균 체류시간)으로 바로 역산된다. ADR-006 1.5의 "5,000명"은 어디까지나 계산 방식을 보여주기 위한 가설적 예시였고, 실제 값은 이 실험의 Group C 스윕 데이터로 대체한다. 단, "평균 체류시간"(사용자가 화면에 머무는 시간)은 이 실험이 측정하는 값이 아니므로 별도 가정 또는 실사용 로그로 보정해야 한다(구현계획 Stage 0의 1.5절 "사용자 로그 및 A/B 테스트로 보정" 참고).

## 11. 예상되는 반론과 방어 논리 (요약)

포트폴리오/면접 상황에서 나올 법한 질문과, 이 문서에 이미 반영된 대응을 정리한다.

| 예상 질문 | 대응 | 문서 위치 |
|---|---|---|
| "커넥션 풀을 500개, 1000개로 늘리면 Redis 없이도 해결되는 거 아닌가요?" | DB 커넥션은 메모리·컨텍스트 스위칭 비용이 드는 자원이고 `max_connections` 상한도 있다. 풀을 늘려도 동일 row에 대한 행 잠금 경합 자체는 해소되지 않아 붕괴 지점이 뒤로 밀릴 뿐 사라지지 않는다. | 2장 H2 |
| "RabbitMQ 큐가 비었으니 데이터 유실이 없다고 어떻게 확신하나요?" | 메인 큐 깊이만으로는 DLQ로 격리된(=DB 미반영) 메시지를 놓친다. 완료 조건에 DLQ 확인을 명시적으로 포함한다. | 7장 |
| "워커가 중간에 죽으면 정말 멱등성이 유지되나요? 설계만 그렇다는 거 아닌가요?" | 실제로 부하 피크에서 워커를 강제 종료(`docker kill`)하고, 재전송된 메시지가 `INSERT IGNORE`로 안전하게 무시되는지 실측으로 검증한다. | 7장 (Group C 전용 카오스 절차) |
| "12,000명을 API에 직접 쏘는 게 실제 트래픽이랑 맞나요? 대기열은요?" | 이 실험은 대기열과 분리해 동시성 메커니즘 자체의 파괴점을 폭넓게 탐색하는 것이 목적이며, 대기열의 실제 방어력은 Stage 2에서 별도 실험으로 검증한다. | 0장 |
| "Group B가 락 대기로 느려진 건지, 클라이언트가 타임아웃 난 건지 어떻게 구분하나요?" | k6 타임아웃을 서버 타임아웃 임계치와 동일하게 명시적으로 고정해, 에러 원인을 서버 지연으로 귀속시킨다. | 3장, 8장 |
| "Group C 응답이 10ms인데, 진짜 DB엔 언제 반영되나요? API가 빠른 척하는 거 아닌가요?" | API 응답 시간과는 별도로, 메시지 발행부터 DB `INSERT` 완료까지의 E2E 리드 타임을 별도 지표로 측정·공개한다. | 3장 (E2E 리드 타임) |
| "워커 1대를 죽였다는데, 그게 재시작 테스트랑 뭐가 다른가요?" | 워커를 최소 2 replica로 구성하고, 죽인 워커가 아닌 살아있는 다른 워커가 재전송된 메시지를 받아 처리하는지까지 확인한다. | 4장, 7장 |
| "`INSERT IGNORE`로 튕겨낸 만큼 PK가 듬성듬성해지지 않나요?" | 맞다. InnoDB 특성상 발생하는 정상적인 부수 현상이며, 이 시스템엔 기능적 악영향이 없다 — 관찰만 하고 정합성 판정 기준에는 포함하지 않는다. | 3장 (PK Gap, 참고 항목) |
