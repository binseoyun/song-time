## 1. 실험 01의 여정

```
Group A(무방비) → Group B(비관적 락) → Group C(Redis 원자적 연산)
   ↓ 정합성 붕괴        ↓ 정합성 확보,        ↓ 정합성 확보 +
                          처리량 붕괴 공유       비동기 반영(RabbitMQ)
                                                  ↓
                          어뷰징 시나리오 실측(인프라 한계 발견)
                          → nginx 튜닝 + backend 이중화 + 시나리오 재설계
                                                  ↓
                          카오스 테스트: 워커 kill(1-8) · API 서버 kill(1-9) · DB 다운(1-10)
```

세 그룹 모두 **같은 조건**(정원 50석, k6 `per-vu-iterations` 스파이크, 동일 동시성 레벨, 동일 반복 횟수)으로 실행해 순수하게 동시성 제어 방식의 차이만 비교할 수 있게 했다.

**정합성 — B/C는 105/105 회차(각 35회×2그룹+A의 정합성 별도판정) 전부 완벽.** A는 레벨 100부터 12,000까지 최소 50건에서 최대 925건까지 정원을 초과했다(최대 정원의 약 19배). B/C는 단 한 번도 초과하지 않았다 — success 표준편차가 전 구간 0.0.

## 3. 가설 검증 종합

| 가설 | 내용 | 결과 |
|---|---|---|
| H1 | Group A는 정합성이 깨지지만 처리량은 가장 높다 | **부분 확인** — 정합성 붕괴는 명확(최대 +925 오버셀). "고처리량"은 저동시성(≤500)에서만 참, 3,000명 이상에서는 B/C와 동일하게 붕괴 |
| H2 | Group B는 정합성은 완벽하지만 커넥션 풀 고갈로 처리량이 급격히 무너진다 | **확인** — 정합성 완벽, 레벨 1,000부터 처리량 흔들리기 시작해 3,000/12,000에서 급락. 다만 A도 같은 구간에서 유사하게 무너져, 순수 커넥션 풀 문제인지 인프라 공통 한계인지는 이 실험만으론 완전히 분리 안 됨 |
| H3 | Group C는 정합성(B 수준)과 처리량(A에 근접)을 동시에 확보한다. 단 "Redis 성공 후 DB 반영 실패" 리스크가 구조적으로 남는다 | **정합성 절반 확인, 처리량 절반 부분 확인.** 정합성은 완벽(오버셀 0, DLQ 0). 처리량은 A/B보다 근소 우위이나 "근접"할 정도는 아님 — 인프라 한계를 그대로 공유. 예견된 리스크(Ghost Decrement)는 카오스 테스트 1-9에서 실제로 재현·확인됨(§5) |

## 4. Group C 어뷰징 시나리오 — 인프라 개선 Before/After

정합성 스윕과 별개로, macro(연타)·overlap(시간표 겹침) 어뷰징 시나리오에서 로컬 인프라 커넥션 한계가 발견됐다(1-7). 원인을 nginx 튜닝(1순위) → backend 2 replica(2순위) → 시나리오 설계 수정(3순위) 순서로 하나씩 고치며 재검증했다.

| 시나리오 | VUS | Before | 1+2순위 적용 | 1+2+3순위 적용 |
|---|---|---|---|---|
| macro unexpected | 3,000 | 92.4% | **0%** | (3,000은 1+2로 이미 완전 해소) |
| macro unexpected | 12,000 | 94.2% | 63.8% | **16.8%** |
| overlap 첫 신청 성공률 | 3,000 | 5.6% | **100%** | — |
| overlap unexpected | 12,000 | 99.1%(성공률 0.9%) | 9.75%(성공률 95.3%) | **0%** |

macro 12,000의 잔여 16.8%는 이 프로젝트가 쓰는 로컬 Docker Desktop 환경이 실제로 **CPU 2코어**뿐이라는 물리적 한계로 판단하고, 시나리오를 더 깎지는 않기로 했다(상세: [트러블슈팅 05](../troubleshooting/05-어뷰징-시나리오-로컬-인프라-커넥션-한계와-개선계획.md)).

## 5. 카오스 테스트 3건 종합 (1-8/1-9/1-10)

Group C의 핵심 계약("Redis 정합성 + RabbitMQ 비동기 반영")이 장애 상황에서도 유지되는지 검증했다.

| # | 시나리오 | 핵심 결과 |
|---|---|---|
| 1-8 | RabbitMQ 워커 kill | 메시지 처리 도중 워커가 죽어도 재전송·멱등성 유지(결정적 테스트 1/1, 자연 조건 6회 중 2회 자연 재전송 — 발생 여부와 무관하게 6/6 전부 무결). 부수 발견: 이 로컬 환경은 `restart: unless-stopped`가 SIGKILL 후 자동 재기동 안 됨(로컬 인프라 한계, K8s에서는 구조적으로 다르게 해결) |
| 1-9 | API 서버(Producer) kill | **Ghost Decrement가 실제로 재현됨**(결정적 테스트) — Redis 등록됨/RabbitMQ 발행 카운터 불변/MySQL 0건. 리컨실리에이션 스크립트로 오탐 없이 탐지 가능함을 확인. 피해자는 재시도 시 409로 영구 차단(수동 개입 없이 복구 불가). 자연 조건 1회 시도에서는 미발생(발행 구간이 극히 짧음) |
| 1-10 | 저트래픽 중 DB 다운 | **republish에 실제 백오프가 전혀 없음을 확인** — 장애 모드에 따라 5회 소진 시간이 65ms(포트 거부)~20초(DNS 실패, 우연한 지연) 사이에서 최대 300배 차이. DLQ 격리된 메시지는 DB가 복구돼도 자동으로 안 살아남(수동 재처리 필요) |

세 테스트 모두 **핵심 정합성(오버셀·중복 등록 0건)은 모든 장애 상황에서 깨지지 않았다.** 반면 **비동기 반영 경로의 완전성(메시지가 반드시 MySQL까지 도달하는가)** 은 두 가지 실제 취약점(Ghost Decrement, republish 무백오프)이 확인됐다 — 둘 다 이미 설계 단계에서 감수하기로 한 트레이드오프였지만, 이번에 "발생 가능성"이 아니라 "실제로 발생하고, 발생하면 영구적"이라는 구체적 근거로 격상됐다.

## 6. 종합 결론 — 이 아키텍처로 계속 가도 되는가

**결론: 그렇다, 단 두 가지 후속 조치를 Stage 3에 명시적으로 남긴다.**

1. **정합성 계약은 최종적으로 신뢰할 수 있다.** 스윕 105회차 + 어뷰징 재검증 + 카오스 테스트 3종 등 서로 다른 조건 수십~수백 회에서 오버셀·중복 등록이 단 한 번도 발생하지 않았다. Redis Lua Script의 원자성은 정상 조건은 물론 워커 kill, API 서버 kill 상황에서도 흔들리지 않았다.
2. **처리량은 인프라 한계 안에서 A/B보다 근소 우위이며, 이건 애플리케이션 설계가 아니라 로컬 Docker Desktop 환경(CPU 2코어, 단일 호스트)의 한계다.** 실제 배포 목표인 K8s(다중 replica + 관리형 로드밸런서)에서는 이 잔여 병목이 인프라 스케일링으로 상당 부분 해소될 것으로 판단한다.
3. **비동기 반영 경로의 두 가지 리스크(Ghost Decrement, republish 무백오프)는 확률은 낮지만 실재하고 영구적이다.** 이번 실측으로 "증명"은 끝났으므로, 다음 단계는 "개선"이다 — Stage 3에서 DLQ 완전한 보상(Compensation) 로직과 DLX+TTL 기반 지연 재시도 전환을 정식 검토한다(각각 별도 ADR로 대안·트레이드오프를 먼저 정리한 뒤 착수).

Stage 2(대기열 + UI 탭)로 넘어가는 데 이 아키텍처를 재검토해야 할 근거는 이번 실험에서 나오지 않았다.

## 7. 한계

- 로컬 단일 호스트 Docker Desktop 환경(worker 2개, RabbitMQ/Redis/MySQL 전부 한 호스트)에서 진행했다. 실제 클라우드 환경(다중 노드, 관리형 큐/DB)이라면 §2의 3,000명 이상 구간 붕괴, §5의 `restart: unless-stopped` 미동작, §5의 DB 재기동 타이밍 등은 상당 부분 다르게 나타났을 것이다.
- 반복 횟수는 A/B/C 스윕이 각 5회, 카오스 테스트는 시나리오당 1~6회로, 통계적으로 넉넉한 표본은 아니다. 다만 모든 실험에서 핵심 지표(오버셀·중복 등록)의 표준편차가 0이거나(스윕) 반복 시행 간 일관성이 확인돼(카오스 테스트), 재현성 자체는 높다고 판단했다.
- Ghost Decrement와 republish 무백오프는 "가능성"에서 "실측"으로 격상됐지만, 실제 발생 빈도(예: 12,000명 규모 트래픽에서 몇 건이나 발생할지)는 이번 실험 범위 밖이다 — 자연 조건 시행에서는 극히 드물게만 관측됐다.
