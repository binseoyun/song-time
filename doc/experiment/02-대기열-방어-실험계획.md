# 실험계획서 02: 대기열 Active 인원 산정 — 이론적 추정 → 실측 검증(Valve Tuning)

- 작성일: 2026-08-10
- 상태: 계획 확정, Stage 2(대기열 구현) 완료 후 실행
- 관련: [실험계획서 01](01-수강신청-동시성-naive-vs-개선-실험계획.md)(Group C 스윕 결과 재사용), [ADR-006](../ADR/ADR-006-실시간-수강신청-설계.md) 1.1~1.5, [구현계획](../실시간-수강신청-구현계획.md) Stage 2

> "Active 인원 5,000명"이라는 숫자를 리틀의 법칙(Little's Law) 계산값으로만 제시하면 "그 가정이 틀렸으면요?"라는 질문에 약하다. 이 문서는 계산값을 **가설**로만 쓰고, 실제 대기열을 켠 상태에서 그 가설을 검증·조정(Valve Tuning)해 "실측으로 확인된 최적값"을 도출하는 절차를 정의한다.

---

## 1. 실험 개요

대기열(Redis Sorted Set + TTL)이 실제로 1.2만 명 규모의 트래픽을 방어하면서, 대기열을 통과해 "Active" 상태가 된 인원이 목표 응답 속도(p95 500ms) 이내로 수강신청을 처리할 수 있는 **최적 Active 인원 수**를 3단계(이론적 상한 측정 → 가설 수립 → 실측 조정)로 산정한다.

## 2. 왜 계산만으로는 부족한가

- **임계점(Tipping Point)의 불확실성**: 서버는 임계점 직전까지 평온하다가 Active 인원이 일정 수를 넘는 순간 TPS가 수직으로 무너지는 구간이 있다. 이 절벽의 정확한 위치는 이론적 계산이 아니라 실측으로만 찾을 수 있다.
- **과소추정에 따른 자원 낭비**: 서버가 10,000명도 버틸 수 있는데 보수적인 계산값(5,000명) 때문에 대기열에 사람들을 불필요하게 오래 세워두면, 실제로는 여유가 있는데도 불만만 쌓인다.
- **Step 1과 Step 3의 조건 차이**: Step 1(이론적 상한 측정)은 대기열 없이 API를 직접 때린 값이라, 대기열 자체의 오버헤드(Redis `ZADD`/`ZRANK`/`ZREM` 연산, TTL 관리)가 빠져 있다. 이 차이를 실측으로 메우지 않으면 이론값과 실제 운영값이 어긋날 수 있다.

## 3. 실험 목적 및 가설

**목적**: Active 인원 수를 "계산된 가설"에서 "k6 부하 테스트로 검증된 값"으로 격상시킨다.

**가설**
- **H1**: [실험계획서 01](01-수강신청-동시성-naive-vs-개선-실험계획.md) Group C 스윕에서 얻은 최대 방어 TPS에 평균 체류 시간을 곱한 초기값(N)은, 대기열의 실제 오버헤드 때문에 실측 안전 상한과 차이가 난다(방향은 사전에 단정하지 않음 — 대기열 오버헤드가 상한을 낮출 수도, 반대로 스윕 시 없던 완충 효과로 높일 수도 있다).
- **H2**: Step 3의 반복적 조정(Valve Tuning)을 거치면, p95 500ms 이내 & 에러율 0.1% 미만을 만족하는 최대 Active 인원(N*)에 수렴한다.

## 4. 3단계 실험 설계

### Step 1 — Limitless Test (수문 개방 테스트)

**이 단계는 새로 실행하지 않고 [실험계획서 01](01-수강신청-동시성-naive-vs-개선-실험계획.md)의 Group C 스윕 결과를 그대로 재사용한다** (대기열 없이 차감 API에 직접 부하 — Group C 실험과 조건이 동일함). 단, 01의 스윕 간격(50/100/300/…/12,000)은 성겨서 붕괴 지점 근처의 정확한 임계 TPS를 특정하기 어려울 수 있다 — 필요하면 붕괴 지점 근방(예: 01에서 관찰된 구간의 ±20%)에서 더 촘촘한 간격으로 추가 측정을 한 번 더 수행한다.

**산출물**: `λ_max` — **SLO를 만족하는 최대 처리량(Maximum Throughput under SLO)**. "p95 지연시간 500ms 이내"라는 목표(ADR-006 4.2 KPI)를 지키면서 시스템이 지속 가능하게 처리할 수 있는 초당 요청 수(req/s)다.

> 💡 **용어 정정(2026-08-19)**: 이전 버전은 이 값을 `T_max`로 표기했는데, 이건 업계 표준 용어가 아니라 이 문서가 붙인 자체 축약이었다. `λ`(람다)는 Little's Law(`L = λW`, ADR-006 1.3/1.5, 실험계획서 02 §3)에서 이미 "처리량"을 가리키는 표준 큐잉 이론 표기로 쓰고 있으므로, 같은 개념에 같은 기호를 일관되게 쓰기 위해 `λ_max`로 정정한다. SRE/용량 계획(Capacity Planning) 맥락에서는 이 개념 자체를 보통 "capacity"(SLO를 만족하는 한도 내 처리량)라고 부른다 — Google SRE 도서의 용량 계획 챕터가 대표적 용례다.

### Step 2 — 가설 수립 (Little's Law 적용)

`N_초기 = λ_max × 평균 체류 시간`

- 평균 체류 시간은 이 실험이 직접 측정하는 값이 아니다. 구현계획 Stage 0의 "1.5 부하 테스트로 확인해야 할 파라미터"에서 정의한 가정치(초기 가설 30~60초)를 사용하고, 출처를 명시한다.
- `N_초기`는 Step 3의 시작점(가설)일 뿐, 최종값이 아니다.
- **이 가정치(평균 체류 시간)는 Step 3의 k6 스크립트가 실제로 시뮬레이션하는 값과 반드시 일치해야 한다** — 아래 Step 3의 Think Time 참고.

### Step 3 — Valve Tuning (수문 조절 테스트, 핵심)

> ⚠️ **k6는 사람이 아니다 — Think Time을 반드시 시뮬레이션해야 한다.** k6 VU가 Active 게이트를 통과하자마자 0.01초 만에 API를 호출하고 세션을 끝내버리면, 실제로는 유저가 화면을 보고 과목을 고르고 클릭하는 데 걸리는 체류 시간(Step 2의 평균 체류 시간 가정치, 예: 15~45초) 동안 Active 슬롯을 붙잡고 있는 상황이 전혀 재현되지 않는다. 그러면 대기열이 비현실적으로 빨리 빠지는 "거짓 성공"이 나오고, `N*`이 실제보다 과대평가된다. **k6 VU는 Active 게이트 통과 후 `sleep(15 + Math.random() * 30)`처럼 무작위 대기(Think Time)를 반드시 거친 뒤 수강신청 API를 호출하도록 스크립트를 작성한다.** 이 Think Time 분포는 Step 2에서 가정한 평균 체류 시간과 반드시 동일한 값(구간)을 써야 한다 — 다르면 Step 2의 가설과 Step 3의 실측이 서로 다른 전제를 검증하는 셈이 되어 비교가 무의미해진다.
>
> (선택 확장) 1지망 과목이 정원 초과로 튕겼을 때 곧바로 2지망 과목을 재시도하는 흐름까지 시뮬레이션하면 더 현실적이지만, 초기 구현에서는 필수 요건(무작위 Think Time)만 반영하고 이 부분은 여력이 되면 추가한다.

1. 대기열 시스템을 켠 상태로 Active 인원 제한을 `N_초기`로 설정한다.
2. 1.2만 명 규모의 대기열 부하(k6)를 발생시킨다 — 대기열 진입 → TTL 부여 → Active 게이트 통과 → **Think Time(무작위 대기)** → 수강신청 API 호출까지 End-to-End.
3. 판정: `p95 500ms 이내` AND `에러율 0.1% 미만`을 모두 만족하는가?
   - **만족(여유 있음)**: Active 인원을 `+1,000`명 단위로 올려 재측정.
   - **불만족(붕괴)**: Active 인원을 `-1,000`명 단위로 내려 재측정.
4. 조정 폭을 처음엔 1,000명 단위로 시작하고, 만족/불만족이 뒤집히는 구간을 찾으면 조정 폭을 500명 → 200명으로 좁혀가며 수렴시킨다(이진 탐색과 유사한 방식).
5. **정지 조건**: 조정 폭이 200명 미만으로 좁아지거나, 총 조정 횟수가 8회에 도달하면 그 시점의 최대 만족값을 `N*`(최종 Active 인원)으로 확정한다. (정지 조건을 미리 정해두지 않으면 "몇 번을 더 조정해야 충분한가"가 모호해져 결과가 자의적이 된다.)

## 5. 변수 설계

### 독립변수 (IV)
Step 3에서 조정하는 **Active 인원 설정값**

### 종속변수 (DV)

| 지표 | 설명 |
|---|---|
| p95 Latency | 대기열 진입부터 수강신청 완료까지 End-to-End, 그리고 Active 게이트 통과 후 수강신청 API만의 p95 둘 다 기록 |
| TPS | Active 게이트를 통과해 실제 처리되는 초당 신청 건수 |
| 에러율 | 5xx, 타임아웃 비율 |
| 대기열 자체 오버헤드 | 대기열 진입/순번 조회 API 자체의 응답 시간, Redis `ZADD`/`ZRANK`/`ZREM` 명령 지연 — Step 1(대기열 없음) 대비 Step 3(대기열 있음)의 차이를 보기 위함 |
| 이탈률 | TTL 만료로 대기열 밖으로 밀려나는 비율 (너무 낮은 Active 인원 설정의 부작용 지표) |

### 통제변수
- 대기열 총 부하: 항상 1.2만 명 고정 (Active 인원만 변화)
- TTL 값: [구현계획](../실시간-수강신청-구현계획.md) Stage 0/1에서 확정된 값으로 고정
- 대상 과목/정원, 실행 환경(리소스 limit 등): [실험계획서 01](01-수강신청-동시성-naive-vs-개선-실험계획.md) 4장과 동일 조건 유지
- k6 클라이언트 타임아웃: 01문서와 동일하게 서버 타임아웃과 일치시킴
- **k6 VU의 Think Time 분포**: Active 게이트 통과 후 API 호출 전 무작위 대기(예: 15~45초 균등분포)를 모든 Step 3 실행에서 동일하게 고정하고, Step 2의 평균 체류 시간 가정치와 반드시 같은 값을 쓴다(위 Step 3 경고 박스 참고).

## 6. 타당도 위협과 통제

| 위협 요인 | 설명 | 통제 방법 |
|---|---|---|
| 정지 조건 모호성 | "언제까지 조정할지" 기준이 없으면 결과가 자의적으로 결정됨 | 5장 4~5단계에 조정 폭 축소 규칙과 최대 반복 횟수(8회)를 명시 |
| Step1/Step3 조건 혼동 | 대기열 오버헤드가 빠진 Step1 값을 최종값으로 오인 | Step3에서 대기열 오버헤드를 별도 DV로 명시 측정, Step1은 어디까지나 초기 가설용임을 강조 |
| 평균 체류 시간 가정의 임의성 | Step2의 가정치가 실측이 아니라 결과 전체의 신뢰도에 영향 | 가정치의 출처를 명시하고, 실제 사용자 로그 확보 후 재계산 여지를 남김(구현계획 1.5) |
| 반복 측정 노이즈 | 매 조정 라운드가 1회 측정이면 노이즈에 취약 | 각 Active 인원 설정값에서 최소 2회 반복 후 평균으로 만족/불만족 판정 |
| **k6 봇의 비인간적 속도(Think Time 누락)** | k6 VU가 Active 통과 즉시 API를 호출하고 세션을 끝내면, 실제 유저가 30초 넘게 슬롯을 점유하는 상황이 재현되지 않아 대기열이 비현실적으로 빨리 빠지고 `N*`이 과대평가됨 | Step 3 k6 스크립트에 무작위 Think Time(`sleep`)을 필수로 삽입, Step 2 가정치와 동일한 분포 사용 |

## 8. 완료 조건 및 후속 반영

- `N*`(최종 Active 인원)을 [구현계획](../실시간-수강신청-구현계획.md) Stage 2와 [ADR-006](../ADR/ADR-006-실시간-수강신청-설계.md) 1.1~1.4에 실측값으로 반영한다.
- "리틀의 법칙으로 계산했다"가 아니라 **"계산된 가설을 k6 부하 테스트로 실측 검증해 물리적 임계점을 확인한 값"** 이라는 근거를 포트폴리오 서술에 명시한다.
