## 1. 문제 상황

### 1-1. 옛 `/recommend`의 한계

기존 AI 기능은 프론트의 "직무 버튼"(백엔드 개발 / 데이터 분석 / PM)을 누르면:

```
프론트 → Node: { jobInterest, major }
Node → ai-server: 전체 강의 목록(수십~수백 과목의 코드·이름·요일·시간)을 통째로
ai-server → Gemini: "아래 강의 목록 중 이 직무에 맞는 3~4개 골라줘" + 전체 목록을 프롬프트에 삽입
Gemini → { recommended_codes: [...] }   (단발 호출, 대화 아님)
```

문제:
- **근거가 없다.** 왜 그 과목인지, 평가 방식은 어떤지, 선수과목이 있는지 답할 수 없다.
- **확장이 안 된다.** 과목이 늘수록 프롬프트가 선형으로 커지고(비용↑), "건초 더미에서 바늘 찾기"로 정확도가 떨어진다.
- **대화가 아니다.** "그럼 그 중에 자리 있는 건?" 같은 후속 질문이 불가능하다. 화면엔 "AI 분석 중...(30초)"이 떴지만 실제로는 백그라운드 배치 호출 한 번이었다.

### 1-2. 원하는 것

학생이 자연어로 이런 걸 묻고 **서버가 가진 실제 데이터에 근거한** 답을 받는 상담 챗봇:

- "이번 학기에 데이터베이스 관련 과목 뭐 있어?" → 실시간 잔여석과 함께 목록
- "네트워크보안 지금 자리 남았어?" → Redis 실시간 좌석
- "알고리즘 강의계획서 평가 비중 어떻게 돼?" → 강의계획서 원문

제약(이 프로젝트의 원칙):
- **새 기능이지만 "기능 나열"이 목적이 아니다.** 로드맵 원칙("문제 정의 → 측정 → 개선 → 재측정, Before/After 정량")을 그대로 적용한다.
- **읽기 전용.** 신청·취소·관심과목 담기는 대행하지 않는다 — "선착순 클릭 연습"이 앱의 목적이라, 챗봇이 대신 신청하면 연습 자체가 무의미해진다(ADR-010 §9).
- **로컬 `docker-compose`로 완결**, 이후 K8s·클라우드 배포까지 이어질 수 있는 구조.

## 2. 어떻게 풀었나

### 2-1. 아키텍처 결정 (ADR-010)

#### 언어·서비스 배치 — Python `ai-server` 확장 (§2)

Gemini SDK가 이미 `ai-server`(Python, 시간표 생성 알고리즘 담당)에 있었고, 벡터 DB·PDF 파싱 생태계가 Python이 강했으며, 옛 `/recommend`도 여기 있었다. Node backend에 새로 붙이는 것보다 자연스러웠다.

#### 상태 소유 경계 — 완전 MSA 분리 (§3, 2026-08-21 재검토로 뒤집음)

**처음엔** "Python은 오케스트레이션만, 대화 상태(Redis/MySQL)는 Node가 소유"로 정했다. **재검토에서** MSA 원칙(분산 데이터, 서비스가 자기 데이터스토어 소유)을 끝까지 적용하는 쪽으로 뒤집었다:

- `ai-server`가 **컴퓨트 + `redis-chat`(최근 대화 캐시) + `db-chat`(MySQL, 영구 히스토리, Alembic 관리) + Qdrant(벡터 DB)**를 전부 직접 소유·연결한다.
- Node는 (1) 인증 게이트웨이, (2) 잔여석·과목 조회용 공개 API 제공자 역할만 남는다.
- Node → `ai-server`는 `authMiddleware`로 인증 후 `x-user-id` 신뢰 헤더로 프록시한다. `ai-server`가 외부에 포트를 노출하지 않는다는 게 이 헤더를 신뢰하는 보안 전제다.

기존 Group C의 `redis`(대기열·좌석 카운터, 지연 민감)와 챗봇의 `redis-chat`을 **인스턴스·접속 주체 모두 분리**했다 — 워크로드 성격이 전혀 다르고(noisy neighbor 리스크) 같이 쓸 이유가 없었다.

#### Tool vs RAG 이원화 (§7)

- **정답이 하나인 값**(잔여석·시간표·정원·교수) → Node API를 호출하는 함수 Tool
- **자연어 매칭이 필요한 것**(강의계획서 본문) → 벡터 검색 RAG

데이터 소스까지 분리했다(Node API vs Qdrant). 나중에 밝혀지지만 **이 두 갈래를 모델이 헷갈리는 게 이 프로젝트의 대표적 회귀**가 된다(§2-3, Stage 3-3).

#### write Tool 배제 (§9)

신청·취소·관심과목 담기는 항상 사용자가 직접 한다. 부수 효과로, "Tool에 사용자 식별자를 어떻게 안전하게 전파할까" 문제 자체가 소멸했다 — read-only Tool들은 로그인 여부와 무관하게 같은 답을 주는 공개 데이터다.

#### Vector DB — Chroma → Qdrant (§4, 2026-08-27 재검토)

처음엔 임베디드 Chroma로 정했다가, **K8s + AWS/GCP 실배포가 로드맵에 확정**되면서 재검토 조건이 충족됐다. Qdrant는 공식 Helm 차트·클라우드 관리형·로컬↔클라우드 API 연속성이 있다. RAG 코드 착수 전이라 전환 비용이 ≈ 0이었다.

#### SSE 스트리밍 (§11)

턴당 응답 생성에 ~2초가 걸려, 비-스트리밍이면 그 시간 내내 빈 화면이 유지됐다. LangGraph 실행 엔진의 `stream_mode=["updates","messages"]`로 (1) 최종 답변 토큰을 생성되는 대로 흘려보내고 (2) Tool 호출 사실을 별도 이벤트로 알린다. nginx·Node·ai-server 3중으로 버퍼링을 해제해야 "타이핑되듯" 나온다.

#### 프레임워크 — LangChain `create_agent` (§12, 2026-08-23 재검토)

원래 `AgentExecutor` + `create_tool_calling_agent`로 쓸 계획이었으나, LangChain 1.0에서 이 API가 **완전히 제거**됐다(버전 고정 없이 설치했다가 ImportError로 발견). `create_agent`(내부는 LangGraph StateGraph 컴파일)로 전환했다. `max_iterations` → `recursion_limit`, `AIMessage.content`가 문자열이 아니라 콘텐츠 블록 리스트로 오는 것 등 마이그레이션 이슈를 실제 실행 중 하나씩 잡았다.

### 2-2. 모델 선정 — 7종 비교, 반직관적 결과 (ADR-012)

같은 70문항 벤치마크 × 5회 반복으로 `CHAT_MODEL`만 바꿔가며 측정했다.

| 지표 | 3.6-flash (baseline) | 3.7-flash | 3.5-flash-lite | **3.1-flash-lite** | gpt-4o-mini | gpt-5-nano | gpt-5-mini |
|---|---|---|---|---|---|---|---|
| Tool 선택 정확도 | 93.1% | 94.9% | 97.3% | **100%** | 92.5% | 90.3% | 86.9% |
| 과잉 호출률 | 41.7% | 31.7% | 16.7% | **0%** | 21.7% | 45.8% | 46.7% |
| latency p50 (ms) | 4,919 | 5,148 | 1,941 | **1,672** | 11,155 | 10,983 | 14,753 |
| turn 오류 | 0 | 0 | 0 | **0** | 0 | **16** | 0 |
| $/1,000 turn | 3.26 | 3.26 | ~0.5 | **0.38** | ~0.2 | ~0.1 | ~0.4 |

**반직관적 핵심 발견: 정확도가 모델 크기와 역상관이었다.** 이 태스크의 난이도는 "언제 Tool을 쓰는가"가 아니라 **"언제 안 쓰고 참는가"**(신청 대행·강의평 질문에 반사적으로 검색하지 않기)에 있었고, 작은 `flash-lite`가 "덜 나서는" 성향이라 오히려 완벽했다. flash 계열(3.6/3.7)은 거절해야 할 상황에도 `search_courses`를 호출하는 "친절 과잉"을 보였다.

**GPT 3종은 전부 부적합**했다: 과잉 호출 46%(7종 중 최악), gpt-5-nano는 recursion-limit 무한 루프 16건, gpt-4o-mini는 "절대 추측 안 함" 지시를 어기고 Tool 없이 자기 지식으로 답한 케이스, latency p50 11~15초.

> **중복 실행 사고**: OpenAI 자동 poller와 수동 실행이 겹쳐 GPT 3종이 6개 컨테이너로 시작 → 중복 kill, ~$0.3-0.5 낭비. `run_in_background`로 띄운 `nohup docker compose run &`는 자식 프로세스까지 죽지 않는다는 걸 배웠다.

### 2-3. Tool 라우팅 — baseline → 개선 반복

측정 하네스(`backend/ai-server/eval/`)를 만들었다: 질문 세트(YAML) → `chat.agent` 직접 호출(Node/인증/SSE 우회) → `tool_calls` 캡처 → 순수 함수로 자동 채점(단위 테스트 15개) → 카테고리별·전체 집계. 질문은 **LLM에게 생성을 안 맡기고** 사람이 시드 데이터를 대조하며 손으로 작성했다(청크 어휘를 그대로 베끼면 난이도가 인위적으로 낮아진다).

#### Stage 0-6 baseline (gemini-3.6-flash, 70문항)

- Tool 선택 93.1%, 정보 조회 5개 카테고리 전부 100%, 할루시네이션 0/17.
- **핵심 발견**: 범위 밖 요청(신청 대행·강의평)에 **42% 과잉 Tool 호출** — 행동은 정확히 거절하되 `search_courses`로 과목 정보를 반사적으로 조회했다. 이게 Stage 3-1의 Before.

#### Stage 3-1 — "교수명 검색"을 프롬프트가 아니라 Tool로 고침 (#82)

flash-lite로 넘어오니 "심준호 교수님 수업 뭐뭐 하셔?"가 빈 결과를 반환했다. `search_courses`가 keyword를 `name`(과목명)·`department`(학과명)에만 매칭하고 `professor`는 안 봤기 때문. flash 계열은 `search_courses("")`로 전체를 받아 스스로 필터하는 우회를 했지만 flash-lite는 "시킨 것만" 해서 우회하지 않았다.

두 가지 방법이 있었다:

| 대안 | 방법 | 문제 |
|---|---|---|
| A. 프롬프트로 우회 지시 | "교수명 질문이면 전체 조회 후 professor로 직접 필터하라" | 모델에게 다단계 추론을 떠넘김. flash-lite처럼 지시를 문자 그대로 따르는 모델엔 취약. description이 복잡해짐 |
| **B. `search_courses`가 professor도 매칭** | keyword 필터에 `professor` 조건 1줄 추가 | **Tool이 실제로 그 능력을 갖게 됨.** 모델은 그냥 `search_courses("심준호")`를 부르면 됨 |

**B를 채택**했다 — "Tool은 도메인이 요구하는 조회를 직접 할 수 있어야 하고, 모델에게 우회 추론을 떠넘기지 않는다." 부수 효과로 flash 계열의 "전체 조회 후 자체 필터" 비효율(토큰·지연)도 사라진다.

시스템 프롬프트는 **최소한만** 손댔다(flash-lite 과적합 위험): 거절 대상을 "신청/취소" → "신청·취소·관심과목 담기·강의평"으로 확장하고 "거절 시 조회 Tool 안 씀"을 명시. 재측정의 핵심 목적은 이 변경이 100%를 깎지 않았는지(회귀) 확인.

**결과**: 답변 포함 검사 77.8% → **100%**, Tool 선택·과잉·과소·할루시네이션 전부 유지(회귀 0).

> **실사용 버그가 남아 있었다.** 1차 재측정은 100%였지만 실제 챗봇을 써 보니 `search_courses(keyword="창병모 교수님")`처럼 모델이 **군더더기를 붙여** 넘기면 부분문자열 매칭이 실패해 빈 결과 → "수업 안 하심"이 나왔다. 벤치마크가 핵심어 부분문자열만 체크(`"보안" in "보안 쪽 수업"` → 통과)해서 놓쳤다. **노이즈 토큰 흡수 필터**(전체 문자열 우선 → 실패 시 "교수님·관련·수업" 등 제거한 토큰 매칭)를 추가하고, 벤치마크에 이 케이스를 재현 시나리오로 넣었다(70 → 72문항).

#### Stage 3-1b — 좌석 데이터 소스 단일화 (ADR-013, #86)

챗봇의 "잔여석"이 `capacity - enrolled`였다. 그런데 `enrolled`는 **관심 과목 하트 수** 카운터고, 실제 실시간 수강신청(Group C, Redis)과는 무관했다. 85/85 실과목이 실제 Redis 좌석과 불일치(평균 48.6석 차이), 84개가 "마감" 오답 위험이었다.

`GET /api/courses`가 Redis `class:{id}:seats`(실시간 잔여석)와 `course_interests` 수를 응답에 싣고, 챗봇이 **실시간 잔여석 / 실시간 신청자 수 / 관심 등록 수 3개를 분리**해 답하도록 고쳤다. 벤치마크에 이 3개를 구분하는 시나리오를 추가(72 → 74문항)하고, 결정적 좌석 픽스처(`seedBenchmarkSeats.js`)를 만들어 "구 방식은 틀린 좌석을 답함"이 드러나게 했다.

> **정식 소스를 놓친 정정(#93)**: 위 수정에서 `interest_count`를 `course_interests` COUNT로 잡았는데, 이 앱의 정식 관심 등록 수 카운터는 **`Class.enrolled`**(수업 목록 UI가 표시하는 "n/M명", `demandController`의 CronJob이 매분 재조정)였다. "화면 75명, 챗봇 0명" 버그. **교훈: 값을 분리하기 전에 그 도메인의 정식 소스가 이미 뭔지 확인.**

#### Stage 3-3 — RAG 결합이 만든 오라우팅, Tool description으로 교정 (#113)

재시딩된 시드(소프트웨어학부 2026-2)에 맞춰 74문항을 전면 재작성한 뒤, Stage 0 이후 모든 변경(모델·RAG·프롬프트·좌석·폴백·rate limit)을 켠 상태로 한 번에 측정했다.

- **가드레일만으로는** Tool 선택 93.1 → 93.5%(제자리)처럼 보였다. 하지만 **실패의 성격이 뒤바뀌어** 있었다:
  - baseline의 과잉 호출(41.7%) → **0%** (Stage 3-1 프롬프트 효과)
  - 대신 RAG Tool 결합이 **"개념어로 과목 목록 찾기"를 강의계획서 의미검색으로 오라우팅**하는 새 회귀를 만들었다 (과목검색 100 → 66.7%).
- "리눅스 들어가는 수업 알려줘"를 물으면 flash-lite가 "리눅스 = 학문 주제"로 보고 `search_syllabus`로 갔다. `search_syllabus`는 유사도 top-3만 주므로 목록형 질문에 부적합 — "네트워크 관련 강의"에 **블록체인·딥러닝을 "네트워크 강의"로 제시**하고 컴퓨터네트워크Ⅰ은 강의계획서가 없어 누락했다.
- **`search_courses`·`search_syllabus`의 description 2곳만 교정**(시스템 프롬프트 무변경): 한쪽엔 "한 단어로 과목 나열 요청은 이 Tool", 다른 쪽엔 "세부 개념 여러 개 나열 시만 + top-3라 누락·오염" — **양방향으로** 명시.
- **결과**: Tool 선택 **100%**(sd 0.0, 72/72 전 rep), 회귀 0, 할루시네이션 0/17. latency invoke p50 4.9 → 1.9초, 비용 $3.26 → $1.00/1000turn.

> **왜 프롬프트가 아니라 Tool description이었나**: 라우팅 신호는 모델이 Tool 설명을 읽고 판단하는 지점에서 가장 강하다. 프롬프트에 "목록형이면 search_courses" 같은 규칙을 넣으면 "동적계획법이랑 그리디 배우는 수업" 같은 진짜 의미검색 요청까지 흔들 수 있다(flash-lite는 프롬프트 지시에 특히 민감). 실제로 Tool description만 고쳤더니 의미검색 라우팅에 회귀가 0이었다.

> **헤드라인 하나로 뭉뚱그리지 않았다**: "93.1% → 100%"는 서로 다른 두 개선의 합이다 — (1) Stage 3-1 프롬프트가 baseline의 과잉호출을 잡았고, (2) 이번 Tool description이 RAG가 만든 오라우팅을 잡았다. 실험 문서에 Before / 가드레일 / 교정 후 **3단**으로 남겨, "RAG 결합 시점에 실제로 회귀가 있었다"는 사실이 지워지지 않게 했다.

### 2-4. RAG 구축 (Stage 1)

#### 청킹 — 과목당 1청크, 파서를 만들지 않음 (A3)

강의계획서 19개(숙명 고정 양식, 8섹션)를 **전수 정독**했다. 의미검색용 본문이 얇아서(과목당 ~250토큰) **과목당 1청크**로 정했고, 분반 병합/분리는 본문 해시로 판단했다(내용 동일 → `class_no` 배열로 병합, 다른 교수·다른 내용 → 분리). 19파일 → 18청크.

PDF 자동 파싱 코드는 **안 만들었다**. 18청크 규모에서는 파서가 "이미 한 번 정독한 작업의 재구현"이고, 파서가 가장 약한 필드(개요·평가·주차별)가 곧 수동 override가 필요한 필드다. 정독 산출물을 `rag/syllabi.yaml`(single source of truth)로 커밋하고 로더가 `YAML → 임베딩 → Qdrant`를 돈다(ADR-010 §13, "규모에 안 맞는 복잡도는 안 들인다"). 전학부 확장 시 파서+`overrides.yaml`로 재검토.

구조화 필드(평가 비중·주교재·교수 이메일 등)는 별도 SQL 테이블 없이 **Qdrant 페이로드**로만 저장하고, `get_syllabus`가 course_code 필터로 정확 조회한다.

#### 임베딩·검색

- `gemini-embedding-001`, **3072차원**, **비대칭 임베딩** — 문서는 `retrieval_document`, 질의는 `retrieval_query` task_type. "질문 ↔ 답이 되는 문서"가 가까워지도록 학습된 방식이다.
- `search_syllabus`: 코사인 유사도 **top-3**, **컷오프(threshold) 없음**. 재적재는 `recreate_collection`(전체 wipe-and-reload).

#### 측정 — naive(Before) vs RAG(After)

옛 `/recommend`가 "전체 과목 텍스트를 프롬프트에 주입"하는 방식이었으므로, 그게 자연스러운 naive 베이스라인이다.

| 지표 | naive (Before, 전문 주입) | RAG (After, top-3) |
|---|---|---|
| 의미검색 정답률 | 100% | 100% (hit@3) / hit@1 97.1% |
| 미등록 할루시네이션 | 0% | 0% |
| turn당 토큰 (의미검색) | 9,332 | **4,268** (2.19× 절감) |
| p50 latency | 1,195 ms | 2,431 ms (RAG가 왕복 때문에 느림) |

**18청크 규모에서 RAG는 정확도 우위가 없다**(둘 다 100%). RAG의 실질 이득은 (1) 토큰 2.2× 절감, (2) 코퍼스 크기 무관한 확장성, (3) "정확한 값=Tool / 의미검색=RAG" 아키텍처 분리 — naive는 잔여석·시간표를 답할 수 없어 어차피 Tool 에이전트 위에 얹어야 하고, 그러면 corpus + Tool 스키마 + 히스토리로 오히려 더 무거워진다.

threshold는 **두지 않기로** 했다: 정답 top1 relevance(0.649~0.773)와 무관 질문 top1(0.630~0.721) 분포가 겹쳐(갭 없음) 어디에 박아도 정답을 자르거나 노이즈를 통과시킨다. 게다가 미등록·범위밖 pass rate가 이미 100% — 에이전트 추론이 낮은 relevance를 이미 걸러내고 있다.

### 2-5. 운영 가드레일 (Stage 3)

#### 사용자 단위 rate limit — 계층 결정을 뒤집음 (ADR-010 §15 재검토, #108)

**처음엔** "Node 계층 + Group C Redis"로 설계했다. **구현하려니** 완전 MSA 방향과 어긋났다 — Node 4레플리카가 카운터를 공유해야 하는데, 정작 그 카운터는 *챗봇 서비스*의 Gemini 토큰 비용에 관한 것이고 `redis-chat`도 챗봇이 소유한다.

MSA 정석은 2계층이다: **API Gateway(coarse, 요청 수) + 서비스 자체(fine, 도메인 비용)**. LLM 토큰 비용은 "요청 수"가 아니라 "사용자별 호출 빈도"로 관리해야 하고 그 비용 구조를 아는 건 `ai-server`다. 전용 게이트웨이가 아직 없으므로(Node가 겸업) **계층 2부터** 구현했다.

`chat/rate_limit.py`: `POST /api/ai/chat` 진입부에서 `redis-chat` 카운터, `INCR`+`EXPIRE`를 **Lua로 원자화**(두 명령 사이 프로세스 종료 시 "만료 없는 영구 카운터" 방지), TTL 음수면 self-heal, **Redis 장애 시 fail-open**. `CHAT_RATE_LIMIT=20`/`WINDOW=60s`(E2E 측정에서 문제없어 유지). 향후 엣지에 coarse 계층(nginx `limit-rps` / AWS WAF)을 얹으면 defense-in-depth가 된다.

#### 장애 폴백 (Stage 3-2, #106)

- `chat/errors.py` `classify_llm_error(exc)` — 3분류(transient / quota / unknown). **raw 예외는 서버 로그에만**, SSE `error` 이벤트엔 `{message, kind, phase}`만. quota vs transient는 둘 다 HTTP 429라 구체 문구(`exceeded your current quota`·`per day` 등)로만 좁히고, 애매하면 재시도 여지가 있는 transient로 본다.
- `build_llm(max_retries=2)` — 429/503만 LangChain 내장 지수 백오프. 스트리밍이라 사용자가 기다리는 중이므로 2회 제한.
- `_persist_turn` — 성공·부분·실패 **전 경로에서 호출**해 사용자 메시지가 유실되지 않게 한다. 스트림 도중 실패 시 부분 답변에 `[응답이 중간에 끊겼습니다]` 꼬리표를 붙여 저장.
- Tool(과목 API·Qdrant·임베딩) 장애는 각자 catch해서 `{"error": 친절문구}` 반환 → 에이전트가 그 안내를 전달하고 지어내지 않는다.
- 검증: 수동 장애 주입 3종(`stop qdrant` / `stop backend` / `GEMINI_API_KEY=invalid`) → 전부 raw 노출 없이 degrade, 해피패스 회귀 0.

#### 옛 `/recommend` 완전 제거 (Stage 3-4, #115)

새 챗봇이 Stage 3-3 측정까지 끝나 안정성이 검증된 뒤, 프론트 `AIRecommendation.tsx`·Node 라우트·ai-server 엔드포인트를 전부 삭제했다. `/recommend` 전용이던 전역 Gemini 설정과 죽은 config 5키도 함께 제거(순변경 -383줄).

### 2-6. 자동 벤치마크가 못 잡은 실사용 버그 2건

두 건 모두 **실제로 앱을 켜서 대화하다** 발견했고, 그때마다 재현 케이스를 벤치마크에 추가했다.

1. **#93 (interest_count 소스)** — §2-3에 서술. 값을 분리하기 전에 도메인의 정식 소스를 확인하지 않았다.

2. **#117 (후속 질문에서 Tool 재호출 안 함 → 교수 이메일 할루시네이션)** — 강의계획서를 여러 턴 조회한 뒤 "심준호 교수님 이메일 알아?"라고 물으니 `get_syllabus` 재호출 없이 `jhshim@university.ac.kr`을 지어냈다(실제 `jshim@sookmyung.ac.kr`, 앞 턴 관측값에도 있던 값).
   - **원인**: Tool 관측값은 다음 턴 히스토리에 안 남는 설계다(토큰 절약 — `{role, 최종 답변 텍스트}`만 저장). 대화가 "조회 → 설명" 흐름으로 드리프트하면 flash-lite가 재호출을 건너뛴다.
   - **드리프트 의존**: 짧고 깔끔한 3턴이나 오타 없는 과목명으로는 재현이 안 되고, 사용자가 실제로 친 5턴(2턴에 오타 포함)을 그대로 넣으면 5/5 결정적으로 재현됐다. 단일턴 위주였던 기존 벤치마크가 못 잡은 이유.
   - **해결**: `run_rag_eval`에 **멀티턴 지원 + `syllabus_followup` 채점 종류**를 추가(히스토리는 프로덕션과 동일하게 최종 답변 텍스트만 보존, 마지막 턴만 채점). 시스템 프롬프트 2군데 최소 수정 — 강의계획서 값 목록에 "담당교수 이메일·연구실" 추가 + "히스토리에 안 보이면 `get_syllabus` 재호출, 기억에 의존 금지" 1문장.
   - **결과**: 재현 시나리오 0/3 → **5/5**, 라우팅·거절 회귀 0.
   - **왜 프롬프트였나**: 이번 문제는 "어떤 Tool을 고르나"(라우팅, → Tool description)가 아니라 "이미 고른 Tool을 **다시** 부를까"(호출 시점, → 프롬프트)였다.

## 4. 방법론에서 배운 것

1. **조각별 측정과 종합 측정을 둘 다 둔다.** Stage 1-4의 라우팅 회귀 세트(7문항)는 Stage 3-3의 오라우팅을 못 잡았다 — 74문항 전수 재측정이 잡았다. 조각별로 "이 변경이 회귀를 안 만들었나"를 보고, 종합으로 "전부 켠 상태에서 실제로 어떤가"를 본다.

2. **실사용 → 버그 → 벤치마크 강화 루프.** 자동 벤치마크가 100%를 줘도 실제로 앱을 켜서 대화하면 버그가 나온다(#82 노이즈 토큰, #93 좌석 소스, #117 후속 질문). 매번 재현 케이스를 벤치마크에 넣어 회귀 가드로 남겼다(70 → 74 → +멀티턴 kind).

3. **작은 모델일수록 프롬프트를 아끼고 Tool을 유능하게.** flash-lite는 지시를 문자 그대로 따라서 정확도가 100%였다. 그래서 프롬프트에 규칙을 얹으면 인접 케이스가 과적합으로 깨진다. 라우팅은 Tool description에서, "이미 고른 Tool 재호출"은 프롬프트에서 — 문제의 계층에 따라 손대는 곳이 다르다.

4. **헤드라인 숫자를 3단으로 분해한다.** "93.1% → 100%"는 두 개선의 합이었고, 그 사이에 RAG 결합으로 인한 회귀가 실제로 있었다. Before / 중간 / After로 남겨야 "어디서 무엇이 깨졌다"가 지워지지 않는다.

5. **LLM에게 벤치마크 질문 생성을 안 맡긴다.** 청크·시드 어휘를 그대로 베낀 질문은 난이도가 인위적으로 낮다. 1인 개발이라 "누가"는 항상 본인이고, 실질 쟁점은 방식이었다.

## 5. 한계 / 실제 운영이라면

- **코퍼스가 18청크로 작아 RAG의 정확도 우위가 없다.** 지금은 토큰 절감·확장성·아키텍처 분리가 이유다. 전학부(수백 청크)로 확장하면 정확도에서도 RAG가 이기고, 그때 threshold·주차별 세부 청킹을 재검토한다.
- **엣지 coarse rate limit이 없다.** 지금은 서비스 계층(ai-server)만 있다. AWS/K8s 실배포 시 nginx-ingress `limit-rps` 또는 AWS WAF rate-based rule로 IP/커넥션 단위 계층을 얹는다(defense in depth).
- **Tool 관측값이 히스토리에 안 남는다.** #117을 프롬프트로 완화했지만 근본 해법(관측값을 요약해 히스토리에 남기기)은 토큰 비용·설계 영향이 커서 별도 검토 대상으로 뒀다.
- **RAG 재적재가 수동 wipe-and-reload다.** 학기당 1회라 충분하지만, 무중단 갱신이 필요해지면 blue-green 컬렉션 스왑을 도입한다.
- **강의계획서 업로드가 로컬 스크립트다.** 관리자 UI는 스코프 과다로 배제했다 — 운영 규모가 커지면 별도 기능으로.

## 부록. 구현 중 실제로 걸린 함정

- **컨테이너 이미지에 코드가 구워진다.** `syllabi.yaml`·`eval/` 반복 수정 시 `docker compose cp` 후 실행, 최종본만 `docker compose build`. 안 하면 옛 코드로 측정된다.
- **Git Bash에서 `MSYS_NO_PATHCONV=1`** 없이 `docker compose run -v ".../out:/out"` 하면 `/out` 경로가 뭉개진다.
- **`ai-server` command에 `alembic upgrade head &&`** 를 넣었다(backend의 seedData 패턴). `down -v`로 볼륨을 지우면 `chat_sessions`/`chat_messages` 테이블이 없어 챗봇 세션 생성이 깨진다. 멱등.
- **프론트 레이아웃은 전부 인라인 style.** `index.css`가 빌드타임에 고정된 Tailwind 산출물이라 새 클래스가 안 생긴다(이 프로젝트에서 반복된 함정).
- **LangChain 1.x 브레이킹**: `AgentExecutor` 제거, Gemini 모델명 드리프트(`gemini-2.0-flash`가 404). 버전 고정 없이 설치하면 최신이 깔린다.
