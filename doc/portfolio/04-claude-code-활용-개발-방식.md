## 1. 출발점 — 왜 "규칙부터" 만들었나

팀 프로젝트(클라우드시스템 수업)를 개인 포트폴리오로 고도화하면서 두 가지 위험이 보였다.

1. **AI가 빠르게 많이 만들어 버리는 위험** — 기능은 늘지만 "왜 이렇게 했는지"를 내가 설명하지 못하면 포트폴리오로서 가치가 없다.
2. **세션이 끊길 때마다 맥락이 사라지는 위험** — 7주짜리 작업을 여러 대화 세션에 걸쳐 해야 한다.

그래서 코드를 한 줄도 고치기 전에 **AI가 매 세션 읽는 규칙 파일(**`CLAUDE.md`**)** 과 **기준 문서(**`portfolio-roadmap.md`**)** 를 먼저 만들었다.

### 1-1. CLAUDE.md에 고정한 규칙


| 규칙                                                                                     | 목적                                                |
| -------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 모든 의사결정은 문서로. ADR은 `doc/ADR/ADR-NNN-주제.md`, 템플릿은 상황 / 대안과 트레이드오프 / 결정과 이유 / 결과(정량·정성)  | AI가 한 일이 "코드만 남고 이유는 사라지는" 상황 방지                  |
| 리팩토링 → `doc/refactoring/`, 트러블슈팅 → `doc/troubleshooting/`, 포트폴리오 소재 → `doc/portfolio/` | 산출물 위치 고정 → 나중에 찾기 쉬움                             |
| **Phase 순서 준수** (테스트 → 동시성 → K8s → CI/CD → 관측성), 앞 Phase를 건너뛰지 않음                      | AI가 "이왕 하는 김에" 범위를 넓히는 것 차단                       |
| **새 기능 추가 금지** — 문제 정의 → 측정 → 개선 → 재측정만                                                | 기능 개수가 아니라 개선 근거로 승부                              |
| **모든 개선은 Before/After 정량 수치**, 원본은 `doc/experiment/`                                   | "좋아졌다"는 말 대신 숫자                                   |
| 시크릿은 어떤 문서·커밋에도 남기지 않음                                                                 | 팀 레포에서 `.env`/K8s secret 노출 사고를 겪은 뒤 추가 (ADR-001) |


실제로 이 규칙이 AI의 판단을 바꾼 사례:

- **ADR-007**: 대기열 부하 문제를 "지금 바로 K8s HPA로 풀자"는 대안을 AI 스스로 기각 — "Phase 순서 위반 + K8s 전환 효과와 인스턴스 증설 효과가 섞여 가설 검증이 오염된다"는 근거를 ADR에 남김.
- **ADR-004/005/006/010**: 비밀번호 재설정·회원 탈퇴·실시간 수강신청·AI 챗봇은 "새 기능 금지"에 걸리므로, 기존 기능 개선으로 포장하지 않고 **"로드맵 외 작업"으로 솔직하게 분류**해 문서에 명시.



### 1-2. Git 자동화의 승인 범위를 명시적으로 나눔

`CLAUDE.md`에 "Git 작업 자동화 승인" 섹션을 두어 **어디까지 AI가 혼자 해도 되는지** 경계를 그었다 (규칙 원문은 [git-workflow.md](../git-workflow.md), PR #8에서 추가).

- **사전 승인 (매번 확인 없이)**: Issue 생성 → 브랜치(`타입/#N-내용`) → 커밋(`타입: 제목 (#N)`) → push → PR(`Closes #N`, 템플릿 채움)
- **절대 자동 금지**: `main` merge, 브랜치 삭제 → 항상 내가 GitHub에서 diff를 보고 직접
- **애매하면 질문**: 이번 작업과 무관한 기존 변경사항을 같은 PR에 넣을지

결과적으로 66개 PR 전부가 "이슈 번호 → 브랜치 → 커밋 → PR"로 추적되고, 리뷰·머지라는 **마지막 게이트는 사람**에게 남았다. 확인 질문으로 흐름이 끊기는 비용은 없애면서, 되돌리기 어려운 행동만 사람이 쥐는 구조다.

## 2. 작업 한 건의 표준 루프

```
[나] 무엇을 할지 말함 ("Stage 3-3 측정하자")
  → [Claude] roadmap/구현계획 읽고 Phase·Stage 확인
  → [Claude] GitHub Issue 생성 (왜 필요한가)
  → [Claude↔나] 설계 선택지가 있으면 산문으로 설명 → 내가 결정
  → [Claude] 브랜치 생성 → 구현 → 로컬 docker-compose E2E 검증
  → [Claude] Before 측정 → 개선 → After 측정, raw를 doc/experiment/raw/에 저장
  → [Claude] ADR / 실험 결과 / 트러블슈팅 문서 작성, roadmap 진행 상황 갱신
  → [Claude] (필요 시) /code-review → 지적 반영
  → [Claude] commit → push → PR (템플릿: 목적 / 작업 내용 / 테스트 내역 / Closes #N)
  → [나] 결과 소화 → PR 리뷰 → merge
```

핵심은 **"측정 → 문서 → PR"이 한 루프 안에 묶여 있다**는 것. 문서를 나중에 몰아서 쓰지 않기 때문에, 예를 들어 실험 05는 "Before / 가드레일 / 교정 후" 3단 수치가 그 작업 PR 안에 같이 들어갔다.

## 3. 설계 결정은 어떻게 AI와 나눴나



### 3-1. "객관식 카드"를 거절하고 "설명 먼저"로 바꿈

Group C(Redis 원자 연산) 구현 전, Claude가 API 응답 시점·DLQ 임계값·취소 흐름을 선택지 카드(AskUserQuestion)로 두 번 물었는데 **두 번 다 거절**했다. 선택지 설명이 한두 줄이라 "왜"를 판단할 수 없었기 때문이다. 대신 각 선택지의 **메커니즘·실패 시나리오·업계 사례**를 산문으로 깊게 설명해 달라고 했고, 설명을 들은 뒤 한 번에 결정했다.

> "즉시 응답으로 가고(Ghost Decrement 감수), DLQ는 5회, 취소는 동기로 하자"
> → [portfolio/01](01-group-c-redis-설계-결정.md)

이 선호를 Claude의 **피드백 메모리**에 남겨서, 이후 세션에서도 복잡한 트레이드오프는 설명이 먼저 오도록 고정했다.

### 3-2. 첫 결론에 안주하지 않고 재검토시킨 사례

AI의 첫 제안이 틀렸다기보다는, **내가 더 파고들면서 결정이 뒤집힌** 경우가 반복됐다. 뒤집힐 때마다 ADR에 "재검토" 서브섹션을 추가해 **원안 → 문제 → 변경 이유**를 남겼다.


| 주제            | 원안                             | 재검토 후                                 | 기록                                                         |
| ------------- | ------------------------------ | ------------------------------------- | ---------------------------------------------------------- |
| 챗봇 서비스 경계     | Python은 오케스트레이션만, 상태는 Node 소유  | ai-server가 자기 DB·Redis 소유 (데이터 분리)    | ADR-010 §3                                                 |
| Tool 루프 구현    | RAG=LangChain, Tool 루프=raw SDK | 전부 LangChain (안전장치를 직접 구현할 필요 없음)     | ADR-010 §12                                                |
| 벡터 DB         | Chroma (임베디드)                  | Qdrant (K8s·클라우드 배포가 로드맵에 확정됨)        | ADR-010 §4, #91                                            |
| 강의계획서 파싱      | pdfplumber 파서 구현               | 정독 결과를 YAML로 커밋(A3) — 18청크 규모에 파서는 과함 | ADR-010 §6/§13, #95                                        |
| rate limit 위치 | Node 게이트웨이                     | ai-server (LLM 비용은 그 서비스 책임)          | ADR-010 §15, #108                                          |
| 시스템 스타일       | "MSA" 로 서술                     | **모듈러 모놀리스 + 서비스 1개 추출**로 정정          | [architecture/00](../architecture/00-아키텍처-스타일-검토.md), #121 |


마지막 항목이 특히 의미 있다. 초기 문서들이 컨테이너를 여러 개 띄운 구조를 "MSA"라고 불러 왔는데, 따로 검토를 시켜 보니 Node backend는 한 코드베이스·한 DB·한 배포 단위인 **모놀리스**였다. AI가 만든 문서의 용어를 그대로 믿지 않고 **정의 기준으로 다시 따져 보게 한 것**이 포트폴리오 서술을 과장 없이 만들었다.

### 3-3. 결과를 "소화할 시간"을 요구함

실험 01(Group A/B) 결과가 나오자마자 Claude가 다음 실험(Group C) 설계로 넘어가려 할 때 브레이크를 걸었다 — "이 실험하기 전에 아까 결과를 내가 충분히 소화하고 진행하자". AI가 요약한 숫자를 받는 것과 **내가 그 숫자가 왜 나왔는지 설명할 수 있는 것**은 다르기 때문이다. 이것도 피드백 메모리로 고정해, 이후 실험 결과 문서화 직후엔 다음 실험으로 바로 넘어가지 않게 했다.

### 3-4. `/code-review` 제안도 그대로 따르지 않음

`/code-review`가 "CLAUDE.md는 결정 1건당 ADR 1개를 요구한다"며 Group C 세부 파라미터(슬롯 5분·DLQ 5회 등) 4개를 ADR로 쪼개라고 지적했다. 나는 이것을 **아키텍처 결정이 아니라 구현 파라미터**로 판단해 portfolio 문서 1개로 유지했다. 규칙의 문구보다 규칙의 의도(되돌리기 어려운 구조 결정만 ADR)를 사람이 해석한 사례로, 이 경계도 메모리에 남겨 이후 세션에서 반복 제안이 나오지 않게 했다.

## 4. 측정을 AI에게 맡긴 방식 — "사람이 못 돌릴 양"을 돌리기

이 프로젝트에서 AI의 가장 큰 기여는 코드 작성보다 **반복 측정의 자동화**였다.

### 4-1. 동시성 실험 (Phase 2)

- k6 + Prometheus + Grafana 부하테스트 환경, 계정 시딩 스크립트, **실험 오케스트레이터 셸 스크립트**를 작성 (#13, #15, #29)
- 동시 사용자 7단계(50~12,000명) × 그룹 3개(A 무방비 / B 비관적 락 / C Redis 원자 연산) × 5회 반복 = **105회차** + 어뷰징 시나리오 + 카오스 테스트 3종(워커 kill, API kill, DB 다운)
- 모든 회차 raw JSON/CSV를 `doc/experiment/raw/`에 저장 → **오버셀 A +925건 / B·C 0건(105회차, sd 0.0)** 이라는 결론이 원본 데이터로 재현 가능 ([ADR-014](../ADR/ADR-014-실시간-수강신청-동시성-제어-방식-확정.md))
- 측정 노이즈가 나오면 원인까지 추적: nginx 업스트림 병목(트러블슈팅 07), **Docker Desktop 2 vCPU 캡**(트러블슈팅 08) → "로컬 노트북 측정의 한계"를 스스로 규정하고 AWS 재측정으로 이관



### 4-2. AI 챗봇 품질 평가 (LLM으로 LLM 앱을 평가)

- **eval 하네스**(`backend/ai-server/eval/`)를 먼저 만들고 기능을 나중에 개선 — 채점 로직은 순수함수 + 단위 테스트
- 질문 세트 70~74개(라우팅) + 56개(RAG)를 Claude가 **시드 데이터 실측값과 대조**하며 작성, 강의계획서 PDF 19개를 전수 정독해 정답 라벨 작성
- `CHAT_MODEL` 환경변수만 바꿔 **LLM 7종(Gemini 4 + GPT 3) × 70문항 × 5회** 비교 → 정확도가 모델 크기와 역상관한다는 반직관적 결과로 가장 싼 `gemini-3.1-flash-lite` 선정 ([ADR-012](../ADR/ADR-012-챗봇-LLM-모델-선정.md))
- `--rescore` 옵션으로 **저장된 raw를 채점 기준만 바꿔 재채점** — 재실행 비용 없이 라벨 오류를 바로잡음
- 결과: Tool 라우팅 93.1→100%, 비용 $3.26→$1.00/1000turn ([portfolio/03](03-ai-챗봇-rag-function-calling.md))



### 4-3. "실사용 → 버그 → 벤치마크 강화" 루프

벤치마크 점수가 100%여도 내가 실제 앱에서 챗봇과 대화하다 버그를 발견했다(#93 관심 등록 수 불일치, #117 교수 이메일 할루시네이션). 이때 AI에게 바로 고치게 하지 않고:

1. 내 **실제 발화를 오타까지 그대로** 재현 케이스로 벤치마크에 추가 (정정된 문장으로는 재현이 안 됐음)
2. Before 측정 (rag-54: 0/3)
3. 수정 → After (5/5) + 회귀 카테고리 확인

## 5. 세션이 끊겨도 이어지게 — 메모리와 문서

7주 작업이 여러 세션으로 나뉘었기 때문에, **맥락을 세 겹으로 저장**했다.


| 층                 | 무엇을                                 | 예시                                                     |
| ----------------- | ----------------------------------- | ------------------------------------------------------ |
| 레포 문서 (영구·공개)     | 결정·측정·문제해결의 공식 기록                   | ADR, 실험 결과, roadmap 체크리스트                              |
| Claude 메모리 (프로젝트) | "이어서 하자" 시 재개 지점, 진행 중 PR 스택, 환경 함정 | "Stage 2-1 이슈 #46 생성됨, 브랜치 착수 전", PR 머지 순서 #77→#79→#81 |
| Claude 메모리 (피드백)  | 내 작업 선호                             | 설명 먼저 / 결과 소화 먼저 / ADR vs portfolio 경계                 |


메모리에 기록해 **같은 함정을 두 번 밟지 않게** 한 것들:

- Git Bash에서 `docker compose run -v ...:/out` 시 경로가 뭉개짐 → `MSYS_NO_PATHCONV=1` 필수
- eval/rag 코드가 컨테이너 이미지에 구워져 있음 → 수정 후 `docker compose build` 또는 `cp` 필요
- 프론트 `index.css`가 빌드 타임 고정 Tailwind 산출물 → 새 유틸 클래스가 안 먹음(트러블슈팅 03), 새 UI는 인라인 style
- IDE(Cursor)가 `.git/config`·`.git/HEAD` 핸들을 잡아 `git checkout`이 실패 → 우회 방법
- 세션 시작 시 `git status`로 **미커밋 변경부터 확인** (결정은 메모리에 적고 파일 커밋을 안 한 채 세션이 끝난 적이 두 번 있었음)
- `doc/PRD.md`(원본 기획서)는 작업 PR에 섞지 않음

## 6. 병렬화와 외부 도구 연결

- **git worktree로 두 Stage 동시 진행**: 챗봇 Stage 2(SSE 스트리밍·UI)와 Stage 3-1(프롬프트 개선)을 별도 워크트리에서 병렬 작업. `COMPOSE_PROJECT_NAME`과 포트(+100) override로 docker-compose 스택 두 벌이 충돌하지 않게 하고, **어느 쪽이 어떤 파일을 소유하는지**(예: `tools.py`·`agent.py`는 3-1 소유, 2는 읽기만) 미리 나눠 머지 충돌을 피함.
- **fork 서브에이전트로 문서 작업 분리**: 구현 흐름을 멈추지 않고 Notion 보고서(실험 보고서, 아키텍처 설계 결정 페이지 등)를 서브에이전트가 병렬로 작성.
- **Notion MCP**: 레포 문서(엔지니어링 기록)와 별도로, 면접 설명용 "쉽게 풀어보면" 버전 보고서를 Notion에 작성 — 같은 결과를 **독자별로 두 벌**(레포=근거, Notion=설명).
- **GitHub CLI(**`gh`**)**: 이슈·PR 생성을 터미널 안에서 끝냄.

## 7. AI가 틀린 사례와 어떻게 잡았나

AI를 썼다고 결과가 자동으로 맞는 건 아니었다. 틀린 것들과, 그걸 잡은 장치:


| 사례                       | 무엇이 틀렸나                                                                      | 어떻게 잡았나 / 이후 조치                                                     |
| ------------------------ | ---------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 청크 수 산술 오류 (#100)        | "19파일 → 17청크"로 문서화했으나 실제 19−1=18 (17은 과목 코드 수)                               | 실제 Qdrant 적재 결과(18 point)와 대조 → ADR에 "정정" 서브섹션으로 남김                 |
| 관심 등록 수 소스 오인 (#93)      | 새 COUNT 쿼리로 값을 만들었는데, 앱의 정식 카운터는 이미 `Class.enrolled`였음 → UI "75명" vs 챗봇 "0명" | 내가 실사용 중 발견 → 교훈: "값을 새로 만들기 전에 도메인의 정식 소스부터 확인"                    |
| 라이브러리 API 전제 (#70)       | ADR이 LangChain `AgentExecutor`를 전제로 쓰였으나 1.x에서 제거됨. Gemini 모델명도 deprecated   | 실제 docker 실행에서 발견 → `create_agent` 전환 여부는 내가 결정, ADR §12 재검토로 기록    |
| 측정 중복 실행 (#78)           | 자동 poller와 수동 실행이 겹쳐 GPT 측정 컨테이너 6개가 동시에 뜸 (API 비용 약 $0.3~0.5 낭비)            | 실험 문서에 사고로 기록, 백그라운드 자동화와 수동 실행을 겹치지 않는 규칙을 메모리에 저장                 |
| 채점 아티팩트 (#104)           | "소프트웨어의이해" vs "소프트웨어의 이해" 공백 차이로 오답 처리                                       | 원본 응답을 직접 확인 → 공백 무시 비교 + `--rescore`로 재채점                          |
| 벤치마크 커버리지 부족 (#82, #113) | 라우팅 회귀 세트가 얕아 RAG 결합 후 "개념어 과목검색 오라우팅"(과목검색 100→66.7%)을 놓침                   | 시드 재작성 때 드러남 → 헤드라인 수치를 3단(Before/가드레일/교정)으로 분리해 **회귀가 지워지지 않게** 기록 |
| 스테이징 실수                  | `git add doc/`가 이번 작업과 무관한 `doc/PRD.md`까지 올림                                 | 커밋 전 확인해 제외, 메모리에 "PRD.md는 섞지 않음" 저장                                |


공통점: **AI가 만든 결과를 실제 시스템(DB·Qdrant·브라우저)의 값과 대조하는 단계**가 있었기에 잡혔다. 그래서 모든 작업에 "로컬 E2E 검증"과 "raw 원본 저장"을 루프에 넣었다.

## 8. 정리 — 면접에서 말할 수 있는 것

1. **AI 사용을 프로세스로 통제했다.** 규칙 파일로 문서 체계·Phase 순서·Before/After·시크릿 위생을 강제하고, Git 자동화는 "PR 생성까지 자동 / merge는 사람"으로 경계를 그었다.
2. **결정권은 나에게 두었다.** AI는 대안과 트레이드오프를 설명하고, 나는 산문 설명을 들은 뒤 결정했다. 첫 결론을 재검토해 뒤집은 결정 6건은 ADR에 원안과 변경 이유까지 남겼다.
3. **AI로 "사람이 손으로 못 돌릴 양의 측정"을 했다.** 동시성 105회차 + 카오스 3종, LLM 7종 × 70문항 × 5회. 원본 데이터는 전부 레포에 있다.
4. **AI의 실수를 잡는 장치를 설계했다.** 실제 시스템 값과 대조, raw 저장 후 재채점, 실사용 버그를 오타까지 재현해 벤치마크로 편입.
5. **1인 개발에서 팀 수준의 추적성을 확보했다.** 59 이슈 / 66 PR / 112 커밋이 전부 이슈 번호로 연결되고, "왜"는 14개 ADR에 있다.



## 9. 한계

- **리뷰 병목은 사람에게 남는다.** PR이 스택으로 쌓이면(#77→#79→#81, #120→#122→#124) 머지 순서 관리가 필요했고, 리뷰 대기 PR이 여러 개 동시에 열려 있던 시기가 있었다.
- **AI 측정은 비용이 든다.** LLM eval은 실제 API 비용이 발생하고, 중복 실행 같은 사고가 곧 비용이다.
- **로컬 환경 한계.** Windows + Docker Desktop(2 vCPU 캡) 위의 측정이라 처리량 상한은 AWS 재측정(인프라 트랙 ④)이 필요하다.
- **메모리는 스냅샷이다.** 메모리에 적힌 상태(예: "PR 리뷰 대기")는 시간이 지나면 낡는다. 그래서 세션 시작 시 `git status`·roadmap을 다시 읽는 것을 규칙으로 두었다.
