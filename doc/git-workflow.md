# Git 작업 규칙 (Issue → Branch → Commit → PR)

- 작성일: 2026-08-10
- 상태: 적용 중
- 목적: "이슈 번호 없는 커밋", "브랜치 이름 제각각", "PR 없이 main 직push" 같은 상태를 정리하고, **모든 변경 이력이 "왜"부터 추적 가능하도록** 고정한다.
- 적용 범위: 이 저장소(`Course Registration Platform`)의 모든 코드 변경. 문서 전용 변경(`doc/` 등)도 동일 규칙을 따르되, 이슈 생성은 생략 가능(아래 예외 참고).

## 왜 지금 정의하는가

지금까지는 기능 단위로 커밋은 쌓아왔지만(`feat: 비밀번호 재설정 기능 추가 (ADR-004)`처럼 부분적으로 이슈/ADR 번호를 참조), 브랜치 전략과 이슈 연동이 명문화되어 있지 않아 시점마다 규칙이 달랐다. `doc/portfolio-roadmap.md`의 **Phase 4 (CI/CD)** 로 GitHub Actions를 붙이려면, 그 전에 "무엇이 병합 트리거인가"("main으로의 PR merge")가 먼저 고정되어 있어야 한다. 이 문서는 Phase 4 착수 전에 필요한 선행 조건이다.

## 전체 흐름

```
[Issue #N 생성] → [브랜치 생성: 타입/#N-설명] → [커밋: 타입: 제목 (#N)] → [Push] → [PR 생성 (Closes #N)] → [Merge] → [이슈 자동 종료 + 브랜치 삭제]
```

---

## 1단계: Issue 생성

모든 작업(기능 추가, 버그 수정, 리팩토링, 인프라 변경 포함)은 **코드를 짜기 전에** Issue로 먼저 정의한다.

- GitHub 저장소 → `Issues` 탭 → `New issue`
- 제목: 무엇을 할지 한 줄로 (예: `Redis Lua 스크립트로 잔여 좌석 원자적 차감`)
- 본문: 최소한 "왜 필요한가"만 채운다. 상세 설계는 ADR/PR로 넘겨도 된다.
- `Submit new issue` → 번호(`#12` 등) 자동 발급. **이 번호가 브랜치/커밋/PR을 관통하는 유일한 식별자다.**

### 예외: 이슈 생성을 생략해도 되는 경우
- 오타/문서 서식 수정처럼 되돌릴 필요도, 추적할 맥락도 없는 변경(`docs:`, `style:` 중 극히 사소한 것)
- 단, 애매하면 이슈를 만든다. 이슈 생성 비용(1분) < 나중에 "이 커밋 왜 했더라" 추적 비용.

---

## 2단계: Branch 생성

`main`에서 분기하며, 이슈 번호를 브랜치 이름에 그대로 새긴다.

**네이밍 규칙**: `<타입>/#<이슈번호>-<작업내용-kebab-case>`

```bash
git checkout main
git pull origin main
git checkout -b feat/#12-redis-lua
```

| 예시 | 의미 |
|---|---|
| `feat/#12-redis-lua` | 12번 이슈: Redis Lua 스크립트 개발 |
| `fix/#15-duplicate-bug` | 15번 이슈: 중복 차감 버그 수정 |
| `refactor/#20-controller-분리` | 20번 이슈: 컨트롤러 계층 분리 |

타입은 3단계 커밋 타입과 동일한 어휘를 쓴다(아래 표 참고) — 브랜치 타입과 그 안의 커밋 타입이 어긋나면(`fix/` 브랜치인데 `feat:` 커밋만 있는 경우) 이슈 범위가 새고 있다는 신호다.

## 3단계: Commit (Conventional Commits)

### 형식

```
<타입>: <제목> (#이슈번호)

<본문> (선택 — '어떻게'가 아니라 '무엇을', '왜' 변경했는지)

<꼬리말> (선택 — 이슈 트래커 참조 등)
```

### 타입 목록

| 타입 | 의미 | 예시 |
|---|---|---|
| `feat` | 새 기능 추가 | `feat: 잔여 좌석 차감 Lua 스크립트 작성 (#12)` |
| `fix` | 버그 수정 | `fix: 동시 요청 시 좌석 중복 차감 수정 (#15)` |
| `docs` | 문서만 변경 | `docs: ADR-006 수강신청 동시성 설계 추가 (#12)` |
| `style` | 포맷팅, 세미콜론 등 로직 변화 없는 변경 | `style: 컨트롤러 들여쓰기 정리 (#12)` |
| `refactor` | 기능 변화 없이 구조만 개선 | `refactor: enrolled 카운트 로직 서비스 계층으로 분리 (#12)` |
| `test` | 테스트 코드 추가/수정 | `test: k6 동시 신청 부하테스트 시나리오 추가 (#12)` |
| `chore` | 빌드/패키지/설정 등 | `chore: ioredis 패키지 설치 (#12)` |

### 작성 규칙

1. **제목**: 명령조/명사형으로 마무리, 50자 이내, 마침표 없음.
   - `feat: Add Redis Lua script` (영문, 동사 원형 시작) 또는 `feat: Redis를 활용한 잔여 좌석 차감 Lua 스크립트 추가` (국문, 명사형 마무리) — 이 저장소는 지금까지 국문 커밋 메시지를 써왔으므로 국문 명사형을 기본으로 한다.
2. **본문**: 한 줄 72자 이내. "어떻게"는 diff를 보면 알 수 있으니 쓰지 않는다 — "왜 이 방식을 선택했는지", "무엇이 문제였는지"만 적는다.
3. **꼬리말**: `(#이슈번호)`를 제목 끝에 반드시 포함해, GitHub 이슈 타임라인에서 관련 커밋이 자동으로 모이게 한다.
4. 작업은 기능 단위로 잘게 쪼개 커밋한다. "일단 다 하고 한 번에 커밋"은 지양한다 — 리뷰/롤백 단위가 커밋이기 때문이다.

## 4단계: Push → PR → Merge

### Push
```bash
git push origin feat/#12-redis-lua
```

### PR 생성
GitHub에서 `main`으로 향하는 Pull Request를 열고, 아래 템플릿(`.github/pull_request_template.md`)을 채운다. PR을 열면 GitHub이 이 템플릿을 자동으로 불러온다.

- **📌 관련 이슈** 항목에 정확히 `Closes #12` 형식으로 적는다. 오타(`Close #12`, `closes#12` 등)가 나면 자동 종료가 동작하지 않으므로 GitHub의 자동완성 제안을 확인한다.

### Merge 및 자동화
- PR을 `main`에 Merge하면:
  1. `Closes #12` 키워드로 12번 이슈가 자동으로 `Closed` 처리된다.
  2. (Phase 4 CI/CD 도입 후) GitHub Actions가 트리거되어 이미지 빌드/푸시 → K8s 무중단 배포까지 이어진다. **이 문서를 먼저 고정하는 이유가 이 트리거 지점을 명확히 하기 위함이다.**
- Merge 완료 후 `feat/#12-redis-lua` 브랜치는 GitHub 화면에서 즉시 `Delete branch` 한다. 오래된 브랜치가 쌓이면 "이 브랜치 아직 살아있는 작업인가?"를 매번 재확인해야 하는 비용이 생긴다.

## 아직 정의하지 않은 것 (한계 인식)

- **브랜치 보호 규칙**(`main` 직push 금지, PR 승인 필수 등)은 GitHub 저장소 설정(Settings → Branches)에서 별도로 켜야 하며, 이 문서만으로는 강제되지 않는다. 필요 시 별도 요청으로 설정한다.
- 이슈 템플릿(`.github/ISSUE_TEMPLATE/`)은 아직 없다 — 지금은 자유 형식 이슈로 시작하고, 반복되는 패턴이 보이면 템플릿화한다.
