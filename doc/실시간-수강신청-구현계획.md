# 실시간 수강신청 기능 구현 계획

- 작성일: 2026-08-10
- 상태: 계획 수립 완료, 구현 착수 전
- 관련: [ADR-006](ADR/ADR-006-실시간-수강신청-설계.md)(설계 근거), [실험계획서 01](experiment/01-수강신청-동시성-naive-vs-개선-실험계획.md)(Stage 0/1 실험 설계), `doc/portfolio-roadmap.md`(로드맵 외 작업)

## 이 문서의 목적

ADR-006이 "무엇을 어떤 기술로 만들지"를 다뤘다면, 이 문서는 "어떤 순서로, 어떻게 나눠서 만들지"를 다룬다. ADR-006의 ~10개 결정은 서로 의존관계가 있어서 문서에 적힌 순서(0→4.2)대로 구현하면 안 된다 — 대기열/UI부터 만들면 정작 핵심인 "동시에 눌러도 정원이 안 터진다"를 오래 검증하지 못한 채 뒤에 숨겨두게 된다.

## 원칙: naive 버전은 "몰라서"가 아니라 "측정하기 위해" 만든다

Stage 0에서 동시성 제어가 전혀 없는 단순한 버전을 먼저 구현한다. 이것은 = **의도적으로 설계한 대조군(baseline)** 이다 — ADR-006에서 이미 최종 설계(Redis Lua + MQ + 멱등성)를 끝내둔 상태이고, naive 버전은 오직 "이 문제가 실제로 존재한다"는 것을 k6로 정량 증명하기 위해 만든다.

이 방식은 `doc/portfolio-roadmap.md`에 이미 정의된 프로젝트 전체 원칙과 일치한다: "모든 개선은 숫자 2개(Before/After)를 갖는다", "깨지는 걸 먼저 증명하는 게 핵심".

**Before/After 측정 기준**: 기존 "관심 과목" API가 아니라, 이번에 새로 만드는 수강신청 기능 자체를 기준으로 삼는다. 기존 관심과목 API에 대한 부하 테스트는 별도로 의미 있는 작업이나 이 기능의 Before/After 기준선은 아니다.

## Stage 0 — 대조군 2개(무방비/비관적 락) + 측정 도구 구축

**목표**: "동시성 제어가 없으면 데이터가 깨지고, RDBMS 락으로 확실히 막으면 서버가 죽는다"는 딜레마를 실측으로 증명한다. 상세 실험 설계는 [실험계획서 01](experiment/01-수강신청-동시성-naive-vs-개선-실험계획.md) 참고.

**만드는 것**

- 수강신청 API 2개 구현체 (동일한 API 계약, 내부 구현만 다름)
  - **Group A(무방비)**: 좌석을 `SELECT`로 읽어 JS 변수에 담고, 그 값으로 계산한 새 값을 블라인드 `UPDATE` (락/트랜잭션 없음 — `.decrement()`처럼 SQL 레벨에서 원자적인 헬퍼는 쓰지 않음, 실험계획서 3장 참고)
  - **Group B(비관적 락)**: 동일 로직을 `sequelize.transaction` + `SELECT ... FOR UPDATE`로 감쌈 (기존 `courseController.toggleInterest`와 동일한 패턴)
- 수강신청 내역 테이블(`registrations`, 기존 `course_interests`와 별개) + 좌석 카운터 필드
- **DB 커넥션 풀을** `max: 5`**로 명시적으로 설정** (현재 `config/database.js`에 미설정 상태 — Group B의 붕괴 시나리오 재현을 위해 명시 필요)
- k6 + Prometheus + Grafana 부하 테스트 환경 (ADR-006 4.2 결정 적용, Docker Compose로 자동 구성)

**측정 시나리오**

- 기본: 정원 100석에 동시 500명 (Group A 데모용)
- 스윕: 50/100/300/500/1,000/3,000/12,000명 동시성 수준별로 각 그룹의 붕괴 지점 확인
- 지표: 좌석 카운터 정합성(음수/초과 여부), TPS, p95 latency, 에러율(5xx/타임아웃), DB 커넥션 풀 대기

**완료 조건**: Group A는 좌석 음수/초과 재현, Group B는 목표 규모 근처에서 타임아웃·5xx 급증 재현 — 두 결과를 `doc/experiment/raw/`에 원본 데이터로 저장.

**관련 ADR-006 섹션**: 2.1(비관적 락 대안), 4.2(부하 테스트 도구)

## Stage 1 — Group C: Redis 원자적 연산 (대기열 없이)

**목표**: Stage 0에서 증명한 두 가지 실패(데이터 붕괴/서버 붕괴)를 동시에 해소하는지 동일 시나리오로 재증명한다.

**만드는 것**

- Redis 원자적 연산 + Lua Script: 좌석 차감(2.1)과 중복/시간표 겹침 검증(2.2)을 **하나의 스크립트로 통합**
- 좌석 카운터 시딩(Seeding) 배치: 수강신청 오픈 전 DB → Redis로 잔여 좌석을 채워 넣는 절차 (ADR-006에서 누락이 지적된 부분)
- 수강신청 취소(Drop) 흐름: `INCR`(좌석 반환) + `SREM`(신청자 명단 제거) — 지금 넣지 않으면 나중에 Lua Script를 다시 건드려야 해서 이 단계에서 함께 설계
- RabbitMQ 도입 (3.1) + 워커의 DB 멱등성 보장(복합 유니크 키 + `INSERT IGNORE`, 3.2)
- DLQ 격리 로직(격리 자체는 구현됨). 알림(모니터링)은 애초 이 단계에서 확보하려 했으나 실제로는 `console.error` 로그 한 줄에 그쳐 체크리스트 항목으로 누락됨 — Stage 3-4로 이관해 보상 로직과 함께 정식 설계 (2026-08-18 확인)

**측정 시나리오**: Stage 0(Group A/B)과 완전히 동일한 시나리오·스윕으로 재실행 (실험계획서 6장).

**완료 조건**: 전 구간에서 초과/음수 0건이면서, Group A 수준에 근접한 TPS·p95를 동시에 달성. Redis 성공/DB 미반영 불일치가 실제로 관찰되는지도 함께 기록(ADR-006에서 지적된 한계의 실증).

**관련 ADR-006 섹션**: 2.1, 2.2, 3.1, 3.2 + "다음 단계 및 보완 필요 사항" 2~5번

## Stage 2 — 트래픽 방어선(대기열) + 수강신청 탭 UI

**목표**: Stage 1로 정합성이 보장된 상태에서, 대규모 트래픽이 한꺼번에 유입되지 않도록 진입을 조절하고 사용자에게 대기 상황을 안내한다.

**만드는 것**

- Redis Sorted Set 기반 대기열 (1.1)
- TTL 기반 세션 유지/이탈 방어 (1.3) — Active 게이트와의 연동 메커니즘을 이 단계에서 구체적으로 확정 (배치 폴링 vs 이벤트 기반)
- Polling 기반 순번 안내 API (1.4)
- 신규 "수강신청" 탭: 실제 학교 수강신청 사이트와 동일한 UI/UX 목표
- **Active 인원 수 산출**: [실험계획서 01](experiment/01-수강신청-동시성-naive-vs-개선-실험계획.md) 11장 — Group C 스윕에서 얻은 "목표 지연시간 이내 유지되는 최대 지속 가능 TPS"를 Little's Law(ADR-006 1.5)로 역산해 결정한다. ADR-006 1.5의 "5,000명"은 계산 방식을 보여준 가설적 예시일 뿐, 실제 값은 이 실측 데이터로 대체한다.

**측정 시나리오**: 별도 실험계획서 `doc/experiment/02-대기열-방어-실험계획.md`(예정)로 설계. 1.2만 명 규모 가상 유저로 대기열 진입~신청 완료까지 End-to-End 시나리오. Stage 1의 서버 부하 감소 여부를 함께 확인.

**완료 조건**: 대기열을 거친 트래픽이 Stage 1의 처리 한계 내로 들어오는지, VU/Throughput/p95 목표(ADR-006 4.2의 KPI) 달성 여부.

**관련 ADR-006 섹션**: 1.1, 1.2(스코프는 Stage 3에서 최종 결정), 1.3, 1.4

## Stage 3 — 운영 고도화

**목표**: 정합성과 UX가 이미 검증된 상태에서 순수 인프라 안정성을 강화한다.

**만드는 것**

- Redis Sentinel 구성 (1.2) — 단, ADR-006에서 지적된 "1인 개발 오버엔지니어링" 논쟁을 먼저 결론짓고 착수 (실제 Sentinel까지 갈지, kind 클러스터에서는 단일 노드로 개념만 증명할지)
- CronHPA 기반 사전 확장 (4.1)
- Redis/RabbitMQ 커넥션 풀 사이징 (파드가 최대치로 늘어났을 때 기준)
- DLQ 완전한 보상(Compensation) 로직: Redis 성공/DB 실패 불일치 시 좌석 자동 반환
- 워커 Circuit Breaker: DB 연속 실패 감지 시 컨슘을 일시 중단하고 알람만 올림 — 지금은 DB가 완전히 죽어 있어도 워커가 계속 실패하는 INSERT를 재시도해 처리 용량을 낭비하고, 그 사이 유입되는 신규 정상 메시지까지 밀리는 문제가 있음 (2026-08-18 논의)
- DLX(Dead Letter Exchange)+TTL 기반 지연 재시도 전환 정식 검토: 카오스 테스트 1-10에서 republish 방식에 실제 백오프가 전혀 없음을 실측(장애 모드에 따라 5회 소진 65ms~20초)으로 확인 — ADR로 대안·트레이드오프를 정리한 뒤 구현 여부 결정 (이슈 #44)

**측정 시나리오**: 장애 주입 실험 — Redis 노드 kill 시 복구 시간, 파드 kill 시 무중단 여부.

**관련 ADR-006 섹션**: 1.2, 4.1 + "다음 단계 및 보완 필요 사항" 5, 7, 8번

### Stage 3 — 운영 고도화 (~3.5~6일)

**2026-08-19 재검토**: Stage 1(정합성)·Stage 2(대기열)로 기능은 이미 완결된 상태다. Stage 3는 그 위에 얹는 장애 대응력/효율 항목이라 전부 필수는 아니다. Stage 2 나머지(2-3~2-6) 완료 후에는 AI 에이전트(이슈 #51)로 먼저 넘어가고, 아래 [보류] 항목은 Phase 3 나머지(`portfolio-roadmap.md`의 resource/HPA)·AWS/K8s 실배포·CI/CD와 함께 마지막 인프라 트랙에서 처리한다. 번호(3-1~3-7)는 원래 구현계획 순서를 유지하고 우선순위만 태그로 구분한다.

- [ ] 3-1. Redis Sentinel 구성 범위 결정(실제 구성 vs kind 단일 노드로 개념 증명) 후 구현 — **[보류/오버스펙]** "1인 개발 오버엔지니어링" 우려가 이 항목 자체에 이미 있고, kind 단일 노드에서 구성해봐야 실증 가치가 낮다. ADR로 "실제 운영이라면 이렇게 구성했을 것"만 남기고 구현은 AWS 실배포 시점으로 미룬다 (1.5~2.5일)
- [ ] 3-2. CronHPA 기반 사전 확장 (3-1과 병렬 가능) — **[보류]** resource requests/limits+HPA(Phase 3 나머지)가 먼저 확정돼야 의미가 생긴다. 그때 통합해서 진행 (0.5~1일)
- [ ] 3-3. Redis/RabbitMQ 커넥션 풀 사이징 (3-1·3-2 이후) — **[보류]** 최대 파드 수(HPA)가 안 정해진 상태에서 하면 근거 없는 튜닝이 된다. Phase 3 나머지 이후로 (1~1.5일)
- [ ] 3-4. DLQ 완전 보상(Compensation) 로직 — 좌석 자동 반환 + DLQ 격리 알림/모니터링(원래 Stage 1 범위였으나 누락되어 이관, 2026-08-18) — **[필수]** Ghost Decrement로 실사용자가 영구 차단되는 유일한 피해 시나리오를 닫는 항목 (3-1~3-3과 병렬 가능, 포함 0.5~1.5일)
- [ ] 3-5. 워커 Circuit Breaker — DB 연속 실패 감지 시 컨슘 일시 중단 + 알람 (재시도 폭풍으로 워커 처리 용량이 낭비되는 것 방지, 3-4 DLQ 보상/알림과 함께 설계, 2026-08-18 논의) — **[권장, 3-4와 함께]** 이미 3-4와 같이 설계하기로 논의된 항목이라 묶어서 처리 시 추가 비용이 작다 (0.5~1일)
- [ ] 3-6. DLX(Dead Letter Exchange)+TTL 기반 지연 재시도 전환 정식 검토 — 1-10 실측(republish 무백오프, 장애 모드에 따라 5회 소진 65ms~20초) 근거로 ADR 작성(대안 비교: 현행 유지 / 단일 TTL 큐 계단식 / 지연 단계별 exchange 여러 개 / delayed-message 플러그인), 구현 여부는 이 검토 결과로 별도 이슈 분리 (3-4·3-5와 함께 설계, 이슈 #44) — **[권장]** 실측은 이미 끝나서 ADR만 쓰면 되는 저비용 항목 (0.5~1일)
- [ ] 3-7. 장애 주입 실험(Redis/DB/파드 kill, 복구 시간 측정) — 3-1~3-6 완료 후 — **[권장, 스코프 축소]** 실제로 구현한 항목(3-4, 필요 시 3-5)에 한해서만 진행 (0.5~1일)

**전체 합계**: 원래 견적 약 23~34.5 작업일, [필수]+[권장]만 먼저 처리하면 약 2~4.5일로 축소된다. [보류] 항목(3-1~3-3, 약 3~5일)은 Phase 3 나머지·AWS/K8s 실배포·CI/CD와 함께 마지막 인프라 트랙에서 재추정한다.
