# 트러블슈팅 08: validate3k 잔여 노이즈의 진짜 원인 — Docker Desktop이 2 vCPU로 인위적으로 좁혀져 있었다

- 날짜: 2026-08-20
- Phase: Stage 2-5, 이슈 #57(실험 02 Step 3, Valve Tuning) — [트러블슈팅 07](07-대기열-지속-폴링-부하에서-nginx-업스트림-병목.md)이 nginx 병목 2건을 고친 뒤에도 validate3k에 남아있던 잔여 노이즈(`http_req_failed` 1.44%, 음수 타이밍)를 이어서 추적한 기록
- 관련 코드: `C:\Users\82102\.wslconfig` (레포 밖, 로컬 머신 설정)
- 관련 문서: [트러블슈팅 07](07-대기열-지속-폴링-부하에서-nginx-업스트림-병목.md), [실험계획서 02](../experiment/02-대기열-방어-실험계획.md), [구현계획 2-3](../실시간-수강신청-구현계획.md) 항목(이전에도 같은 종류의 문제가 한 번 있었음 — 아래 "이전에도 있었다" 참고)
- 원본 데이터: `doc/experiment/raw/queue-step3-diag3k-active300.json`, `docker-stats-diag3k-2cpu.csv`(2 vCPU 상태 실측), `queue-step3-revalidate3k-active300.json`, `docker-stats-revalidate3k-8cpu.csv`(8 vCPU 상태 실측)

## 배경 — "고쳤는데 왜 아직도 노이즈가 남아있지?"

트러블슈팅 07에서 nginx keepalive 풀(64→2048)과 health check(`max_fails=10 fail_timeout=3s`)를 고친 뒤 validate3k(3,000 VU)를 돌렸더니, 12,000명 규모였던 `no live upstreams` 재앙은 사라졌지만 `http_req_failed` 1.44%, `registration_server_error` 48건, 그리고 `http_req_duration`의 최솟값이 **-434ms**로 찍히는 잔여 노이즈가 남아 있었다. validate2k(2,000 VU)는 완전히 클린(0% 실패)했는데 3,000 VU로 올라가는 순간에만 노이즈가 생긴다는 게 단서였다.

## 첫 가설: "k6 클라이언트 자체가 3,000 VU를 못 버티는 것 아닌가"

음수 `http_req_duration`은 서버가 느려서 나오는 값이 아니다 — k6가 요청 타임스탬프를 찍는 시점 자체가 뒤틀렸다는 신호라, 처음엔 "이 로컬 머신에서 k6가 3,000 VU를 감당 못 해 스케줄링이 밀리는 클라이언트 아티팩트"로 가설을 세웠다. 그런데 `docker-compose.loadtest.yml`을 보니 k6도 별도 머신이 아니라 **같은 Docker Desktop VM 안의 컨테이너 하나**로 돈다 — 즉 "클라이언트 vs 서버"가 아니라 "같은 리소스 풀 안에서 컨테이너끼리 경합"이라는 뜻이었다. 가설을 검증하려면 실제로 `docker stats`를 부하 시점과 겹쳐서 찍어봐야 했다.

## 진단 — docker stats로 실측하니 예상과 다른 그림이 나왔다

`docker stats --no-stream`을 2초 간격으로 백그라운드에서 수집하면서 validate3k를 재현했다(`diag3k` 라운드). 그 전에 `docker info`를 먼저 찍어보니 **`NCPU=2`, `MemTotal≈10.4GB`**였다 — 이 호스트는 실제로는 16코어(22스레드)/32GB인데, Docker Desktop이 인위적으로 2 vCPU로 캡핑돼 있었다(`C:\Users\82102\.wslconfig`에 `processors=2 memory=10GB`가 명시돼 있었다).

부하가 몰리는 순간(3,000명이 한꺼번에 `/api/queue/enter`를 때리는 시점)의 컨테이너별 CPU를 합산하니:

| 컨테이너 | CPU% (2 vCPU = 200% 예산 기준) |
|---|---|
| `backend_1` | 68.71% |
| `backend_2` | 63.15% |
| `nginx` | 3.53% |
| `k6` | 10.87% |
| `sugang-control-plane`/`worker`/`worker2` (이 실험과 무관한 K8s kind 클러스터) | 4.41% + 9.38% + 1.61% = 15.4% |
| `biostream_api`/`qdrant` 등 (이 실험과 무관한 별도 프로젝트) | 3.44% + 0.07% ≈ 3.5% |
| **합계** | **172.41% / 200%** |

세 가지가 한꺼번에 드러났다:

1. **`backend_1`+`backend_2`만으로 이미 132%** — 트러블슈팅 05가 짚었던 "Node 이벤트 루프가 순간 부하에 CPU 바운드"라는 진단과 일치하는 **진짜 서버 부하**였다. nginx나 k6의 문제가 아니었다.
2. **이 실험과 전혀 무관한 컨테이너들이 같이 CPU를 갉아먹고 있었다** — `sugang-*`(K8s kind 클러스터, Phase 3 준비용으로 띄워둔 것)와 `biostream_*`(완전히 다른 프로젝트)가 합쳐서 약 19%를 썼다. 2 vCPU라는 좁은 예산 안에서는 이 정도도 유의미했다.
3. 그 결과 nginx(3.5%)와 k6(11~48%)까지 포함해 **2 vCPU 예산이 사실상 꽉 찬 상태**로 부하테스트를 돌리고 있었다.

`diag3k` 결과: `http_req_failed` 1.00%(원래 1.44%보다는 낮지만 여전히 노이즈), `registration_server_error` 0건(3,000/3,000 신청 전부 성공 — 원래 validate3k의 48건과 다름), 실패는 전부 `status:200`(대기열 순번 조회 폴링) 타임아웃, 음수 타이밍도 -1ms대(원래 -434ms보다 훨씬 작음)로 줄었다. **실행마다 노이즈 크기가 달랐다는 것 자체가 코드 결함이 아니라 그때그때의 CPU 경합 정도에 좌우되는 리소스 문제라는 정황증거였다.**

### 이전에도 있었다 — 처음 겪는 유형의 문제가 아니었다

구현계획 문서(2-3 항목)를 다시 보니, 실험 02 Step 1(VU 150/200/250 측정)에서도 "1차는 무관한 컨테이너와의 CPU 경합으로 노이즈, 정리 후 재측정"이라는 기록이 이미 있었다. 즉 **"이 로컬 머신에 무관한 컨테이너가 같이 떠서 부하테스트를 오염시키는 것"은 이번이 처음이 아니라 재발한 패턴**이다 — 다만 그때는 컨테이너를 정리하는 임시 대응으로 넘어갔고, 이번처럼 "왜 애초에 이렇게 좁은 예산을 다투게 됐는가"(Docker Desktop 2 vCPU 캡)까지는 파고들지 않았었다.

## 원인

- **직접 원인**: `.wslconfig`가 `processors=2`, `memory=10GB`로 호스트 실제 스펙(16코어/32GB) 대비 극단적으로 좁게 잡혀 있었다.
- **증폭 요인**: 이 좁은 예산을 이 실험과 무관한 프로젝트(`sugang-*` K8s 클러스터, `biostream-*`)까지 상시로 나눠 쓰고 있었다.
- 두 요인이 겹쳐 3,000 VU 부하처럼 backend가 순간적으로 CPU를 많이 요구하는 시점에 전체 컨테이너 CPU 합계가 예산에 근접/충돌했고, 그 여파가 대기열 상태 조회(`GET /api/queue/status`) 응답 타임아웃과 타임스탬프 왜곡(음수 duration)으로 나타났다.

## 조치

`.wslconfig`를 아래와 같이 수정했다(레포 밖 시스템 설정이라 Git 추적 대상 아님):

```ini
[wsl2]
memory=16GB      # 10GB → 16GB (호스트 32GB의 절반, Windows 몫도 남김)
swap=4GB          # 유지
processors=8      # 2 → 8 (호스트 16코어의 절반, 나머지 8코어는 Windows/다른 앱 몫)
```

수정은 "예약"이 아니라 "상한선 상향"이다 — 평소(유휴 시)엔 여전히 CPU를 거의 안 쓰고, 부하가 몰릴 때만 이 여유를 실제로 쓴다. `wsl --shutdown` + Docker Desktop 재시작으로 적용했다(볼륨/컨테이너 데이터는 재부팅과 같은 개념이라 보존됨 — 삭제되지 않음).

## 결과 (Before/After)

| 조건 | `http_req_failed` | `checks` | `registration_server_error` | `http_req_duration` p95 | 최소값(음수 여부) | 부하 시점 CPU 합계 |
|---|---|---|---|---|---|---|
| 원래 validate3k (2 vCPU, 트러블슈팅 07 시점) | 1.44% | 98.55% | 48건 | 1.33s | -434.2ms | (미측정) |
| `diag3k` 재현 (2 vCPU, docker stats 병행 측정) | 1.00% | 98.96% | 0건 | 2.16s | -1.08ms | **172.41% / 200%** (86%) |
| `revalidate3k` (8 vCPU로 상향 후) | **0.00%** | **100.00%** | **0건** | **14.66ms** | -8.3µs(사실상 0) | **324% / 800%** (40%) |

8 vCPU로 올린 뒤에는 3,000 VU 부하에서 실패가 완전히 0건이 됐고, p95도 2.16초→14.66ms로 두 자릿수 배 개선됐다. CPU 합계도 부하 시점 최대 40%대로 내려가 여유가 충분함을 확인했다.

## 결론 — nginx 수정은 필요했지만, 남은 문제는 애플리케이션 코드가 아니었다

트러블슈팅 07의 nginx 수정(keepalive/health check)은 "6%만 완료되고 멈추는" 재앙적 실패를 없앤 **필요하고 유효한 수정**이었다. 하지만 그 이후 남은 1%대 잔여 노이즈는 nginx나 backend 코드를 더 건드려서 해결할 문제가 아니라, **로컬 테스트 환경(Docker Desktop) 자체가 호스트 실제 스펙 대비 너무 좁게 할당돼 있었고, 거기에 무관한 프로젝트 컨테이너들까지 상시로 얹혀 있었다는 환경 구성 문제**였다. 이 구분을 못 했다면 존재하지도 않는 코드 버그를 찾아 nginx/backend를 계속 건드리며 시간을 썼을 것이다.

## 교훈

- **"부하테스트 결과가 이상하다" → 애플리케이션 코드부터 의심하기 전에, 부하테스트 환경 자체의 리소스 할당을 먼저 확인한다.** `docker info`의 `NCPU`/`MemTotal`은 30초면 확인 가능한데, 이번엔 그걸 먼저 안 봐서 "k6 클라이언트 한계"라는 잘못된 첫 가설을 세울 뻔했다.
- **"k6가 딴 머신에서 돈다"는 암묵적 가정을 의심하라.** `docker-compose.loadtest.yml` 구조상 k6도 서버 컨테이너와 같은 리소스 풀을 나눠 쓴다 — 클라이언트/서버를 분리된 자원으로 착각하면 진단 방향이 완전히 틀어진다.
- **로컬 Docker 환경에 실험과 무관한 다른 프로젝트 컨테이너가 상시로 떠 있는 것 자체가 반복되는 리스크 요인이다.** 구현계획 2-3에서 한 번, 이번에 또 한 번 — 같은 유형의 노이즈가 재발했다. 좁은 리소스 예산에서는 무관한 컨테이너 하나하나가 실험 결과를 오염시킬 수 있다는 걸 팀(1인 개발이라도) 차원의 체크리스트로 남길 가치가 있다.
- **재현 편차 자체가 진단 정보다.** 같은 조건(3,000 VU, 동일 코드)을 두 번 돌렸는데 노이즈 크기가 달랐다(1.44% vs 1.00%, -434ms vs -1ms) — 결정론적 코드 버그였다면 이런 편차가 나오지 않는다. 이 편차 패턴 자체가 "리소스 경합" 가설 쪽으로 무게를 실어준 단서였다.
