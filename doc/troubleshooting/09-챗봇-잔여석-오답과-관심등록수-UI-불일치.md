# 트러블슈팅 09: 챗봇이 "잔여석"을 관심과목 하트 수로 답하던 문제 + 정정 과정에서 만든 두 번째 버그

- 날짜: 2026-08-27 ~ 2026-08-28
- 단계: AI 챗봇 Stage 3-1b (이슈 #86) → 정정 (이슈 #93). 실사용 테스트에서 발견
- 관련 코드: `backend/src/controllers/courseController.js`, `backend/src/controllers/demandController.js`, `backend/ai-server/chat/tools.py`, `backend/ai-server/chat/agent.py`
- 관련 문서: [트러블슈팅 06](06-취소-후-재신청-DUPLICATE-오탐과-여석-미반영.md) §2~3(이 문제의 전신), [ADR-013](../ADR/ADR-013-좌석-데이터-소스-단일화.md), [실험 03 §8](../experiment/03-프롬프트개선-before-after.md)
- 관련 PR: #90(#86), #94(#93)

이 문서는 두 개의 버그를 순서대로 다룬다. **A**는 원래 버그(챗봇 잔여석 오답), **B**는 A를 고치는 과정에서 내가 새로 만든 버그(챗봇 관심 등록 수가 화면과 다름)다. B가 이 문서의 핵심 교훈이다.

---

## A. 챗봇이 "잔여석"을 관심과목 하트 수로 계산하고 있었다 (이슈 #86)

### A-1. 증상 (사용자 리포트)

실제 로그인 계정으로 AI 챗봇을 쓰며:

> "'창병모 교수님 이번학기 수업 해?' 라는 질문에 이번학기 수업하지 않으신다고 뜨고, '데이터베이스 관련 수업 알려줘' 하니깐 2개밖에 없어."

(이건 #82에서 해결) 이어서 좌석 관련:

> "독일어Ⅰ 자리 있어?" → 챗봇 "자리가 없습니다 (잔여석 0)"

그런데 실제로는 독일어Ⅰ 40석이 전부 비어 있었다.

### A-2. 진단 — "수강 인원"을 뜻하는 값이 3개, 서로 다른 저장소

[트러블슈팅 06 §2](06-취소-후-재신청-DUPLICATE-오탐과-여석-미반영.md)에서 이미 한 번 짚었던 지점이다: `getCourses`가 `Class.enrolled`를 그대로 반환하고, Group C(Redis) 등록/취소는 이 값을 안 건드린다. 챗봇 `chat/tools.py`가 그 `enrolled`로 `capacity - enrolled`를 계산해 "잔여석"이라고 답하고 있었다.

| 개념 | 저장소 | 갱신 주체 |
|---|---|---|
| 실시간 수강신청 잔여석 | Redis `class:{id}:seats` | Group C 원자 연산(등록/취소) |
| 관심 등록(하트) 수 | MySQL `Class.enrolled` (+ `course_interests` 행) | `toggleInterest` |
| (실험용) Group A/B 잔여 카운터 | MySQL `Class.remainingSeats` | naive/pessimistic 경로만 |

`Class.enrolled`는 추가로 `seedData.js`가 데모용 가짜 값(44, 50, 88, …)으로 하드코딩하고, `toggleInterest`가 하트마다 `+1/−1` 한다. → 챗봇이 이걸로 계산한 "잔여석"은 실제 Redis 좌석과 무관했다.

**오차 규모**: 85개 실과목 전부 `capacity - enrolled` ≠ 실제 Redis 잔여석, 평균 절대 오차 48.6석, 84개가 "실제보다 빡빡하게"(마감 오답 위험).

### A-3. 수정 (ADR-013, PR #90)

- `GET /api/courses`·`/api/courses/:code` 응답의 `remainingSeats`를 **Redis `class:{id}:seats`(실시간 잔여석)** 로 통일. MySQL 컬럼값(stale)은 응답에서 제거. Redis 장애 시 `null` + 200
- `chat/tools.py` `_summarize`: `enrolled` 제거 → `remaining_seats` / `registered_count`(= 정원 − 잔여석) / `interest_count` 3개로 분리
- 이때 `interest_count`의 소스를 **`course_interests` 테이블 `GROUP BY COUNT`** 로 새로 잡았다 ← **이게 B의 원인**

**Before/After** (gemini-3.1-flash-lite, 74문항 × 5회): 답변 포함 검사 73.7% → 100%, 답변 제외 80% → 100%.

## B. 정정 과정에서 만든 버그 — 챗봇 관심 등록 수가 화면과 다름 (이슈 #93)

### B-1. 증상 (사용자 리포트)

PR #90 머지 후 다시 브라우저 테스트:

> "안태훈 교수님의 알고리즘 수업에 관심 등록(좋아요)을 한 인원은 다음과 같습니다. 알고리즘 (21000549-1): 0명 / 21000549-2: 0명 이렇게 떠. 확인해보면 관심목록에서 해당 과목들의 좋아요는 75,65인데. 이제 잔여석은 정확하게 표시돼."

- 챗봇: 관심 등록 수 **0명**
- 수업 목록 화면: **75, 65명**

잔여석(A) 문제는 해결됐는데, 관심 등록 수가 화면과 어긋났다.

### B-2. 진단 — `Class.enrolled`는 이미 관심 등록 수 카운터였다

`interest_count`(챗봇) = `course_interests` `COUNT` = 0. 수업 목록 "n / M명"의 n = `Class.enrolled` = 75.

`Class.enrolled`가 왜 75인지 추적하다 `demandController.aggregateDemand`를 발견:

```js
// backend/src/controllers/demandController.js
const interestCount = await CourseInterest.count({ where: { class_id: klass.id } });
const demandStatus = computeStatus(interestCount, klass.capacity);
await klass.update({ enrolled: interestCount, demandStatus });  // ← enrolled를 실측으로 덮어씀
```

즉 **`Class.enrolled`는 이 앱의 정식 관심 등록 수 카운터**였다:

- `toggleInterest`가 하트마다 `+1/−1`로 즉시 유지
- `aggregateDemand`(관심과목 체커 CronJob, 매분)가 `CourseInterest.count()` 실측으로 재조정
- `demandStatus`(NORMAL/NEAR/FULL)도 이 값으로 계산
- **수업 목록 UI가 표시하는 "n / M명"의 n이 바로 이 값**

로컬에는 이 CronJob이 없어서(`docker-compose`에 checker 서비스 없음, `CRON_SECRET` 미설정) `enrolled`가 시드값(75)에 멈춰 있었고, 챗봇의 `COUNT`(0)와 크게 벌어졌다. K8s에서는 매분 재조정돼 둘이 거의 같다.

### B-3. 근본 원인

**A를 고칠 때 "`enrolled`는 시드가 섞인 하이브리드"라고만 보고, 그 도메인에 이미 정식 관심 등록 수 소스가 뭔지(=`enrolled` 자신) 확인하지 않았다.** `demandController`가 `enrolled = interest count`로 쓰고 있다는 걸 놓치고, 같은 개념을 세는 두 번째 소스(`course_interests` COUNT)를 새로 만들었다. 두 소스는 K8s에서는 일치하지만 로컬에서 갈라졌고, 무엇보다 **챗봇이 UI와 다른 숫자를 말하게** 됐다.

### B-4. 수정 (PR #94)

챗봇이 UI와 같은 소스(`enrolled`)를 쓰게 되돌린다:

```diff
# backend/ai-server/chat/tools.py  _summarize
-       "interest_count": course.get("interestCount"),
+       "interest_count": course.get("enrolled"),
```

- `courseController.js`: #86에서 넣은 `course_interests` `GROUP BY COUNT`(응답 `interestCount` 필드) 제거. `seatSnapshot`은 Redis 좌석만 담당
- **`remaining_seats` / `registered_count`(Redis 실시간 좌석 기준)는 A 그대로 유지** — 그게 원래 버그의 핵심이었다

**검증** (라이브): "알고리즘 관심 등록 수?" → 챗봇 "75명 / 65명" = 수업 목록 UI와 일치. "잔여석 / 신청자 수?" → "89석 / 1명" (Redis, 회귀 없음).

eval 재측정은 안 했다 — `interest_count` **값**을 채점하는 시나리오가 없다(`seats-12`는 `answer_must_not_include`로 "신청자 수와 혼동" 여부만 확인).

## 교훈

1. **값을 여러 소스로 "분리"하기 전에, 그 도메인의 정식 소스가 이미 무엇인지 확인한다.** "이 필드는 지저분해 보인다"만으로 새 소스를 만들면, 같은 개념을 세는 두 곳이 생기고 언젠가 갈라진다. `demandController`를 먼저 읽었으면 `enrolled`가 관심 등록 수의 정식 카운터라는 걸 알았을 것이다.

2. **분리 자체는 옳았다.** `enrolled` 하나로 "잔여석"까지 답하던 게 A의 버그였고, `remaining_seats`(Redis) / `registered_count` / `interest_count`로 쪼갠 건 유지된다. 틀린 건 `interest_count`의 소스 선택 하나뿐이다.

3. **"화면과 챗봇이 다른 숫자를 말한다"는 그 자체로 버그다.** 어느 쪽이 "더 정확한지"와 무관하게, 사용자는 두 UI가 같은 걸 물었는데 다른 답을 하면 신뢰를 잃는다. 정답은 "둘을 같은 소스에 붙이는 것".

4. [트러블슈팅 06](06-취소-후-재신청-DUPLICATE-오탐과-여석-미반영.md)에서 "여석 미반영"으로 한 번 만났던 `Class.enrolled` vs Redis 문제가, 챗봇이라는 새 소비자가 생기면서 다시 나타났다. 데이터 소유권 경계가 애매한 필드는 소비자가 늘 때마다 재발한다 — ADR-013이 `/api/courses` 응답 계약을 "실시간 좌석 = Redis" 하나로 못박은 이유.

## 남은 일 (별도 이슈, 보류)

- 수업 목록 탭에 "실시간 신청자 수"(`capacity - remainingSeats`)를 관심 등록 수와 나란히 표시. 사용자가 이번엔 "UI엔 안 넣고 챗봇만 고쳐라"고 해서 챗봇(`registered_count`)만 반영된 상태.
- 로컬 `docker-compose`에 관심과목 체커(CronJob 대응)가 없어 `enrolled`가 시드값에 고정됨 → 재시딩(Stage 1) 때 `enrolled` 시드값 정리 + 필요 시 로컬 aggregate 수단.
