- 상태: **1~3순위 전부 적용 및 검증 완료** (2026-08-19). 아래 §적용 결과 참고.
- 관련: `nginx/default.conf`, `docker-compose.yml`(backend), `backend/src/server.js`, [실험 01 Group C 결과](../experiment/01-결과-groupC.md), [Notion 실험 보고서 02](https://app.notion.com/p/3c0b8654c5d18118b06cc28035311069)

## 증상

Group C 정합성 스윕(50~12,000명, 35회차)은 오버셀 0건·DLQ 0건으로 완벽했지만, 곧이어 돌린 어뷰징 시나리오(macro 연타·overlap 겹침, 3,000/12,000명 × 3회)에서 `http_req_failed`가 급증했다. 에러 메시지는 전부 동일한 패턴이었다.

```
error="Post \"http://nginx/api/registrations/redis\": EOF"
```

VUS=200 규모의 보정 단계에서 이미 `http_req_failed=95%`가 관측됐고, 3,000/12,000 규모의 정식 실행에서는 macro 시나리오의 `unexpected`(EOF 등 비정상 응답) 비율이 88~98%까지 치솟았다. overlap 시나리오는 더 심해서, VUS=12,000 rep2는 12,000명 중 **단 1명도 첫 신청에 성공하지 못했다.**

이건 Redis Lua Script의 원자성 문제가 아니다 — success는 macro 6/6 회차 전부 정확히 정원(50)에 고정됐고, 마지막 회차의 최종 DB를 직접 교차 검증한 결과 두 과목 모두에 등록된 유저는 0명이었다(상세: [실험 01 Group C 결과](../experiment/01-결과-groupC.md) §3-3). 즉 **애플리케이션 로직은 멀쩡한데, 그 로직에 도달하기도 전에 요청이 드랍되고 있다.**

## 원인 분석 (코드 근거)

"로컬 환경 한계"라고 뭉뚱그리기 전에, 실제로 뭐가 빠져 있는지 코드에서 확인했다.

### 1. nginx가 커넥션을 받는 능력 자체가 튜닝 안 됨

`nginx/default.conf`는 `server {}` 블록만 갖고 있고 `events {}`(→ `worker_connections`)나 `worker_processes`를 전혀 건드리지 않는다.

```nginx
server {
    listen 80;
    location /api/ {
        proxy_pass http://backend:8000/api/;
    }
    ...
}
```

`nginx:alpine` 베이스 이미지의 기본값(보통 `worker_processes 1`, `worker_connections 1024`)이 그대로 적용된다. macro 시나리오가 VUS당 5개 요청을 `http.batch`로 동시발사하면 순간에 최대 60,000개 커넥션이 몰리는데, nginx가 받을 수 있는 슬롯은 기본값 기준 1,024개뿐이다.

### 2. nginx→backend 사이에 커넥션 재사용(keepalive)이 없음

`proxy_pass http://backend:8000/api/;` 한 줄뿐이고, upstream 블록도 `keepalive` 설정도 없다. 즉 nginx는 **요청마다 backend와 TCP 커넥션을 새로 맺는다.** 평상시엔 티가 안 나지만, 순간 부하가 몰리면 이 반복적인 TCP 핸드셰이크 자체가 무시 못 할 비용이 된다.

### 3. backend가 단일 인스턴스, 단일 프로세스

`docker-compose.yml`의 `backend` 서비스는 컨테이너 1개뿐이다. `backend/src/server.js:16`도 `app.listen(PORT, callback)`으로 클러스터링 없이 단일 Node 프로세스로 뜬다 — 코어가 몇 개든 이벤트 루프는 하나다. 반면 RabbitMQ 워커는 카오스 테스트 준비 과정에서 이미 `worker_1`/`worker_2` 2개로 이중화되어 있다(`docker-compose.yml`). 실제 K8s 배포(로드맵 As-Is 다이어그램)도 backend 2 replica인데, **로컬 부하테스트 스택만 여기서 벗어나 있다.**

### 4. 테스트 시나리오 자체가 필요 이상으로 부하를 만듦

overlap 시나리오는 "이미 대상 과목을 신청해둔 유저"라는 전제를 **매번 라이브 HTTP 요청으로** 만든다. 하지만 실제로 검증하려는 건 두 번째 요청의 SINTER 겹침 체크지, 첫 번째 요청의 정원 경합이 아니다 — 정합성 스윕에서 이미 검증한 것과 같은 종류의 부하를 어뷰징 시나리오 안에서 중복으로 만들어내고 있다. macro도 `MACRO_REQUESTS=5`를 `http.batch`로 완전 동시 발사하는데, 실제 매크로 클릭(더블클릭, 폼 중복 전송)이 마이크로초 단위로 정확히 동시에 일어나지는 않는다 — 테스트가 현실보다 더 가혹한 조건을 스스로 만들고 있을 가능성이 있다.

## 개선안 (우선순위별)

| 순위 | 조치 | 근거 | 비고 |
|---|---|---|---|
| 1 | nginx `worker_connections` 상향 + `worker_processes auto` + upstream `keepalive` 커넥션 풀 추가 | 원인 1·2 | 테스트용 임시방편이 아니라 리버스 프록시 운영 표준 설정 — 실제 배포 품질도 같이 개선됨. K8s Ingress에도 동일 설정 누락 여부 점검 필요(Phase 3 나머지 항목과 연결) |
| 2 | docker-compose에서 backend를 2 replica로 (RabbitMQ 워커 이중화 패턴 재사용) + nginx 로드밸런싱 | 원인 3 | 실제 K8s 배포 구조(backend 2 replica)와 로컬 테스트 환경을 일치시킴. Node `cluster` 모듈은 도입하지 않음 — 이미 "레플리카로 스케일"하는 아키텍처를 쓰기로 했으므로 프로세스 레벨 클러스터링까지 이중으로 넣는 건 과잉설계로 판단 |
| 3 | overlap: "이미 등록된 상태"를 라이브 HTTP 대신 Redis에 직접 시딩(`SADD`)해서 첫 호출 자체를 제거. macro: `MACRO_REQUESTS` 축소 또는 완전 동시 대신 짧은 간격(20~50ms)을 둔 순차 요청으로 변경 | 원인 4 | 검증하려는 지점(SINTER 체크, 원자성)에만 부하를 집중시켜 순간 커넥션 요구량 자체를 줄임 |
| 4 (조건부) | 위를 다 적용해도 12,000 규모에서 여전히 무너지면, "Windows Docker Desktop(WSL2/Hyper-V 가상 네트워크)의 근본 한계"로 결론짓고 문서화 | — | 실제 클라우드 환경이라면 Ingress+레플리카+HPA가 흡수했을 것이라는 한계 인식을 포트폴리오 문서에 남김 |

## 검증 계획

한 번에 다 바꾸지 않고, 이 프로젝트가 지금까지 지켜온 "하나씩 바꾸고 측정한다" 원칙을 그대로 적용한다.

1. 1순위(nginx 튜닝)만 적용 → `VUS=200`으로 재보정 → EOF 비율이 크게 줄어드는지 확인
2. 안 줄어들면 2순위(backend 2 replica) 추가 → 같은 `VUS=200`으로 재확인
3. 그래도 안 되면 3순위(시나리오 자체의 부하 총량 축소)
4. 세 조치를 다 적용한 뒤 3,000/12,000 규모로 어뷰징 시나리오 재실행 → [실험 01 Group C 결과](../experiment/01-결과-groupC.md) §3의 수치를 Before로 삼아 After와 비교

## 적용 결과

세 우선순위 모두 적용했다(PR #33, #35, 그리고 이 문서와 같은 이슈 #29 브랜치에서 진행한 3순위). 단계마다 `VUS=200`으로 먼저 재보정한 뒤 실제 실험 규모(3,000/12,000)로 확인하는 순서를 지켰다.

### 1순위+2순위만 적용 (시나리오 설계는 그대로)

| 시나리오 | VUS | unexpected(실패) | 비고 |
|---|---|---|---|
| macro | 3,000 | **0 / 15,000 (0%)** | 완벽 |
| overlap | 3,000 | **0 / 3,000 (0%)**, first_success 3,000/3,000 | 완벽 |
| macro | 12,000 | 38,296 / 60,000 (63.8%) | 여전히 노이즈 큼 |
| overlap | 12,000 | 1,170 / 12,000 (9.75%), first_success 11,432/12,000(95.3%) | Before보다 극적으로 개선됐으나 미완 |

**3,000명 규모는 인프라 개선만으로 완전히 해결됐다.** 12,000명(이 프로젝트의 목표 트래픽 규모)에서만 유의미한 노이즈가 남아, 3순위를 진행하기로 결정했다.

### 1+2+3순위 전부 적용 (VUS=12,000)

| 시나리오 | 조치 | unexpected(실패) |
|---|---|---|
| macro | `MACRO_REQUESTS` 5→2 | 4,037 / 24,000 (**16.8%**, 63.8%→16.8%) |
| overlap | 라이브 첫 신청 → Redis 직접 시딩 | **0 / 12,000 (0%)**, rejected 12,000/12,000 — 완벽 |

overlap은 3순위로 완전히 해결됐다. macro는 큰 폭으로 개선됐지만(63.8%→16.8%) 완전히 0은 안 됐다 — `MACRO_REQUESTS=2`(순간 부하 24,000건)도 여전히 3,000명 스윕(15,000건)보다 크고, 이 프로젝트의 Docker Desktop 환경이 실제로 CPU 2코어뿐이라는 물리적 한계(§원인 분석에서 이미 실측)에 가까워진 결과로 해석한다. `MACRO_REQUESTS`를 더 낮추면(예: 1) 중복 클릭 자체를 검증할 수 없어 시나리오의 의미가 사라지므로, 이 이상은 시나리오 설계로 줄이지 않고 로컬 환경의 한계로 받아들인다.

### 결론

- 1순위(nginx 커넥션 튜닝) + 2순위(backend 2 replica): 정합성 스윕과 동일한 종류의 부하(3,000명 규모까지)는 완전히 해소
- 3순위(시나리오 설계 수정): overlap은 완전 해소, macro는 63.8%→16.8%로 대폭 개선되나 완전 해소는 못 함 — 남은 건 로컬 인프라(CPU 2코어)의 물리적 한계로 판단, 추가 조치는 비용 대비 효과가 낮다고 결론
