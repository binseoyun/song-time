# 트러블슈팅 04: 부하테스트 환경(k6+Prometheus+Grafana) 구축 중 발견한 문제 2건

- 날짜: 2026-08-11
- Phase: Phase 2, 이슈 #13 (Stage 0-5~0-7)
- 관련: `docker-compose.loadtest.yml`, `backend/scripts/seedLoadTestAccounts.js`, `loadtest/scripts/registration.js`

`docker-compose.loadtest.yml` + 계정 시딩 스크립트 + k6 스크립트를 새로 작성한 뒤, 실제로 컨테이너를 띄우고 스모크 테스트(20 VU, Group A 대상)를 돌려 파이프라인 전체(계정 시딩 → k6 → nginx → backend → DB, k6 → Prometheus remote-write → Grafana)가 실제로 동작하는지 검증했다. 이 과정에서 두 가지 문제를 만났다.

## 1. 스키마 드리프트: `remainingSeats` 컬럼이 없는 상태로 backend가 crash-loop

### 증상

```
backend-1  | ❌ 데이터 삽입 오류: Unknown column 'remaining_seats' in 'field list'
```

`db_data`는 이름 붙은 Docker 볼륨이라 지난 세션들에서 계속 재사용되고 있었는데, 그 볼륨은 `Class` 모델에 `remainingSeats`(ADR-006, 실시간 수강신청용 잔여좌석 카운터)가 추가되기 **이전** 스키마로 이미 초기화된 상태였다.

### 원인

`src/seedData.js`가 기동 시마다 돌리는 `sequelize.sync({ force: false })`는 **테이블이 없으면 생성**하지만, **이미 존재하는 테이블에 새 컬럼을 추가하는 `ALTER TABLE`은 하지 않는다.** 이 한계는 이미 `Class.js` 모델 주석(remainingSeats 필드)에서 예견돼 있었던 내용인데, 실제로 오래된 로컬 볼륨에서 그대로 재현됐다.

### 해결

로컬 더미 시드 데이터일 뿐 보존할 가치가 있는 데이터가 아니므로, 볼륨을 지우고 처음부터 다시 만들었다.

```bash
docker compose -f docker-compose.yml -f docker-compose.loadtest.yml down
docker volume rm courseregistrationplatform_db_data
docker compose -f docker-compose.yml -f docker-compose.loadtest.yml up -d
```

재기동 후 85개 과목이 정상 시딩되고 `remainingSeats` 컬럼도 정상 생성됨을 확인했다.

### 한계 / 앞으로의 과제

이건 임시방편이다. `sync()` 기반 스키마 관리 자체가 로드맵 P6(사전 발견 문제)로 이미 등록돼 있고, Phase 3 "나머지" 항목의 "DB 마이그레이션 도구 도입"에서 근본적으로 다룰 예정이다. 실 운영 환경이라면 볼륨을 지우는 방식은 애초에 불가능하므로(데이터 유실), umzug/sequelize-cli 같은 마이그레이션 도구로 `ALTER TABLE`을 명시적 이력으로 관리해야 한다.

## 2. Git Bash(MSYS) 경로 치환이 `docker ... -e` 환경변수 값을 깨뜨림

### 증상

k6 스모크 테스트가 100% 실패했고, 에러 메시지가 이상했다.

```
error="Post \"http://nginxC:/Program%20Files/Git/api/registrations/naive\": lookup nginxC on 127.0.0.11:53: no such host"
```

`TARGET_BASE_URL`(기본값 `http://nginx`)과 `TARGET_PATH=/api/registrations/naive`를 합친 값이 `http://nginxC:/Program Files/Git/api/registrations/naive`로 깨져 있었다.

### 원인

Windows의 Git Bash(MSYS2)는 `/`로 시작하는 인자를 자동으로 Windows 경로로 오인해서 변환하는 알려진 동작이 있다. `docker compose run --rm -e TARGET_PATH=/api/registrations/naive k6` 명령의 `/api/registrations/naive`가 "유닉스 스타일 절대경로"로 오인되어 `C:/Program Files/Git/api/registrations/naive`로 치환된 뒤 컨테이너 환경변수로 전달됐다. 애플리케이션 코드나 k6 스크립트 문제가 아니라 **로컬 셸 레이어의 문제**였다.

### 해결

`MSYS_NO_PATHCONV=1`을 명령 앞에 붙여 이 자동 변환을 끈다.

```bash
MSYS_NO_PATHCONV=1 docker compose -f docker-compose.yml -f docker-compose.loadtest.yml run --rm \
  -e TARGET_PATH=/api/registrations/naive -e VUS=20 k6
```

이후 정상적으로 `http://nginx/api/registrations/naive`로 요청이 나갔다.

### 참고

PowerShell이나 Linux/macOS 셸에서는 이 문제가 재현되지 않는다 — Windows에서 Git Bash로 이 프로젝트의 부하테스트 명령을 실행하는 경우에만 해당하는 로컬 환경 특이사항이다.

## 3. (부수 관찰) Group A 스모크 테스트에서 이미 관측된 정합성 붕괴 조짐

위 두 문제를 해결한 뒤 20 VU로 Group A(`/api/registrations/naive`)를 스모크 테스트한 결과:

| 지표 | 값 |
|---|---|
| k6 응답 기준 성공(201) 건수 | 20/20 |
| DB `registrations` 실제 행 수 | 20건 |
| `Class.remainingSeats` 감소량 | 50 → 49 (**1만 감소**, 기대값은 20 감소) |

20건 모두 API 응답으로는 성공(201)했고 `registrations` 테이블에도 20건이 정확히 쌓였지만, 좌석 카운터는 딱 1만 줄었다 — 여러 요청이 동시에 같은 `remainingSeats` 값을 읽어 각자 `-1`한 값을 블라인드 `UPDATE`하면서 서로의 갱신을 덮어쓴 lost-update가 20 VU 규모에서도 이미 재현됐다.

**이건 정식 실험 결과가 아니다.** 실험계획서 01의 통제변수(반복 5회, 웜업 제외, 동일 조건 재현성 확보 등)를 따르지 않은 단발성 스모크 테스트일 뿐이며, 목적은 어디까지나 "파이프라인이 실제로 요청을 보내고 응답을 받아 지표를 남기는지" 확인하는 것이었다. 다만 결과적으로 ADR-006/실험계획서 01의 가설 H1("무방비 방식은 정합성이 깨진다")이 아주 작은 규모에서도 이미 관측 가능하다는 것을 확인했다는 점에서, 다음 이슈(실험 01 정식 실행, Stage 0-8)의 재현 가능성에 대한 사전 신호로 기록해둔다.

## 4. 결론

두 문제 모두 애플리케이션 코드가 아니라 **로컬 실행 환경(Docker 볼륨 영속성, Windows 셸의 경로 치환)** 에서 비롯됐다. `doc/troubleshooting/01`에서 얻은 교훈("증상과 원인이 다른 레이어에 있을 수 있다")이 이번에도 그대로 적용됐다 — 첫 번째는 에러 메시지(`Unknown column`)가 원인 레이어(스키마 vs 데이터)를 정확히 가리켰지만, 두 번째는 에러 메시지(`no such host`)만 보면 DNS/네트워크 문제로 오해하기 쉬웠고 실제로는 셸의 인자 전처리 단계에서 이미 값이 깨져 있었다.
