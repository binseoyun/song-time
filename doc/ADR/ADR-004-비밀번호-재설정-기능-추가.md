# ADR-004: 비밀번호 찾기 → "재설정" 방식으로 구현

- 날짜: 2026-08-04
- 상태: 승인됨
- 관련: `backend/src/controllers/authController.js`, `backend/src/routes/authRoutes.js`, `frontend/Course Registration Platform/src/components/LoginPage.tsx`, `K8s/30-backend.yaml`, `K8s/40-frontend.yaml`, `docker-compose.yml`

## 상황 (Context)

로그인 화면에 "비밀번호를 잊으셨나요?" 버튼이 있었지만 `onClick` 핸들러가 아예 없어서 눌러도 아무 반응이 없었다 — UI만 있고 기능은 구현된 적이 없는 상태였다. 사용자가 비밀번호를 잃어버렸을 때 복구할 방법이 전혀 없었다.

## 검토한 대안과 트레이드오프

### 1안: 비밀번호 "찾기" (원본 비밀번호를 조회해서 그대로 보여주기) — 기각
- **기술적으로 불가능하다.** `authController.js`의 회원가입 로직이 `bcrypt.hash(password, 12)`로 비밀번호를 저장하는데, bcrypt는 **단방향 해시**다. "원래 비밀번호 → 해시값"은 되지만 "해시값 → 원래 비밀번호"로 되돌리는 연산 자체가 존재하지 않는다. DB의 `password` 컬럼에는 `$2a$12$...` 형태의 해시 문자열만 있고, 사용자가 입력했던 원본 비밀번호는 시스템 어디에도 남아있지 않다.
- 설령 평문 저장으로 바꿔서 "가능하게" 만들었다 해도 해서는 안 된다. OWASP Top 10의 A02(Cryptographic Failures)에 해당하는 결함이며, DB가 유출되면 전체 유저의 비밀번호가 그대로 노출된다. 많은 사용자가 여러 서비스에 같은 비밀번호를 재사용하므로, 이 앱 하나의 문제로 끝나지 않고 사용자의 다른 계정까지 위험해진다.

### 2안: 이메일/SMS 인증 기반 재설정 — 기각 (인프라 부재)
- 가장 표준적이고 안전한 방식이지만, `User` 모델에 `email` 필드 자체가 없고 메일 발송 인프라(SMTP 등)도 없다.
- 이 프로젝트의 리스크 관리 원칙(`portfolio-roadmap.md`: "새 기능 추가는 하지 않는다")에 비춰봐도, 이메일 인증 인프라를 새로 들이는 건 지금 스코프를 넘어서는 일이다.

### 3안: 학번+이름 본인확인 → 새 비밀번호 직접 설정 (채택)
- 장점: 기존 인프라(`Users` 테이블의 `studentId`, `name` 컬럼)만으로 구현 가능. 회원가입 때 쓰던 해싱 로직을 그대로 재사용.
- 전제: 이 프로젝트의 사용 대상은 자대생이라 학번은 학생 1인당 1개뿐이고, `User` 모델에 `studentId: {unique: true}`가 이미 걸려 있어 DB 레벨에서 중복이 원천적으로 불가능하다 — 그래서 `studentId`를 식별자로 삼는 데 문제가 없다.
- 단점: 이메일/OTP 같은 "소유 기반" 인증이 아니라 "지식 기반"(학번+이름을 아는 사람이면 누구나 통과) 인증이라, 타인이 악용할 수 있는 여지가 있다 (→ 한계 항목 참고).

## 결정과 이유

**3안. "찾기"가 아니라 "재설정"으로 기능 자체를 재정의한다.**

옛 비밀번호를 절대 복원·노출하지 않고, 본인확인만 통과하면 새 비밀번호를 설정하게 한다. 실제 서비스(네이버, 카카오, 은행 등)들도 전부 "비밀번호 찾기"라는 이름을 쓰더라도 실제로는 "재설정" 플로우만 제공한다 — 옛 비밀번호를 보여주는 곳은 없다.

## 구현

### 백엔드: `authController.js`, `authRoutes.js`

`resetPassword` 컨트롤러를 새로 추가했다.

```js
// backend/src/controllers/authController.js
exports.resetPassword = async (req, res) => {
    try {
        const { studentId, name, newPassword } = req.body;

        if (!studentId || !name || !newPassword) {
            return res.status(400).json({ message: '학번, 이름, 새 비밀번호를 모두 입력해주세요.' });
        }

        // 학번과 이름이 동시에 일치하는 사용자만 찾음 — 어느 쪽이 틀렸는지는 알려주지 않음(계정 존재 여부 유추 방지)
        const user = await User.findOne({ where: { studentId, name } });
        if (!user) {
            return res.status(400).json({ message: '학번 또는 이름이 일치하지 않습니다.' });
        }

        const hashedPassword = await bcrypt.hash(newPassword, 12);
        user.password = hashedPassword;
        await user.save();

        res.status(200).json({ message: '비밀번호가 재설정되었습니다. 새 비밀번호로 로그인해주세요.' });
    } catch (error) {
        console.error('비밀번호 재설정 오류:', error);
        res.status(500).json({ message: '서버 오류가 발생했습니다.' });
    }
};
```

핵심 설계 포인트: `User.findOne({ where: { studentId, name } })`처럼 **학번과 이름을 하나의 쿼리 조건으로 동시에 검사**한다. "학번은 맞는데 이름이 틀렸다"처럼 어느 쪽이 틀렸는지 구분해서 응답하면, 공격자가 이름을 바꿔가며 시도해서 "이 학번이 실제로 존재하는지"를 추측할 수 있게 된다(계정 존재 여부 유추 공격). 그래서 항상 동일한 메시지(`학번 또는 이름이 일치하지 않습니다`)만 돌려준다.

```js
// backend/src/routes/authRoutes.js
router.post('/reset-password', authController.resetPassword);
```

### 프론트엔드: `LoginPage.tsx`

- `isReset` 상태를 추가해서, 죽어있던 "비밀번호를 잊으셨나요?" 버튼에 `onClick={() => setIsReset(true)}`를 연결
- 재설정 전용 폼: 학번 / 이름 / 새 비밀번호 / 새 비밀번호 확인 4개 입력
- "새 비밀번호 확인"이 "새 비밀번호"와 다르면 **서버에 요청을 보내기 전에** 프론트에서 먼저 막음
- 성공/실패 메시지를 로그인 폼의 에러 표시와 분리된 상태(`resetMessage`, `error`)로 관리
- "로그인으로 돌아가기" 버튼으로 원래 화면 복귀

### DB에서 실제로 일어나는 일

- 새 행 생성/삭제 없음 — 기존 `Users` 테이블에서 `studentId`+`name`이 일치하는 **그 행 하나의 `password` 컬럼만 `UPDATE`**
- 스키마 변경 없음 — 컬럼 추가/삭제 없이 회원가입 때 쓰던 `password` 컬럼을 그대로 재사용
- 해싱 방식도 회원가입과 동일(`bcrypt`, cost factor `12`) — 재설정 후에도 로그인 컨트롤러의 `bcrypt.compare(password, user.password)`가 그대로 작동. 로그인 로직은 "지금 DB에 어떤 해시가 들어있는지"만 신경 쓰지, 그 해시가 회원가입 때 만들어졌는지 재설정 때 만들어졌는지는 구분하지 않는다.

### K8s / docker-compose 배포 반영

이 기능은 **frontend와 backend 코드가 동시에 바뀌었기 때문에, 두 환경 모두 이미지를 다시 빌드해야 반영된다.** (ADR-003에서 만든 "이미지 재사용 가능" 구조는 "환경마다 다른 주소를 안 넣어도 된다"는 뜻이지, "코드가 바뀌어도 재빌드가 필요 없다"는 뜻은 아니다.)

| 구성요소 | docker-compose | K8s(kind) |
|---|---|---|
| backend | `docker compose build backend` → 로컬 이미지 `courseregistrationplatform-backend:latest` 갱신 | `docker build -t binseoyun/backend:v2` → Docker Hub push → `K8s/30-backend.yaml` 이미지 태그 `v1→v2` 수정 → `kubectl apply` → `kubectl rollout status`로 롤아웃 확인 |
| frontend | `docker compose build frontend` → 로컬 이미지 갱신 | `docker build -t binseoyun/frontend:v4` → push → `K8s/40-frontend.yaml` 태그 `v3→v4` 수정 → `kubectl apply` |
| 반영 후 접근 경로 | `http://127.0.0.1:8090` (nginx 경유) | `http://127.0.0.1:18080` (Ingress 경유) |

**구현 중 겪은 시행착오 2가지** (둘 다 ADR-003에서 만든 same-origin 구조를 이해하지 못하고 테스트해서 생긴 문제):

1. **K8s에서 버튼 클릭이 안 됨**: backend는 `v2`로 재배포했지만 frontend 재배포를 빠뜨렸다. K8s는 여전히 `v3`(재설정 기능 추가 이전 코드)를 쓰고 있어서, "비밀번호를 잊으셨나요?" 버튼에 `onClick` 자체가 없는 예전 JS가 그대로 떠 있었던 것 — frontend를 `v4`로 재빌드/재배포해서 해결.
2. **`Unexpected token '<'... is not valid JSON`**: nginx를 거치지 않는 `http://127.0.0.1:3001`(frontend 컨테이너에 직접 접근)로 테스트했을 때 발생. frontend는 `serve -s build`로 떠 있는데, `-s`(SPA 모드) 옵션 때문에 `/api/auth/reset-password`처럼 모르는 경로는 API가 아니라 `index.html`을 그대로 반환한다. 그 HTML을 `response.json()`으로 파싱하려다 실패한 것 — ADR-003 이후 `3001`/`13000` 같은 개별 포트는 nginx/Ingress 없이는 API가 동작하지 않는 게 **의도된 동작**이라, nginx 경유 주소(`8090`)로 테스트해서 해결했다.

## 결과 (정량·정성)

**curl 기반 시나리오 검증** (docker-compose `8090`, K8s `18080` 양쪽 모두 동일하게 통과):
1. 회원가입 → 기존 비밀번호로 로그인 → `200` 성공
2. 틀린 이름으로 재설정 시도 → `400` 거부(`학번 또는 이름이 일치하지 않습니다`)
3. 정확한 학번+이름으로 재설정 → `200` 성공
4. 재설정 후 기존 비밀번호로 로그인 시도 → `400` 거부(`비밀번호가 올바르지 않습니다`)
5. 새 비밀번호로 로그인 → `200` 성공

**브라우저 UI**: `8090`, `18080` 양쪽 모두 "비밀번호를 잊으셨나요?" → 재설정 폼 → 성공 메시지 → 로그인 화면 복귀까지 정상 동작 확인.

## 한계 (실제 운영 환경이라면)

학번+이름 본인확인은 **지식 기반 인증**이다. 친구의 학번과 이름을 아는 사람이면 누구나 그 사람의 비밀번호를 임의로 바꿔버릴 수 있다는 취약점이 있다 — 특히 같은 학과·동아리처럼 서로의 학번을 아는 사이에서는 실질적인 위협이 된다.

실제 운영 환경이라면 **소유 기반 인증**(이메일 인증 링크 또는 SMS OTP)을 추가해야 한다. 이를 위해서는:
- `User` 모델에 `email` 필드 추가 (스키마 변경)
- 메일 발송 인프라(SMTP, AWS SES 등) 연동
- 재설정 요청 시 만료시간이 있는 1회용 토큰을 발급해서 이메일로 보내고, 그 토큰을 가진 사람만 실제 재설정 폼에 접근하게 하는 구조로 변경

이번 구현은 "본인확인 없이 아무나 비밀번호를 못 바꾼다" 수준까지는 확보했지만, "정말 본인만 바꿀 수 있다"는 수준까지는 아직 아니라는 걸 명확히 한계로 남긴다.
