## 0. 수강신청 트래픽 처리 로직의 언어 스택 — 별도 서비스로 뺄지 vs 기존 backend에 통합할지

> **용어 정정 (2026-09-01, #121)**: 원래 제목이 "마이크로서비스 언어 스택 선정"이었으나, 이 절의 실제 결정은 **"별도 서비스(Spring Boot)를 만들지 않고 기존 Node backend에 통합"**이다 — 즉 이 시스템은 MSA가 아니라 모듈러 모놀리스다. 아래 결정 내용(Node 유지)은 그대로고, 프레이밍만 정정한다. 전체 아키텍처 스타일 검토는 `doc/architecture/00-아키텍처-스타일-검토.md`.

### 상황(Context)
현재 시스템은 메인 API 서버(Node.js)와 AI 분석 서버(Python)로 역할이 분리되어 운영 중이다. 약 1.2만 명의 대규모 동시 접속이 발생하는 '수강신청 핵심 로직'을 처리할 방식을 정해야 한다. 한국 엔터프라이즈 시장의 표준인 Spring Boot(Java)를 도입해 3개 언어가 혼합된 폴리글랏(Polyglot) 환경을 구성할지, 기존 메인 서버 스택인 Node.js를 유지할지 결정이 필요하다.

목표: 언어적 유행이나 업계 표준을 맹목적으로 따르기보다, 도메인 특성(I/O Bound)을 정확히 분석하고 인프라 복잡도를 최소화하면서 극한의 처리량을 확보할 수 있는 기술을 선정한다.

### 검토한 대안과 트레이드오프

**대안 A: Spring Boot (Java/Kotlin)**
- 장점: 멀티 스레드 풀(Thread Pool) 기반의 안정적인 동시성 처리와 촘촘한 트랜잭션 제어(JPA 등) 생태계가 발달해 있음.
- 단점(오버엔지니어링 리스크): Node.js와 Python에 이어 Java까지 3개 언어를 K8s 클러스터 위에서 구동해야 함. CI/CD, 로깅, 모니터링 환경이 파편화되어 유지보수 비용과 컨텍스트 스위칭 오버헤드가 커짐.

**대안 B: Node.js**
- 장점: 이벤트 루프 기반 비동기 논블로킹 모델로, 네트워크 대기 시간이 긴 I/O 바운드 워크로드를 스레드 생성 비용 없이 처리함. JVM 대비 부팅 속도가 빨라 K8s 파드 스케일 아웃에 유리함.
- 단점: 싱글 스레드 특성상 무거운 동기 연산이 발생하면 이벤트 루프 전체가 멈추는(Block) 병목이 발생할 수 있음.

### 아키텍처를 통한 언어적 한계 돌파 전략
Node.js의 약점인 '싱글 스레드 병목'과 '복잡한 트랜잭션 처리의 한계'는 언어 교체 대신 **시스템 아키텍처의 책임 분산**으로 해결한다.
- **CPU 연산의 격리**: 시간표 겹침 확인, 중복 검증, 좌석 차감 등 무거운 동시성 제어 로직을 Node.js가 아닌 Redis 내부의 단일 Lua Script 트랜잭션으로 위임해 CPU 병목을 차단한다.
- **트랜잭션 책임 위임**: DB 락을 걸고 복잡하게 수정하는 대신, 검증을 통과한 데이터를 RabbitMQ로 비동기 전송하고 RDBMS의 복합 유니크 키 + `INSERT IGNORE`로 DB 엔진 단에서 멱등성을 보장한다.
- **I/O Bound 역할 집중**: Node.js 서버는 무거운 연산 없이 요청을 Redis/RabbitMQ로 빠르게 전달하는 라우터 역할만 수행해 이벤트 루프 효율을 극대화한다.

### 결정과 이유
대규모 수강신청 트래픽을 처리하는 핵심 마이크로서비스 스택으로 **Node.js**를 채택한다.

1. **1인 개발 환경의 현실적 제약**: 단일 개발자가 메인 백엔드부터 AI 서버, K8s 인프라까지 홀로 운영하는 상황에서 Spring Boot를 도입해 3개 이기종 스택을 유지보수하는 것은 전형적인 오버엔지니어링이며, 제한된 리소스 내에서 프로젝트 완성도를 무너뜨릴 리스크로 판단했다.
2. **도메인 워크로드와의 핏(I/O Bound)**: 수강신청 로직의 대부분이 외부 인프라(Redis, MQ)와의 네트워크 통신이므로, 비동기 I/O에 강한 Node.js가 가장 가볍고 빠르게 요구사항을 충족한다.
3. **폴리글랏 오버헤드 방지**: 개발 환경을 통일해 확보한 리소스를 인프라 튜닝과 k6 기반 부하 테스트(1.2만 명 규모)에 집중 투자한다.
4. **아키텍처 중심의 문제 해결 증명**: 언어의 태생적 한계를 회피하지 않고 Redis Lua Script, 메시지 큐 비동기 처리, K8s 스케일 아웃이라는 구조적 엔지니어링으로 정면 돌파한다.

## 1. 트래픽 제어 및 대기열 시스템

### 1.1 대기열 핵심 기술 선정

**상황**: 약 1.2만 명의 재학생이 '실시간 선착순 수강신청' 시점에 일시 접속할 것으로 예상된다. 모든 트래픽이 한 번에 WAS/RDBMS로 유입되면 시스템 마비가 발생한다. 서버를 보호하는 대기열 시스템을 구축하고, 사용자에게 공정하고 정확한 대기 순번을 실시간으로 안내해야 한다.

**검토한 대안과 트레이드오프**

- **Redis Sorted Set**
  - 동작 방식: 요청 시각(Timestamp)을 점수(Score)로 삼아 오름차순 정렬.
  - 장점: `ZRANK`로 O(log N)에 특정 유저의 순번을 즉시 계산 가능. `ZREM`으로 이탈자(TTL 만료 등)를 즉시 제거하고, `ZRANGE`로 일정 인원만 진입시키는 Throttling에 최적화됨.
  - 단점: 인메모리 기반이므로 노드 장애 시 대기열 데이터 유실 위험(AOF/RDB 백업 전략 필요).
- **Message Queue(Kafka, RabbitMQ 등)**
  - 동작 방식: 요청을 큐에 적재(Produce)하고 FIFO로 소비(Consume).
  - 장점: 트래픽 버퍼링, 순차 처리(FIFO) 보장.
  - 단점: 특정 메시지가 큐 내 어느 위치에 있는지 즉시 파악하기 어려워 "현재 대기 순번" 실시간 제공에 부적합. 이탈자를 큐 중간에서 선제적으로 제거하기 어려움.

**결정과 이유**: 진입 대기열의 핵심 기술로 **Redis Sorted Set**을 채택한다. 대기열의 본질은 단순 순차 처리가 아니라 '유입량 조절(Throttling)과 실시간 대기 피드백'이며, 이탈자를 쉽게 제거해 후순위 대기자를 빠르게 진입시킬 수 있다. Redis의 데이터 유실 위험은 수강신청이라는 단기성(수십 분 이내 종료) 이벤트 특성상 감내 가능한 리스크로 판단한다.

### 1.2 대기열 저장소(Redis) 인프라 아키텍처

**상황**: 1.1에서 대기열 핵심 기술로 Redis를 채택했다. 1.2만 명 규모 트래픽이 집중되는 상황에서 Redis가 다운되면(단일 장애점) 대기열 데이터가 전면 유실되고 수강신청이 마비된다. 노드 장애 시 수동 개입 없이 즉시 복구되는 고가용성(HA) 구조가 필요하다.

**검토한 대안과 트레이드오프**

- **Standalone**: 구성 단순, 지연 없음 / 단일 장애점(SPOF) — 장애 시 시스템 전체 중단.
- **Replica(Master-Slave)**: 데이터 복제 및 읽기 부하 분산 가능 / Master 다운 시 자동 Failover 미지원, 수동 개입 필수 — 분초를 다투는 선착순 상황에 부적합.
- **Sentinel**: Sentinel 노드가 Heartbeat로 모니터링, Master 다운 시 다수결 투표로 Slave를 자동 승격(Auto Failover) / 인프라 리소스 및 설정 복잡도 증가.
- **Cluster**: 대규모 데이터 분산 저장에 최적화 / 대기열은 보통 단일 Key(`waiting_queue:global`)로 관리되므로 Cluster 환경에서도 결국 특정 1대의 Master에 요청이 집중됨 — 분산 이점 없이 관리 비용만 증가하는 오버엔지니어링.

**결정과 이유**: 대기열 Redis 인프라로 **Sentinel 아키텍처**를 채택한다. 1.2만 명 규모의 삽입/조회 트래픽은 단일 노드의 기본 처리량(100k+ TPS)으로 병목 없이 수용 가능하므로, 핵심 과제는 성능 확장(Cluster)이 아니라 장애 시 즉각 무중단 복구(Sentinel)다.

> ⚠️ **재검토 필요**: 섹션 0에서 "1인 개발 현실 제약상 폴리글랏/오버엔지니어링을 피한다"는 논리로 Spring Boot를 배제했는데, 여기서는 추가 운영 부담(Sentinel 노드 구성)이 있는 아키텍처를 채택했다. 두 논리가 상충하지 않으려면 "왜 Sentinel의 운영 비용은 감내 가능한 수준인지"를 좀 더 구체적으로 (예: K8s 매니페스트 몇 줄로 끝나는 수준인지, 실제 관리 포인트가 몇 개 늘어나는지) 밝히거나, 로컬 kind 클러스터에서는 단일 노드로 개념을 증명하고 "실 서비스라면 Sentinel"이라는 식으로 스코프를 명확히 나눌 것.

### 1.3 세션 유지 및 이탈 방어(TTL)

**상황**: Active 상태로 진입한 사용자 중 일부가 네트워크 단절, 장시간 미조작, 비정상 종료 등으로 시스템 자원을 계속 점유하는 "유령 유저" 문제가 발생할 수 있다. 서버 수용 인원이 한정된 상태에서 유령 유저가 자리를 비우지 않으면 대기열이 영원히 줄지 않는 마비 상태에 빠질 수 있다.

**적용 방식**: 대기열을 통과해 Active 상태로 진입하는 순간 Redis 토큰에 `TTL`을 설정한다(`EXPIRE` 명령어 활용).
1. 대기(Wait)에서 진입(Active)으로 전환 시 사용자 토큰에 `TTL = 180초`를 설정한다.
2. 사용자가 수강신청 API를 호출할 때마다 서버는 먼저 Redis에서 해당 토큰의 TTL 잔여 여부를 확인한다.
3. TTL이 만료되어 토큰이 사라졌다면 `401 Unauthorized` 또는 전용 에러 코드를 반환하고, 프론트엔드는 사용자를 대기열 맨 뒤로 되돌린다.
4. 새로고침(F5) 시에도 TTL이 남아있다면 기존 세션을 유지시켜 재대기를 방지한다.

> ⚠️ **보완 필요**: TTL 만료로 사용자가 쫓겨나는 순간, "Active 인원 게이트"의 슬롯이 정확히 언제/어떻게 줄어들고 대기열에서 다음 인원이 언제 들어오는지(주기적 배치 폴링인지, TTL 만료를 이벤트로 감지해 즉시 트리거하는지)가 명시되어 있지 않다. 구현 전에 이 메커니즘을 구체화해야 한다.

### 1.3 보완 해결: Active 게이트 ↔ TTL 연동 메커니즘 확정 (이슈 #46, 2026-08-19)

위 보완 필요 사항과, 여기서 파생되는 세 가지 세부 결정을 묶어서 정리한다. 네 결정 모두 서로 맞물려 있어(예: 2번 결정이 3번 결정의 대안 하나를 원천적으로 배제) 하나의 절로 함께 기록한다.

#### (1) 대기열이 보호하는 대상: 전역(global) 게이트 vs 과목별 게이트

**상황**: 1.1~1.3 원문은 "대기열"과 "Active 게이트"가 정확히 무엇의 진입을 조절하는지 — 수강신청 사이트 자체인지, 특정 과목의 신청 화면인지 — 명시하지 않는다. 과목별 좌석 경쟁 자체는 이미 Stage 1(2.1/2.2)의 Redis Lua Script가 원자적으로 처리하고 있으므로, 이 대기열이 또 과목 단위로 존재해야 하는지가 불분명했다.

**검토한 대안과 트레이드오프**

- **과목별 대기열**: 인기 과목마다 별도 Sorted Set으로 줄을 세움. 장점: 과목별 실제 경쟁 강도에 비례해 대기가 발생(비인기 과목은 대기 없이 즉시 입장). 단점: 실제 수강신청은 사용자가 여러 과목을 탐색·비교하며 진행되는데, "입장 전에 어느 과목 줄에 설지"를 미리 정해야 하는 구조와 맞지 않는다. 자료구조도 과목 수만큼 늘어나 운영 복잡도가 커진다.
- **전역 게이트**: 특정 과목과 무관하게 "수강신청 화면 진입 자체"를 하나의 Sorted Set으로 조절. 장점: 실제 학교 수강신청의 체감 병목(특정 과목이 아니라 오픈 시각에 전교생이 사이트 자체로 몰림)과 정확히 일치. 자료구조 1개로 단순하고, Stage 1의 좌석 Lua Script(관심사: 정합성)와 완전히 분리된 관심사(관심사: 서버 보호)로 남는다.

**결정과 이유**: **전역 게이트**를 채택한다. 학교 수강신청 트래픽은 "이 과목이 인기라서" 몰리는 게 아니라 "신청 시작 시각에 전체 재학생이 동시 접속"해서 몰린다 — 경쟁의 단위가 과목이 아니라 사이트 진입 그 자체다. 과목별 대기열은 이 실제 행동 패턴과 맞지 않을 뿐 아니라, 이미 해결된 문제(과목별 좌석 경쟁)를 대기열 레벨에서 다시 쪼개 푸는 중복 설계가 된다.

#### (2) Active 게이트 자료구조: 개별 키 `EXPIRE` vs Sorted Set 재사용

**상황**: 원문(1.3)은 "Redis 토큰에 `EXPIRE`로 TTL 설정"이라고만 되어 있다. 이 방식대로면 개별 키는 Redis가 알아서 지워주지만, "지금 이 순간 Active 인원이 정확히 몇 명인지"를 조회하려면 `SCAN`으로 키를 훑거나 별도의 `INCR`/`DECR` 카운터를 따로 관리해야 한다.

**검토한 대안과 트레이드오프**

- **개별 키 + `EXPIRE` + 별도 카운터**: 표준적인 TTL 패턴. 단점: 카운터가 실제 살아있는 키 개수와 어긋날 위험이 상존한다(카운터 갱신 실패, 프로세스 재시작 중 유실 등) — Stage 1에서 이미 "좌석 수를 여러 곳에 중복 관리하면 어긋난다"(P1, TOCTOU)는 교훈을 얻었는데 같은 함정을 여기서 반복하는 셈이다.
- **Sorted Set 재사용(`score` = 만료 예정 시각)**: 대기열(1.1)과 동일한 자료구조 패턴을 Active 게이트에도 그대로 적용. `ZREMRANGEBYSCORE(key, -inf, now)`로 만료자를 일괄 제거하고, `ZCARD`로 현재 Active 인원을 별도 카운터 없이 즉시·정확히 조회한다.

**결정과 이유**: **Sorted Set 재사용**을 채택한다. 별도 카운터가 없으므로 "카운터와 실제 상태가 어긋난다"는 실패 지점 자체가 사라지고(Single Source of Truth), 대기열과 동일한 자료구조·연산 패턴이라 구현·테스트 비용도 줄어든다.

#### (3) 승격(Promotion) 트리거 방식: 배치 폴링 vs 이벤트 기반(Redis Keyspace Notification)

**상황**: 원문이 지적한 보완 필요 사항 그 자체 — TTL 만료를 감지해 Active 슬롯을 비우고 대기열의 다음 인원을 들여보내는 흐름을, 주기적으로 훑는 배치 방식으로 할지 만료 이벤트를 즉시 감지하는 이벤트 방식으로 할지가 미정이었다.

**검토한 대안과 트레이드오프**

- **이벤트 기반(`notify-keyspace-events Ex` + pub/sub)**: 키가 만료되는 순간 Redis가 이벤트를 발행하고, 구독자가 즉시 승격을 트리거. 장점: 지연 없는 즉각 반응. 단점: ① 현재 `docker-compose.yml`의 Redis는 기본 설정 그대로라 이 기능을 새로 켜야 하는 운영 항목이 추가되고, Stage 3의 Sentinel 구성에서도 동일 설정을 유지해야 해 관리 포인트가 늘어난다. ② Redis pub/sub은 fire-and-forget이라 구독자(Node.js)가 하필 그 순간 재시작 중이면 이벤트를 영구히 놓친다 — 결국 놓친 이벤트를 잡아줄 안전망으로 배치 폴링을 어차피 같이 둬야 하므로, 이벤트 기반을 추가해도 배치 폴링 자체를 안 짜도 되는 게 아니라 그 위에 얹는 것에 가까워 순이득이 작다. ③ 결정적으로, (2)에서 개별 키 `EXPIRE` 대신 Sorted Set 재사용을 택했기 때문에 애초에 "키 만료" 이벤트 자체가 발생하지 않는다 — Sorted Set 멤버는 만료되지 않고 `score`로만 판별되므로, 이벤트 기반은 이 설계에서 성립 조건 자체가 없다.
- **배치 폴링(고정 주기 승격 사이클)**: 고정 주기(예: 2~3초)마다 ① 만료자 제거(`ZREMRANGEBYSCORE`) ② 빈 슬롯 계산 ③ 대기열 앞순위를 그만큼 승격, 세 단계를 하나의 Lua Script로 원자 처리. 장점: 추가 인프라 설정이 필요 없고, fire-and-forget 유실 위험이 없으며(다음 사이클이 항상 안전망), 고정 주기라 k6 부하 테스트로도 재현 가능한 결정적(deterministic) 동작이다. 단점: 최대 폴링 주기만큼 승격이 지연된다(수 초 단위).

**결정과 이유**: **배치 폴링**을 채택한다. ① (2)의 Sorted Set 재사용 결정과 구조적으로 맞물린다 — 이벤트 기반의 전제(개별 키 만료 이벤트) 자체가 이 설계엔 없다. ② ADR 1.4(클라이언트 통신)에서 이미 동일한 논리(운영 단순성, Stateless, 오버엔지니어링 회피)로 Polling을 채택한 전례가 있어, 내부 메커니즘도 같은 철학을 일관되게 적용한다. ③ TTL이 120~180초 단위이므로 2~3초의 폴링 지연은 사용자 체감상 무의미하다. ④ 즉시성이라는 이득 대비, 이벤트 기반이 요구하는 추가 인프라 설정과 유실 위험이라는 비용이 이 규모(1.2만 명, 분 단위 TTL)에서는 정당화되지 않는다.

#### (4) TTL 정책: 고정(Fixed) vs 슬라이딩(Sliding)

**상황**: 원문 1.3은 "진입 시각 기준 TTL 180초"만 언급하고, 사용자가 API를 호출(활동)할 때마다 TTL이 갱신되는지는 명시하지 않는다.

**검토한 대안과 트레이드오프**

- **슬라이딩**: 활동이 있을 때마다 TTL을 그 시점부터 다시 연장. 장점: 실제로 작업 중인 사용자가 시간에 쫓겨 강제로 쫓겨나는 경우가 없다. 단점: "무엇을 활동으로 인정할지"의 경계가 모호하다 — 예컨대 순번 조회(폴링)까지 활동으로 인정하면, 클라이언트가 몇 초마다 자동으로 상태를 확인하기만 해도 사실상 세션이 무제한 유지되어, TTL을 애초에 도입한 목적(1.3 상황 문단의 "유령 유저 방지")이 무력화된다. 또한 Stage 2-4(Little's Law로 Active 인원수 역산)의 계산은 "1인당 체류 시간"을 상수로 가정하는데, 슬라이딩이면 체류 시간이 세션마다 달라져 이 역산의 전제가 흔들린다.
- **고정**: Active 진입 시각 기준으로 TTL을 고정하고, 활동 여부와 무관하게 그 시각에 만료. 장점: 유령 유저 방지라는 TTL의 원래 목적이 흔들리지 않고, Little's Law 역산의 전제(고정 체류 시간)와 정확히 맞아떨어지며, 구현도 단순하다. 단점: 이론적으로는 한창 작업 중인 사용자도 시간이 되면 쫓겨날 수 있다 — 다만 ADR 1.5가 이미 "수강신청 흐름(과목 검색→선택→클릭)은 짧다"고 전제하고 TTL(120~180초)을 그보다 여유 있게 잡았으므로, 실제로 이런 상황이 발생할 가능성은 낮다고 판단한다. 체감 UX는 프론트엔드의 "만료 임박" 경고(예: 남은 30초 안내, 2-6 UI 탭에서 고려)로 보완 가능하다.

**결정과 이유**: **고정 TTL**을 채택한다. ① 슬라이딩은 폴링만으로 세션이 무한정 유지될 수 있는 허점이 있어 TTL의 원래 목적(유령 유저 방지)을 구조적으로 약화시킬 위험이 있다. ② Stage 2-4의 Little's Law 역산이 "체류 시간 상수"를 전제하므로, 고정 TTL이 뒷단 계산과 일관성을 유지한다. ③ 도메인 특성상 고정 TTL의 단점(작업 중 강제 만료)이 실제 발생할 가능성은 낮고, 발생하더라도 프론트엔드 경고로 완화할 수 있어 서버 로직을 복잡하게 만들 실익이 없다.

**적용 파라미터(잠정값, 2026-08-19 조정)**: `ACTIVE_GATE_LIMIT`(Active 동시 인원 한도)과 `ACTIVE_TTL_SECONDS`(고정 TTL)는 둘 다 환경변수로 분리한다. 최종 확정값은 Stage 2-3/2-4(실험 02, Little's Law 역산 + Valve Tuning 실측)가 끝나야 나오지만, 이슈 #46/#48 구현 중 1.5의 최초 가설값(Active 50명, TTL 120초)이 실제 사용 패턴과 안 맞는다는 문제를 발견해 다음과 같이 조정했다:

- **TTL 120초 → 600초(10분)**: 120초는 "과목 하나를 빠르게 클릭"하는 흐름을 가정한 값이었는데, 실제 수강신청은 한 세션에서 여러 과목(정원 마감 시 대체 과목 재시도 포함)을 신청하므로 너무 짧다.
- **Active 50명 → 300명**: 여전히 감으로 정한 수치가 아니라, Stage 1 Group C 스윕 실측(`doc/experiment/01-결과-groupC.md`) — "동시 500명이 몰려도 handled_rate 100%" — 을 근거로 그보다 충분히 낮게 잡았다.

두 값 다 여전히 잠정치이며, 2-4(Little's Law 정식 역산)와 2-5(Valve Tuning 실측)에서 최종 확정한다.

**최종 확정(2026-08-20, 이슈 #57, [실험 02 결과](../experiment/02-결과.md) §12~17, [ADR-007](ADR-007-대기열-부하-backend-인스턴스-수평-확장.md))**: `ACTIVE_GATE_LIMIT=300`을 그대로 최종값(`N*`)으로 확정한다. Little's Law 역산은 개념적 오류로 폐기됐고(실험 02 결과 §6), Valve Tuning 실측(Round 1/1b, `VUS=12,000`)에서도 붕괴·개선의 원인이 Active 크기가 아니라 backend 처리 용량(대기 인원의 지속 폴링 총량을 받아내는 능력)이었음이 확인돼, Active 값 자체를 조정할 근거가 없었다. 대신 backend 인스턴스를 2대→4대로 수평 확장해 TTL 이탈 33.4%→0%, 전체 에러율 4.89%→0.06%로 개선했다(ADR-007). 다만 등록 API p95(4.4초)는 목표(500ms)에 못 미친 채 마무리됐고, 완전한 달성은 Phase 3(K8s 운영화 — CronHPA 사전 확장 + HPA 병행, [ADR-011](ADR-011-CronHPA-HPA-병행-확장-구조.md))로 명시적으로 이월한다.

### 1.4 클라이언트 대기 순서 렌더링(통신 방식)

**상황**: 사용자의 대기 순번은 실시간으로 줄어드는데, 서버가 이를 프론트엔드에 지속적으로 갱신해주지 않으면 사용자는 진행 상황을 알 수 없어 새로고침을 반복하거나 이탈한다. 1.2만 명 규모 클라이언트에게 서버 과부하를 최소화하면서 순번/예상 대기 시간을 전달할 통신 방식이 필요하다.

**검토한 대안과 트레이드오프**

- **Polling**: 클라이언트가 주기(예: 3~5초)마다 HTTP 요청 / 구현 단순, Stateless(서버 확장에 제약 없음), 모든 인프라와 호환 — 다만 1.2만 명이 3초마다 요청하면 초당 약 4,000건의 HTTP 오버헤드 발생.
- **SSE(Server-Sent Events)**: 서버 → 클라이언트 단방향 스트리밍 / 목적(단방향 통신)에 정확히 부합, 자동 재연결 — 다만 1.2만 개 연결을 유지해야 하므로 서버 메모리·커넥션 풀 튜닝이 필수.
- **WebSocket**: 양방향 실시간 통신 / 최저 지연 — 다만 대기열 안내는 단방향이면 충분해 오버엔지니어링이고, Stateful 특성상 스케일 아웃 시 Sticky Session/세션 클러스터링이 까다로움.

**결정과 이유**: **Polling**을 채택한다.
1. **연결 유지 비용 부재(Stateless)**: SSE/WebSocket은 1.2만 개 연결을 계속 쥐고 있어야 하지만, Polling은 요청-응답 후 즉시 연결을 끊어 서버가 상태를 기억할 필요가 없다.
2. **스케일 아웃 단순성**: Stateless이므로 로드밸런서가 여러 서버에 단순하게 트래픽을 분산할 수 있다.
3. **Thundering Herd 방지**: SSE 서버 1대가 다운되면 연결이 끊긴 클라이언트 전원이 동시에 재연결을 시도해 트래픽 폭풍이 발생할 수 있다. Polling은 애초에 요청이 3~5초 구간에 분산되어 있어 서버 장애 시에도 트래픽이 완만하게 분산된다.
4. **비즈니스 요구사항**: 대기 순번을 0.01초 단위로 보여줄 필요는 없다. 3초 주기 갱신으로도 충분하다(실제 티켓팅 서비스들도 유사한 주기로 갱신).

> 💡 **개선 아이디어(선택)**: 순번이 많이 남았을 때는 폴링 주기를 늘리고(예: 10초), 앞쪽에 가까워질수록 주기를 줄이는(예: 2초) 적응형 폴링을 고려하면 서버 부하와 UX를 동시에 개선할 수 있다.

### 1.5 부하 테스트로 확인해야 할 파라미터

1. **Active 인원수 결정**: 부하 테스트 도구(k6 등)로 "수강신청 1건 성공"에 필요한 DB 쿼리(조회/차감/INSERT) 시나리오를 만들고, 동시 접속자를 100/500/1,000명 단위로 늘려가며 최대 TPS를 도출한다. Little's Law를 응용해 "1인당 평균 체류 시간 × 초당 처리 가능 인원"으로 초기 Active 인원 기준점을 역산한다.
2. **TTL 시간 선정**: 업계 표준(결제 포함 3~5분, 단순 선착순 1~2분)을 참고하되, 수강신청은 `[과목 코드 입력] → [대기] → [과목 선택] → [신청 클릭]` 흐름이 짧으므로 초기값 120초로 가설을 세우고, 실제 사용자 로그(연습 모드 등)로 완료 시간 분포를 측정해 보정한다.
3. **초기 설정 및 반복 개선**: TTL 2분, Active 인원 보수적으로(예: 50/12,000)로 시작 → k6로 1.2만 명 가상 트래픽 테스트 → 병목 구간 확인 및 튜닝 → Active 인원 상향, 을 반복한다.

## 2. 핵심 수강신청 로직 및 동시성 제어

### 2.1 초과 예매 방지 및 동시성 제어

**상황**: 대기열을 통과한 Active 사용자 다수가 인기 과목(정원 50명 가정)의 수강신청 버튼을 동시에 클릭한다. 다수의 서버 스레드가 동시에 '잔여 좌석' 값을 읽고 차감하려 할 때 경쟁 상태(Race Condition)가 발생해 정원을 초과하는 신청이 성공할 수 있다.

**검토한 대안과 트레이드오프**

- **DB 비관적 락(`SELECT ... FOR UPDATE`)**: 정합성 보장이 가장 강력함 / 1,000명 동시 요청 시 1명만 락을 획득하고 나머지는 DB 커넥션을 쥔 채 대기(Blocking) — 커넥션 풀이 순식간에 고갈되고 데드락 위험도 높음.
- **DB 낙관적 락(Version 컬럼)**: 평상시 조회 속도가 빠름 / 충돌이 극심한 환경에서는 1명 성공에 999명이 실패해 재시도 로직이 필수이고, 이 재시도 폭주가 WAS의 CPU/스레드를 고갈시킴.
- **Redis 분산 락(Redisson Pub/Sub)**: DB 트래픽을 완전히 직렬화해 보호하고 정합성 리스크가 0%에 가까움 / `락 획득 → DB 조회 → DB 업데이트 → 락 반납`의 4단계 네트워크 I/O가 강제되는 직렬 구조. 1회당 평균 50ms로 가정하면 처리량은 초당 20건 수준으로, 1,000명 동시 클릭 시 마지막 사용자는 약 50초를 대기해야 함.
- **Redis 원자적 연산(`DECR`) + Lua Script**: DB 트랜잭션 없이 Redis 인메모리에서 `SISMEMBER`(중복 확인) → `DECR`(좌석 차감) → `SADD`(신청자 등록)를 하나의 Lua Script로 원자적으로 처리 / DB와의 동기화 실패(정합성) 리스크와 Lua Script가 무거워지면 Redis 전체가 Block될 위험.

**결정과 이유**: **Redis 원자적 연산 + Lua Script**를 채택한다.
1. RDBMS 락(비관적/낙관적)은 커넥션 풀 고갈이라는 물리적 병목으로 이어지므로 1순위로 배제.
2. Redis 분산 락은 정합성은 우수하나 4단계 네트워크 I/O 직렬화 구조상 처리량 한계가 명확해 배제.
3. DB 물리적 병목에 부딪혀 서버가 다운되는 것보다, 통제 가능한 엔지니어링 과제(정합성 리스크 관리)를 해결해 극한의 성능을 확보하는 편이 합리적이라고 판단.
4. 치명적 단점(데이터 동기화 실패 리스크)은 **3중 안전망**으로 통제한다: ① 성공 데이터를 MQ로 전송 ② 워커의 수동 ACK로 메시지 영속성 보장 ③ DB 복합 유니크 키로 멱등성 보장 ④ 반복 실패 메시지의 Dead Letter Queue(DLQ) 격리.

> ⚠️ **중요 — 2.2와의 관계 명확화 필요**: 아래 2.2에서 설명하는 "중복/시간표 겹침 검증" Lua Script는 이 섹션의 `DECR`을 포함한 확장판이다. **좌석 차감과 검증은 반드시 하나의 Lua Script로 합쳐 원자적으로 실행되어야 하며, 검증 호출과 차감 호출을 별도의 두 요청으로 분리하면 안 된다** (분리하면 Check-Then-Act 틈이 재발해 이 섹션에서 막으려 한 Race Condition이 그대로 부활한다). 문서/구현 모두에서 "단일 Lua Script"라는 표현을 명시적으로 통일할 것.
>
> ⚠️ **보완 필요 — 좌석 카운터 초기화(Seeding)**: 수강신청 오픈 전에 각 과목의 잔여 좌석 수를 DB(`Class.capacity - Class.enrolled`)에서 Redis로 채워 넣는 절차가 명시되어 있지 않다. 이 워밍업이 누락되거나 stale하면 전체 설계가 무의미해지므로, 오픈 전 배치 스크립트(또는 CronJob)로 언제·어떻게 시딩할지 별도로 설계해야 한다.
>
> ⚠️ **보완 필요 — 수강신청 취소(Drop) 흐름 부재**: 이 문서는 신청(추가) 경로만 다루고 있다. 실시간 수강신청이라면 취소도 필수 기능이며, 취소 시 Redis `INCR`(좌석 반환)과 `SREM`(신청자 명단 제거)이 필요하고, 반환된 좌석이 대기 중인 다음 신청자에게 어떻게 노출되는지도 함께 설계해야 한다. 현재 스코프에서 완전히 빠져 있다.
>
> ⚠️ **보완 필요 — DLQ 격리 이후의 보상(Compensation) 로직 부재**: Redis에서는 "성공"(좌석 차감 완료) 판정을 받았지만 DB 저장이 계속 실패해 DLQ로 격리된 경우, 해당 학생은 화면상 성공으로 보이는데 실제 DB엔 기록이 없다. 이 좌석을 다시 정원으로 되돌리는 보상 로직이나, 최소한 DLQ 적재 시 즉시 알림을 받는 모니터링이 필요하다. "나중에 개발자가 DLQ를 확인한다"는 수준으로는 실시간 서비스에서 신뢰성을 담보할 수 없다.

### 2.2 중복 예매 및 무결성 검증

**상황**: 특정 과목의 잔여 좌석을 차감(Redis `DECR`)하기 전에 반드시 ① 동일 과목 다중 클릭(중복 신청) ② 기존 신청 과목과의 시간대 겹침을 검증해야 한다. 이 검증을 서버 코드/DB/Redis 중 어디서 처리하느냐에 따라 동시성 버그 발생 여부가 갈린다.

**검토한 대안과 트레이드오프**

- **Application Layer**: 서버 코드에서 Redis/DB 데이터를 가져와 겹침 여부를 판단한 뒤 별도로 차감 명령을 보냄 / Check와 Act 사이의 틈에서 Race Condition이 발생함(매크로로 0.01초 안에 2번 클릭하면 둘 다 통과해버림). 데이터 왕복으로 인한 네트워크 오버헤드도 큼.
- **Database Layer**: 요청마다 RDBMS에 `SELECT`를 날려 확정 시간표를 조회해 겹침을 검증 / 1.2만 명의 폭발적인 `SELECT` 트래픽으로 DB 커넥션이 고갈됨 — 2.1에서 Redis로 DB 트래픽을 막아둔 아키텍처적 노력이 무의미해지는 안티 패턴.
- **Cache(Redis) Layer**: 수강신청 오픈 전 유저별 기존 시간표와 전체 과목 시간표를 Redis `Set`에 캐싱(Cache Warm-up)해두고, 검증 로직 자체를 Redis 내부(단일 Lua Script)로 밀어 넣음. `SISMEMBER`(중복 검증) → `SINTER`(시간표 겹침 검증, 교집합 존재 여부) → 통과 시 `DECR`(좌석 차감) + `SADD`(신청 과목 추가) 순으로 하나의 스크립트에서 처리 / Redis 싱글 스레드 특성상 스크립트가 실행되는 동안 Check-Act 틈이 원천 차단되고, RDBMS 접근 없이 메모리 연산만으로 처리되어 DB를 읽기 트래픽 폭주로부터 보호함.

**결정과 이유**: 중복 예매 및 시간대 겹침 검증을 **Cache(Redis) Layer**에서, **2.1의 좌석 차감과 하나의 Lua Script로 통합해** 처리한다.
- 검증(서버)과 차감(Redis)이 분리되었을 때 필연적으로 발생하는 Check-Then-Act 틈을 단일 Lua Script로 결합해 완벽한 원자적 트랜잭션을 보장한다.
- 복잡한 시간표 겹침 연산을 RDBMS `JOIN`/`SELECT` 대신 Redis `Set`의 교집합(`SINTER`) 연산으로 대체해 메인 DB를 읽기 트래픽 폭주로부터 보호한다.
- 데이터가 머무는 Redis 저장소 내부로 검증 로직을 밀어 넣어 불필요한 네트워크 I/O 왕복을 없앤다.

## 3. 비동기 처리 및 데이터 영속성

### 3.1 메시지 큐(Message Queue) 도입

**상황**: 앞단(Redis Lua Script)에서 검증을 통과한 '수강신청 성공 데이터'가 메모리에 머물고 있다. 이를 RDBMS에 동기적으로 넣으면 DB 병목이 발생하고, 비동기로 넣을 때 중간 연결이 끊어지면 데이터가 유실될 수 있다. API 서버가 즉시 성공 응답을 반환하면서도, 워커나 DB가 일시적으로 다운되어도 데이터가 절대 유실되지 않는 신뢰성 있는 MQ 인프라가 필요하다.

**검토한 대안과 트레이드오프**

- **RabbitMQ**: 워커가 명시적 수동 ACK를 보내지 않으면 메시지를 지우지 않고 재시도함. DLQ 설정이 기본 기능으로 제공되어 구성이 직관적임 / 트래픽이 초당 십만 건 단위로 넘어가면 브로커 부하가 걸리지만, 1.2만 명 규모에는 무리 없음.
- **Kafka**: 메시지를 디스크에 로그(Log) 형태로 순차 기록해 며칠치 트래픽을 보관하고 재생(Replay)할 수 있어 DB 손상 시 완전 복구가 가능함 / Zookeeper(또는 KRaft)와 브로커 노드를 구성해야 해 인프라 리소스와 학습 곡선이 높고, DLQ도 직접 토픽을 만들고 재시도 로직을 구현해야 함.

**결정과 이유**: **RabbitMQ**를 채택한다. 전체 재학생이 1.2만 명이나 초기 서비스는 전공 과목과 일부 인기 교양으로 제한되므로, 대규모 스트리밍에 특화된 Kafka는 클러스터 유지보수 비용 대비 실효성이 떨어지는 오버스펙이다. 데이터 유실 방지에 필요한 수동 ACK와 DLQ가 기본 내장되어 있어 복잡한 재시도 설계 없이 무결성 파이프라인을 빠르게 구축할 수 있다.

### 3.2 비동기 워커 노드 설계 및 데이터베이스 멱등성 보장

**상황**: 워커가 DB에 데이터를 성공적으로 `INSERT`한 직후, RabbitMQ에 "처리 완료(ACK)" 신호를 보내는 찰나에 워커가 다운되거나 네트워크가 끊길 수 있다. RabbitMQ는 처리가 실패했다고 판단해 동일 메시지를 다른 워커에게 다시 전송(중복 전달)한다. 동일 메시지가 여러 번 유입되어도 DB에는 1건만 저장되는 멱등성이 필요하다.

**검토한 대안과 트레이드오프**

- **애플리케이션 계층 검증(`SELECT` 후 `INSERT`)**: 워커가 미리 존재 여부를 조회한 뒤 삽입 / Check-Then-Act 문제가 그대로 재발함 — 두 워커가 동시에 조회하면 둘 다 "없음"으로 판단해 중복 삽입함. 사용 금지 대상.
- **DB 유니크 키 + 애플리케이션 예외 처리**: `[학번+과목코드]` 복합 유니크 키를 걸고 무조건 `INSERT`, 중복 시 발생하는 예외를 `Catch`해 무시 후 ACK / 완벽한 멱등성 보장, 다만 예외 처리 자체가 약간의 오버헤드를 유발.
- **DB 유니크 키 + `INSERT IGNORE`(또는 `Upsert`)**: 중복 시 DB가 에러 대신 조용히 무시(Ignore)하고 정상 응답 반환 / 예외 처리 없이 코드가 단순해지고 성능이 우수함, 다만 MySQL 종속 문법이라 DB 교체 시 쿼리 수정이 필요.

**결정과 이유**: **DB 복합 유니크 키 + `INSERT IGNORE`**를 채택한다.
1. `[학번+과목코드]` 복합 유니크 키로 RDBMS 레벨에서 원천적으로 중복 저장을 차단한다.
2. 애플리케이션 계층의 `try-catch` 대신 DB 고유 문법으로 처리해 워커 로직이 단순해지고 예외 처리 오버헤드가 사라진다.
3. 중복 메시지도 정상(Success) 응답을 받으므로 워커가 즉시 ACK를 보낼 수 있어, 실패 메시지가 불필요하게 큐에 쌓이거나 DLQ로 새는 것을 방지한다.

## 4. 인프라 확장 및 검증

### 4.1 서버 확장성(Scalability)

**상황**: Node.js 애플리케이션이 이미 K8s 클러스터 위에서 동작 중이며, 수강신청 오픈 시각(예: 오전 9시 정각)에 1.2만 명의 트래픽이 한꺼번에 몰린다.

**검토한 대안과 트레이드오프**

- **일반 HPA(반응형 확장)**: 파드의 CPU/메모리 사용량이 임계치를 넘으면 자동으로 파드 개수를 늘림 / 지표 수집과 새 파드 기동에 최소 1~2분이 걸려, 오전 9시 정각의 트래픽 폭증에는 이미 늦음.
- **CronHPA(예측형 사전 확장)**: CPU 지표를 기다리지 않고 '시간'을 기준으로 스케일링해, 수강신청 시각 전에 파드를 최대치로 미리 늘려두고 종료 후 최소치로 되돌림 / 티켓팅/수강신청처럼 정해진 시각에 트래픽이 폭증하는 도메인의 표준 운영 방식.

**결정과 이유**: **CronHPA(예측형 사전 확장)**를 채택한다. 트래픽 발생 시각이 명확히 예정되어 있는 도메인 특성상, 반응형 확장의 1~2분 지연은 곧 서버 다운을 의미하므로 사전 확장이 필수적이다.

> **확장(2026-08-24, 이슈 #72, [ADR-011](ADR-011-CronHPA-HPA-병행-확장-구조.md))**: 이 결정은 유지하되 **HPA 병행**으로 확장한다 — 사전 확장이 1순위 수단인 것은 그대로이고, 예측을 벗어난 트래픽을 HPA가 안전망으로 흡수한다. 다만 두 컨트롤러를 각각 걸면 같은 `spec.replicas`를 번갈아 덮어써 파드 수가 진동하므로, **스케줄은 HPA의 `minReplicas`만 조정하고 `replicas` 기록자는 HPA 하나로 유지**한다. 그동안 ADR-007·실험 02 결과·로드맵이 이 결정을 반영하지 않고 "HPA 기반 동적 확장"으로만 적어왔던 표기 오류도 함께 정정했다.

> ⚠️ **보완 필요**: Node.js 파드 스케일링만 다루고 있고, 파드 수가 늘어나면 함께 증가하는 Redis/RabbitMQ 커넥션 수(커넥션 풀 사이징)에 대한 논의가 빠져 있다. 파드를 최대치로 늘렸을 때 Redis/RabbitMQ가 받아들일 수 있는 총 커넥션 한도도 함께 설계해야 한다.

### 4.2 대기열 및 부하 테스트(Load Testing)

**상황**: 1.2만 명의 동시 접속 상황을 가상으로 재현해 병목 지점(Redis 차감, MQ 워커 속도 등)을 찾아내고 튜닝해야 한다.

**검토한 대안과 트레이드오프**

- **nGrinder**: Groovy 기반으로 시나리오 작성이 쉬움, Docker Compose로 자동 환경 구성 가능 / k6 대비 트래픽 발생 성능이 낮고, **Grafana 연동이 불가능**해 현대적 대시보드 통합에 제약이 큼.
- **k6 + InfluxDB + Grafana**: JavaScript로 직관적인 시나리오 작성, nGrinder 대비 압도적으로 가벼운 성능 / InfluxDB-Grafana 연동에 수동 개입이 필수적이라 Docker Compose만으로 원클릭 배포가 불가능함.
- **k6 + Prometheus + Grafana**: JavaScript 기반(Node.js와 언어 통일), Go로 작성된 k6 엔진의 성능 + Prometheus의 시계열 수집 능력 / 수동 개입 없이 Docker Compose로 100% 자동 환경 구성이 가능하며, Grafana와 완벽하게 연동됨.

**결정과 이유**: **k6 + Prometheus + Grafana**를 채택한다. 세 대안 중 유일하게 개발자 수동 개입 없이 Docker Compose로 완전 자동 환경 구성이 가능하고, Prometheus/Grafana는 현재 K8s 생태계와 가장 자연스럽게 융합되는 클라우드 네이티브 표준 모니터링 스택이다. Node.js와 동일한 JavaScript로 시나리오를 작성할 수 있어 컨텍스트 스위칭 비용도 없다.

**목표 지표(KPI)**
1. **VU(Virtual Users)**: 1.2만 명 동시 접속 시뮬레이션 유지력
2. **Throughput(TPS/RPS)**: 대기열을 거쳐 들어온 초당 요청을 에러 없이 방어하는지
3. **Latency(p95)**: 상위 95% 사용자가 버튼 클릭 후 응답받기까지의 시간 (목표: 500ms 이내)

이 설계를 그대로 구현에 옮기기 전에 아래 항목들을 먼저 결정/보완해야 한다.

1. **로드맵 스코프 확정**: `doc/portfolio-roadmap.md` Phase 2에 대기열(Waiting Room) 시스템을 명시적으로 포함하고, "왜 이것이 신규 기능이 아니라 기존 수강신청 기능이 실제 트래픽을 견디기 위한 필수 전제조건인지"를 근거로 남긴다. (→ 이 ADR과 별개로 로드맵 문서에 반영)
2. **2.1/2.2 Lua Script 통합**: 좌석 차감(2.1)과 중복/겹침 검증(2.2)이 하나의 Lua Script라는 점을 구현 시점에 코드/문서 양쪽에서 명확히 통일한다.
3. **Redis 좌석 카운터 시딩(Seeding) 절차 설계**: 수강신청 오픈 전 DB → Redis로 잔여 좌석을 채워 넣는 배치(CronJob 등)를 별도로 설계한다.
4. **수강신청 취소(Drop) 흐름 설계**: 현재 문서에 전혀 없다. 좌석 반환(`INCR`)과 신청자 명단 제거(`SREM`), 그리고 반환된 좌석이 대기자에게 어떻게 노출되는지를 새로 설계해야 한다.
5. **DLQ 보상(Compensation) 및 모니터링 설계**: Redis 성공/DB 실패 불일치가 발생했을 때의 자동 복구(좌석 반환) 또는 최소한 실시간 알림 체계를 설계한다.
6. ~~**Active 게이트 ↔ TTL 연동 메커니즘 구체화**: TTL 만료 시 Active 슬롯이 언제/어떻게 줄고 대기열에서 다음 인원이 언제 들어오는지(배치 폴링 vs 이벤트 기반)를 명시한다.~~ → **해결**: §1.3 보완 해결(이슈 #46) 참고 — 전역 게이트 + Sorted Set 재사용 + 배치 폴링 + 고정 TTL로 확정.
7. **Sentinel 채택의 운영 비용 재검토**: "1인 개발 오버엔지니어링 방지" 논리와의 정합성을 다시 짚거나, 로컬 kind 클러스터에서의 실제 구현 범위(단일 노드로 개념 증명 vs 실제 Sentinel 구성)를 명확히 한다.
8. **Redis/RabbitMQ 커넥션 풀 사이징**: Node.js 파드가 CronHPA로 최대치까지 늘어났을 때 Redis/RabbitMQ가 감당할 총 커넥션 수를 함께 설계한다.
