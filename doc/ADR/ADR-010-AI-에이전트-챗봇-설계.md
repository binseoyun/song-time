# ADR-010: AI 에이전트 챗봇(RAG + Function Calling) 아키텍처 설계

- 날짜: 2026-08-20
- 상태: 결정됨 (ADR-006과 같은 성격 — 여러 결정이 통합된 설계 문서. 구현 중 세부가 바뀌면 개별 ADR로 분리)
- 관련: 이슈 #51, `doc/AI-에이전트-구현계획.md`, `backend/ai-server/main.py`(현행 구현)

## 0. 배경 — 왜 다시 만드는가

현재 `/recommend` 엔드포인트는 "직무 버튼 클릭 → jobInterest+major 2개 값 전송 → 전체 강의 목록을 프롬프트 하나에 욱여넣어 Gemini 단발 호출 → JSON 코드 리스트 응답"이 전부다. 화면엔 "AI가 분석 중..."이라고 나오지만 실제로는 대화가 아니라 백그라운드 배치 호출 한 번이다.

실사용 관점에서 이 방식은 학생의 실제 고민(하나의 학부 안에도 분야가 다른 전공 선택 과목이 무수히 많고, 각자 선호·진로가 달라 어떤 강의를 들을지 일일이 강의계획서를 읽어보며 판단해야 하는 어려움)을 전혀 못 돕는다. 목표는 이걸 **강의계획서 근거로 답하고, 실시간 정보(잔여석·대기열)를 조회하고, 필요하면 신청까지 함께 고민해주는 대화형 상담 에이전트**로 바꾸는 것이다.

## 1. 로드맵과의 관계

`portfolio-roadmap.md`의 "새 기능 추가 금지" 원칙과 별개로, 비밀번호 재설정(ADR-004)·회원 탈퇴(ADR-005)·실시간 수강신청(ADR-006)과 같은 **"로드맵 외 작업"**으로 정직하게 분류한다. 실시간 수강신청 Stage 2/3가 모두 마무리된 시점(2026-08-20)에 착수한다.

## 2. 언어/서비스 배치 결정

### 상황
새 코드를 어디(어떤 언어/프로세스)에 둘지 정해야 한다. 이 프로젝트는 이미 Node.js 백엔드(Express)와 별도 Python `ai-server`(FastAPI, `google-generativeai` 사용 중) 두 서비스가 존재한다.

### 검토한 대안과 트레이드오프

| 대안 | 장점 | 단점 |
|---|---|---|
| **A. Python — 기존 `ai-server` 확장** | Gemini SDK가 이미 이 프로세스에 있음(`main.py`). Chroma는 Python이 1급 지원(원 개발 언어)이라 SDK/문서/커뮤니티 사례가 가장 풍부. PDF 파싱 생태계(pdfplumber 등)도 Python이 강함. 기존 `/recommend`가 이미 여기 있어 자연스러운 확장 | 대화 상태(Redis/MySQL)에 접근하려면 Python 쪽에도 새 클라이언트 연결이 필요(§3에서 이 문제를 다시 다룸) |
| B. Node.js — 기존 backend에 직접 통합 | 이미 Redis/MySQL 커넥션이 backend에 있어 대화 상태 저장이 더 직접적 | Chroma의 JS 클라이언트는 존재하지만 Python 대비 성숙도가 낮음, PDF 구조 보존 파싱 생태계가 Python보다 약함, 기존 `/recommend` 로직이 Python에 있어 로직이 두 언어에 흩어짐 |
| C. 완전히 새로운 서비스(언어 무관) | 관심사 분리 명확 | 새 컨테이너=새 리소스 부담(이 프로젝트가 이미 신중히 다루는 문제, ADR-007/008/009 참고), Gemini 호출 로직이 두 군데로 중복 |

### 결정과 이유
**A(Python, 기존 `ai-server` 확장)를 채택한다.** Chroma/PDF 파싱 생태계 우위가 결정적이고, 새 컨테이너를 안 늘리는 게 이 프로젝트가 일관되게 지켜온 원칙(ADR-009: Circuit Breaker 보류 이유도 결국 "복잡도 대비 이 프로젝트 규모에서 정당화 안 됨")과 맞는다.

## 3. 상태 소유 경계 — Python은 오케스트레이션만, 상태는 Node가 소유

### 상황
`ai-server`가 Python으로 결정됐는데, 대화 상태(최근 대화 메모리 Redis, 영구 히스토리 MySQL `chat_sessions`/`chat_messages`)를 어디가 관리할지가 남는다. 확인해보니 `ai-server`는 지금까지 완전히 **stateless**했다(`/recommend`, `/api/schedule` 둘 다 상태 없음, `requirements.txt`의 `sqlalchemy`/`mysql-connector-python`은 실제로는 어디서도 쓰이지 않는 죽은 의존성이었다 — `scheduler.py`는 `mock_db.py`의 목 데이터만 쓴다).

### 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| **A. Python이 Redis/MySQL에 직접 연결** | 구현이 한 프로세스 안에서 끝남 | 이 프로젝트 전체가 "Node backend = 모든 상태의 단일 진실"(대기열 Redis, Registration MySQL 등)이라는 원칙을 지켜왔는데 여기서 처음으로 깨짐. 같은 스키마에 Node/Python 두 클라이언트가 각자 연결하면 스키마 변경 시 양쪽 다 맞춰야 하는 유지보수 부담 발생 |
| **B. Python은 오케스트레이션만, 상태 읽기/쓰기는 Node 내부 API 경유** | 기존 원칙 유지. Tool 실행(예: `GET /api/courses`)도 이미 Node API를 호출하는 구조라서(이슈 #51), 상태 저장도 같은 패턴이면 아키텍처가 일관됨 | Python→Node 내부 HTTP 호출이 한 홉 늘어남(대화 응답 스트리밍 자체엔 영향 없음 — SSE는 Python이 Gemini와 직접 주고받고, 상태 저장은 응답 완료 후 비동기로 기록) |

### 결정과 이유
**B를 채택한다.** "상태는 Node가 소유"라는 이 프로젝트의 일관된 원칙(Redis 대기열, MySQL Registration 전부 이 원칙을 따름)을 깨지 않는 게, 향후 스키마 변경/디버깅 비용을 줄이는 데 더 중요하다고 판단했다. 구체적으로 Node backend에 `POST /api/ai/sessions/:id/messages`(내부 전용, `cronAuthMiddleware`류가 아니라 서비스 간 인증 — 상세는 구현 시 확정) 같은 내부 API를 추가하고, Python은 이걸 호출해 대화 기록을 남긴다.

## 4. Vector DB 결정 — Chroma

### 상황
Pinecone/Chroma/Weaviate/Milvus/Faiss/Qdrant/pgvector/Elasticsearch/pgvecto.rs 9개 옵션을 조사했다(전체 비교는 부록 A).

### 결정과 이유
**Chroma**를 채택한다. 새 인프라 부담이 사실상 0(기존 `ai-server` 프로세스에 임베디드로 내장 가능), 강의계획서 수십~수백 건 규모에 정확히 맞고, Apache 2.0으로 라이선스 문제도 없다. 2순위 후보였던 Qdrant(단일 컨테이너, Rust, CPU 효율 좋음)는 "실제 벡터 DB 서비스 운영 경험"이라는 포트폴리오 서사엔 유리하지만 이 규모에서 실익이 크지 않아 보류. pgvector는 MySQL 스택에 Postgres를 새로 얹어야 하는 비용 때문에 제외.

**AWS(S3 Vectors, Aurora+pgvector)도 검토했으나 지금은 채택하지 않는다.** 비용 자체는 이 규모에서 무시할 수준(S3 Vectors 1천만 벡터·월 100만 쿼리 기준 월 $11.38, Aurora+pgvector 프리 티어 존재)이지만, 로드맵의 "AWS 실배포"는 아직 착수 전인 후반부 단계다. 지금 벡터 DB만 AWS로 가져가면 이 프로젝트가 지금까지 지켜온 "로컬 `docker-compose`로 완결" 원칙이 깨지고, 아직 시작 안 한 Phase를 부분적으로 앞당기는 셈이 된다(K8s Phase 3 관련 항목들을 전부 보류한 것과 같은 논리, ADR-007 참고). **재검토 조건**: 로드맵의 AWS 실배포 단계에 실제로 도달하면, 그때 Chroma→S3 Vectors(또는 Aurora+pgvector) 마이그레이션을 검토한다 — Before/After 비용·지연 수치까지 남기면 포트폴리오 서사로도 유효하다.

## 5. 임베딩 모델 결정 — Gemini `gemini-embedding-001`

### 상황
청킹된 강의계획서 텍스트를 벡터로 바꿀 임베딩 모델이 필요하다.

### 검토한 대안
- **A. Gemini `gemini-embedding-001`**: 이미 이 프로젝트가 Gemini를 쓰고 있어 API 키/SDK 재사용, $0.15/1M 토큰(2026-08 기준), 3072차원(768/1536으로 축소 가능, Matryoshka), 최대 입력 2,048토큰
- **B. 로컬 오픈소스 임베딩(예: `sentence-transformers`)**: 무료, 네트워크 호출 없음 — 그러나 모델 다운로드(수백MB~수GB)와 추론 자체가 CPU를 쓰는데, 이 로컬 환경은 이미 CPU가 여러 번 병목이었던 이력이 있다(트러블슈팅 08, ADR-007). 임베딩은 일회성 배치 작업(적재 시 1회)이라 CPU 부담은 짧게 끝나지만, 굳이 로컬 리소스를 쓸 이유가 API 비용($0.15/1M 토큰, 강의계획서 수백 건이면 몇 센트 수준)보다 크지 않다
- **C. Chroma 기본 임베딩 함수**(`all-MiniLM-L6-v2` 등): 설정 없이 바로 동작하지만 검색 품질이 Gemini 계열보다 낮다는 평가가 일반적이고, "이미 쓰는 모델과 일관성 유지"라는 이점도 없음

### 결정과 이유
**A(Gemini `gemini-embedding-001`)를 채택한다.** 비용이 무시할 수준이고, 생성 모델과 임베딩 모델을 같은 공급자로 맞추면 API 키/SDK/장애 대응 로직을 하나로 유지할 수 있다.

## 6. PDF 파싱 라이브러리 결정 — `pdfplumber`

### 상황
사용자가 강의계획서를 PDF로 제공할 예정이다. 텍스트 추출 라이브러리가 필요하다.

### 검토한 대안
- **A. `pdfplumber`**: MIT 라이선스, 테이블/구조화 데이터 추출에 강함(강의계획서의 "주차별 강의 계획" 같은 표 구조를 살리는 데 유리), 속도는 느린 편(18페이지/초)
- **B. `PyMuPDF`**: 8~12배 빠르고(180페이지/초) 레이아웃 보존이 우수하지만 **AGPL-3.0 라이선스** — 네트워크로 서비스를 제공하는 프로그램에 AGPL 라이브러리를 포함하면 그 서비스 이용자에게 AGPL 조건으로 소스를 제공해야 하는 의무(§13, network use)가 생긴다. 이 프로젝트는 이미 전체가 GitHub에 공개돼 있고 향후 실제 배포(AWS)까지 계획돼 있어, 이 의무를 피하는 게 낫다

### 결정과 이유
**A(`pdfplumber`)를 채택한다.** 속도 차이(12배)는 강의계획서 수십~수백 건을 1회 적재하는 배치 작업에서는 체감되지 않고(전체 처리 시간이 몇 분 vs 몇십 초 수준 차이), 라이선스 리스크를 원천 차단하는 게 더 중요하다.

## 7. Tool vs RAG 이원화 아키텍처

### 결정
정답이 정해진 구조화된 값(교수명·시간표·잔여석·졸업요건)은 임베딩 검색이 아니라 기존 DB/API를 직접 호출하는 **Tool**로 처리한다. 강의계획서 본문처럼 자연어 매칭이 필요한 데이터만 **Vector DB(RAG)** 대상으로 삼는다.

### 이유
안 그러면 청킹 경계 때문에 "몇 명 남았어?" 같은 정답이 하나뿐인 질문에서도 할루시네이션이 날 수 있다 — RAG는 "의미적으로 비슷한 내용을 찾아오는" 도구지 "정확한 최신 값을 조회하는" 도구가 아니기 때문이다.

## 8. Tool 인벤토리

기존 API로 대부분 커버된다:

| Tool | 대상 API | 신설 여부 |
|---|---|---|
| 잔여석 조회 | `GET /api/courses` | 기존 |
| 대기열 순번 조회 | `GET /api/queue/status` | 기존 |
| 신청/취소(write) | `POST`/`DELETE /api/registrations/redis...` | 기존(최종 채택 API는 로드맵 Phase 2 "최종 개선안 선택" 완료 후 확정 — Stage 2에서 연동) |
| 과목 단건 조회 | `GET /api/courses/:code` | **신설** — 현재 없음, 매번 전체 리스트를 프론트가 필터링하는 구조라 Tool 입장에서 비효율 |
| 강의계획서 의미 검색 | (신규) Chroma 쿼리 | 신설 |

## 9. Write Tool 확인 흐름

read-only Tool(잔여석/대기열/과목 조회)은 즉시 자동 실행한다. write Tool(신청/취소)은 **LLM이 파라미터만 제안 → 프론트가 확인 카드 렌더링 → 사용자 승인 후에만 실제 API 호출**한다. 프롬프트 튜닝이 아니라 Tool 등급(read/write) 자체로 강제하는 구조적 가드레일이다 — 프롬프트만으로 "실행 전에 꼭 물어봐"라고 지시하면 우회될 위험이 있지만, 애초에 write Tool 실행 코드 경로 자체를 사용자 승인 없이는 못 타게 만들면 이 리스크가 구조적으로 사라진다.

## 10. 대화 상태 저장

- **작업 메모리(최근 N턴)**: Redis, TTL 부여 — Group C가 이미 확립한 "휘발성 상태 전용" 원칙 재사용(ADR-006 1.3)
- **영구 히스토리**: MySQL `chat_sessions`/`chat_messages` 신설 — 추후 Tool 정확도/할루시네이션 측정용 eval 데이터 원본으로도 사용
- 소유/접근 방식은 §3 결정에 따라 Node backend가 관리, Python은 내부 API 경유

## 11. 스트리밍 및 배치 위치

새 서비스를 만들지 않고 기존 `ai-server`(FastAPI)에 `POST /api/ai/chat`(SSE) 엔드포인트를 추가한다. nginx(ADR-003 연장)에 SSE용 버퍼링 해제(`proxy_buffering off`)/타임아웃 연장 설정이 추가로 필요하다.

## 12. 프레임워크 결정 — LangChain/LlamaIndex 없이 `google-generativeai` native function calling

Tool 4~5개, 단일 에이전트 규모라 오케스트레이션 프레임워크가 주는 이점(멀티 에이전트, 복잡한 체인)이 거의 없다. 기존 `ai-server`가 이미 같은 SDK를 raw하게 쓰고 있어 일관성을 유지하고, "기술을 결론이 아니라 필요해서 쓴다"는 이 프로젝트의 포트폴리오 서술 원칙과도 맞는다.

## 13. 청킹 전략 — 열린 사항

강의계획서를 주차/섹션 단위로 청킹한다는 방향은 정했지만, **정확한 규칙(고정 크기 vs 구조 기반, 오버랩 크기 등)은 실제 PDF를 받아 구조를 확인한 뒤 확정한다.** 지금 미리 정하면 실제 문서 구조와 안 맞을 위험이 있다 — Stage 1 착수 시 PDF 샘플 몇 개로 파싱 결과를 먼저 확인하고 그때 확정한다.

## 14. 측정 계획 (Before/After, 로드맵 원칙 적용)

새 기능이라 비교 대상이 없는 게 아니라, 실시간 수강신청 때처럼 "가드레일 없는 baseline → 개선 → 재측정" 구조로 수치를 남긴다:

- Tool 선택 정확도(테스트 질문 세트 대비 올바른 Tool+파라미터 호출 비율)
- RAG 검색 hit rate(정답 청크가 top-k 안에 들어오는 비율)
- 할루시네이션 비율(Tool/RAG 근거 없이 답한 비율, 수작업 샘플링)
- E2E p95 latency, Gemini 토큰 비용

테스트 질문 세트와 측정 원본은 `doc/experiment/`에 저장한다.
