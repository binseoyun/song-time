# ADR-008: DLX(Dead Letter Exchange)+TTL 기반 지연 재시도 전환 — 현행 유지, 전환 보류

- 날짜: 2026-08-20
- 상태: 결정됨
- 관련: 이슈 #44, 구현계획 Stage 3-6, 이슈 #62(3-4 DLQ 완전 보상 로직), 카오스 테스트 1-10(이슈 #40)
- 관련 코드: `backend/src/worker.js`, `backend/src/config/rabbitmq.js`

## 상황 (Context)

카오스 테스트 1-10(이슈 #40, 2026-08-18)에서 `worker.js`의 재시도 방식(실패 시 `attempts`를 늘린 메시지를 같은 큐에 **즉시** 재발행)에 실제 백오프가 전혀 없음을 실측으로 확인했다:

- DB 컨테이너가 네트워크에서 완전히 사라진 상태(DNS 조회 실패)에서는 재시도 간격이 우연히 ~4초로 벌어져 5회 소진에 17~20초가 걸림 — 설계된 백오프가 아니라 DNS 재시도의 부수 효과
- 컨테이너가 막 재기동돼 포트만 아직 안 열린 상태(ECONNREFUSED)에서는 5회 소진이 **65~82ms**(2회 재현) 만에 끝남

즉 진짜 백오프가 없어, 수 초~수십 초 지속되는 짧은 장애조차 5번의 재시도 "기회"를 순식간에 다 써버리고 DLQ로 격리된다. 이걸 개선할지 정식으로 검토하는 것이 이 ADR의 목적이다.

## 검토한 대안과 트레이드오프

| 대안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A. 현행 유지 | 즉시 재발행(무백오프) | 이미 구현됨, 추가 작업 없음, 카오스 테스트 1-8/1-9로 재전송·멱등성 계약이 이미 검증됨 | 짧은 장애조차 재시도가 순식간에 소진돼 DLQ로 격리됨 |
| B. 단일 지연 큐(TTL)+DLX 계단식 | delay 큐 1개, 메시지 발행 시 `expiration` 속성을 `attempts`별로 다르게(1s→5s→15s→30s→60s) 설정 | 표준 RabbitMQ 기능만으로 구현 가능(플러그인 불필요), 큐 관리 부담 최소, 기존 메시지 스키마(`attempts` 필드)를 거의 그대로 재사용 가능 | delay 큐+DLX 바인딩 설정 추가, 메시지별 TTL 계산 로직 필요, 기존 멱등성 계약이 새 구조에서도 유지되는지 재확인 필요 |
| C. 시도 단계별 여러 큐 | `attempts`마다 고정 TTL 큐(retry-1s/5s/15s/30s/60s) 5개 + DLX 체인 | 큐별로 "몇 번째 재시도 대기 중인지" 모니터링 가능(가시성) | 큐 5개+바인딩 다중 관리 — 이 프로젝트 규모(1인 개발, 큐 2개로 지금까지 충분) 대비 과함 |
| D. `rabbitmq-delayed-message-exchange` 플러그인 | 헤더에 `x-delay`(ms)만 지정하면 그 시간 뒤 라우팅 | 구현 가장 단순, 가장 유연(임의 지연시간) | **RabbitMQ 공식 이미지에 기본 미포함** — 플러그인 설치(이미지 교체 또는 `rabbitmq-plugins enable`)가 필요한 인프라 변경 수반, 커뮤니티 플러그인이라 B/C 대비 이식성·신뢰도가 낮음 |

## 결정과 이유

**A(현행 유지)를 채택하고, DLX+TTL 전환은 보류한다.**

핵심 근거는 **이 문제가 더 이상 "사용자 피해" 문제가 아니라는 재평가**다. 이슈 #62(Stage 3-4, DLQ 완전 보상 로직)가 함께 진행되면서, 재시도가 전부 실패해 DLQ로 격리되더라도 좌석이 자동으로 반환되는 안전망이 생긴다. 즉 **Ghost Decrement로 인한 사용자 영구 차단(진짜 심각한 피해)은 DLX+TTL 없이도 3-4만으로 이미 막힌다.** DLX+TTL이 추가로 주는 가치는 "사용자 보호"가 아니라 "백오프 없이 너무 빨리 DLQ로 밀려나서, 살릴 수 있었던 요청의 재처리 기회를 놓치는 것을 줄이는 것"(처리 성공률·효율 문제)으로 좁아진다.

이 좁아진 가치 대비 비용(B안 기준으로도 delay 큐 신설 + DLX 바인딩 + TTL 계산 로직 + 기존 멱등성 계약 재검증)은 1인 개발 포트폴리오 프로젝트 규모에서 정당화하기 어렵다고 판단했다. 특히:

1. **실제 장애 발생 확률이 낮다** — 카오스 테스트 1-8/1-9/1-10 전부 "인위적으로 주입한" 장애였고, 자연 조건에서는 1-9(Ghost Decrement)조차 1회 시도에서 미발생했다.
2. **이미 3-4가 최악의 결과(사용자 피해)를 차단한다** — DLX+TTL의 부재로 남는 리스크는 "정상 처리율이 이론상 최적보다 약간 낮다" 정도이지, 서비스 신뢰성 자체를 위협하지 않는다.
3. **Circuit Breaker(3-5)와의 상호작용 복잡도** — DLX+TTL까지 같이 들어가면 "Circuit Breaker가 열려 있는 동안 delay 큐에서 대기 중인 메시지는 어떻게 되는가" 같은 새로운 엣지 케이스가 생긴다. 지금 우선순위가 더 높은 3-4/3-5(이슈 #62)에 집중하기 위해서도 범위를 넓히지 않는 것이 낫다.

## 결과 (정성)

- 코드 변경 없음. `worker.js`/`rabbitmq.js`의 현행 재시도 방식(즉시 재발행, `MAX_ATTEMPTS=5`)을 그대로 유지한다.
- 이슈 #44는 이 ADR로 종결한다.
- **재검토 조건**: 배포 후 실사용 데이터에서 DLQ 격리율이 유의미하게 높거나(예: 짧은 DB 재시작이 실제로 자주 관측됨), 처리 성공률이 목표를 밑도는 것이 확인되면 그때 B안(단일 지연 큐+DLX 계단식)을 다시 검토한다 — "먼저 증명하고 그다음 개선한다"는 이 프로젝트의 기존 원칙(2026-08-18 논의)을 여기서도 그대로 적용한다.
