# ADR-009: DLQ 보상 로직 축소 + Circuit Breaker 보류 — "선증명 후개선" 원칙 재적용

- 날짜: 2026-08-20
- 상태: 결정됨
- 관련: 이슈 #62, 구현계획 Stage 3-4/3-5/3-7, 카오스 테스트 1-9(이슈 #38)/1-10(이슈 #40)

## 상황 (Context)

구현계획 Stage 3(2026-08-19 재분류)는 3-4(DLQ 완전 보상 로직)를 [필수], 3-5(워커 Circuit Breaker)를 [권장]으로 태그해뒀다. 이슈 #62를 착수하기 직전, 실제 구현 범위를 설계하면서 두 가지를 다시 짚어봤다.

**DLQ 보상은 사실 두 개의 서로 다른 실패 경로를 가리킨다:**
- (a) **DLQ 격리**: 메시지가 큐에 들어와 워커가 5회 재시도 후 실패 → DLQ로 격리. 워커가 그 순간에 아는 이벤트라 즉시 대응 가능.
- (b) **Ghost Decrement**: `registerRedisAtomic`의 RabbitMQ 발행 자체가 실패(fire-and-forget) → 메시지가 큐에 아예 안 들어감. 워커는 이 신청의 존재 자체를 모른다 — 아무 이벤트도 안 남아 **주기적 스캔**으로만 탐지 가능.

이 둘 다 "Redis 성공/MySQL 실패 불일치"라는 같은 증상이지만, (a)는 이벤트 기반으로 싸게 닫히고 (b)는 새 인프라(스캔 job)가 필요하다.

## 재평가 — 이 서비스의 실제 성격을 놓고 다시 판단

이 서비스는 실제 학교 수강신청 시스템이 아니라 **연습(practice) 환경**이다. Ghost Decrement가 발생해 한 학생의 연습 세션이 꼬여도, 실제 졸업 요건 과목을 놓치는 게 아니라 다시 연습하면 된다. 원래 [필수] 태그의 근거였던 "실사용자가 영구 차단되는 유일한 피해 시나리오"라는 표현은 실제 수강신청 시스템 기준의 심각도이지, 연습 도구 기준은 아니다.

또한 이 프로젝트가 일관되게 지켜온 **"선증명 후개선"** 원칙(2026-08-18 논의, DLX+TTL 보류 결정에도 이미 적용, ADR-008)을 그대로 다시 적용하면:

- 카오스 테스트 1-9(Ghost Decrement, 이슈 #38)는 **자연 조건에서 1회도 재현되지 않았다** — 발행 직전 인위적 지연 훅을 넣어야만 만들 수 있는 상황이었다.
- 카오스 테스트 1-10(DB 다운, 이슈 #40)도 컨테이너를 직접 죽여야 만들 수 있는 상황이다.
- 즉 두 실패 모드 다 "자연 조건에서 한 번도 관측되지 않은, 게다가 심각도가 낮은 서비스의 문제"다. 지금 미리 인프라를 갖추는 것보다, 실제로 관측되면 그때 대응하는 것이 이 프로젝트의 기존 판단 기준과 일관된다.

**Circuit Breaker의 가치도 좁은 조건에서만 성립한다** — "고부하(다수의 메시지 유입)"와 "DB 장애"가 동시에 발생해야 의미가 있다. 이 서비스는 연습 도구라 상시 고부하 상태가 아니고(부하테스트 시나리오와 실사용 트래픽 패턴은 다르다), 이 조건이 겹치는 순간 처리량이 잠깐 떨어지는 정도는 감내 가능한 실패 모드다.

## 결정과 이유

1. **(a) DLQ 격리 시점 좌석 자동 반환만 구현한다(3-4 축소).** `worker.js`의 DLQ 분기(이미 존재하는 지점)에 `cancelAtomic.lua`와 동일한 Redis 되돌리기 연산을 추가하는 것으로, 비용이 극히 작다(새 인프라 불필요, 기존 함수 재사용). 그리고 이 경로는 유일하게 "지금 아예 복구 수단이 없는" gap이다 — DLQ에 격리된 메시지는 지금 블랙홀이라, 아무리 확률이 낮아도 닫아둘 가치가 있다.
2. **(b) Ghost Decrement 주기적 리컨실리에이션 자동화는 보류한다.** 기존 수동 스크립트(`backend/scripts/reconcileGhostDecrements.js`)가 이미 탐지 용도로 존재하므로, 의심되면 언제든 수동 실행할 수 있다. 자동화(별도 cron 엔드포인트 + 전체 유저 대상 일반화)는 관측된 필요가 생기면 그때 만든다.
3. **Circuit Breaker(3-5)는 보류한다.** "고부하+DB 장애 동시 발생"이라는 좁은 조건에서만 가치가 있고, 연습 도구 특성상 일시적 처리량 저하는 서비스 신뢰성을 위협하지 않는다.
4. **검증(3-7)도 범위가 좁아진다** — Circuit Breaker 검증은 대상이 없어지므로 제외. DLQ 좌석 반환만 카오스 테스트 1-8/1-9와 같은 방식(발행 직전 지연 훅 재사용 또는 워커의 MySQL 반영을 강제로 실패시키는 훅)으로 검증한다.

## 결과 (정성)

- 이슈 #62 범위를 "DLQ 완전 보상 로직 + Circuit Breaker"에서 "DLQ 격리 시점 좌석 자동 반환"으로 축소한다.
- 신규 코드: `backend/src/services/registrationCompensationService.js`(좌석 반환 함수), `worker.js` DLQ 분기에서 호출.
- 단위 테스트: `backend/tests/registrationCompensation.test.js` — 정상 반환, 이중 반환 방지(이미 취소된 경우), 사용자 직접 취소 후 반환 스킵 3가지 케이스.
- **카오스 검증(3-7 축소판, 이슈 #40과 같은 방식)**: 전체 docker-compose 스택에서 `docker compose stop db`로 DB를 인위적으로 내린 뒤, 실제 `/api/registrations/redis` 등록 1건을 실행해 End-to-End로 확인했다.
  - 등록은 Redis만으로 처리되므로 DB가 죽어 있어도 201 성공 응답 확인
  - 워커가 5회 재시도(`attempts=1/5`~`5/5`, worker_1/worker_2가 번갈아 처리, 총 약 23초 — DNS 조회 실패로 재시도 간격이 벌어지는 카오스 테스트 1-10과 동일한 장애 모드) 후 `[worker] DLQ로 격리` 로그 확인
  - 곧바로 `[compensation] DLQ 격리로 인한 좌석 자동 반환` 로그 확인
  - Redis 실측: `class:{classId}:seats`가 반환 전 0 → 반환 후 1(원래 값)로 복구, `user:{userId}:registered`에서 해당 classId 제거 확인
  - DB 재기동 후 테스트 데이터(더미 과목/계정) 정리 완료
- **재검토 조건**: 배포 후 실사용 데이터에서 Ghost Decrement 또는 DLQ 격리가 실제로 관측되면(로그 또는 수동 스크립트 실행 결과), 그때 (b) 자동화와 Circuit Breaker를 다시 검토한다.
