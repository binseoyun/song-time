# ADR-007: 대기열 지속 폴링 부하 대응 — Active 게이트 조정 대신 backend 인스턴스 수평 확장(2→4대)

- 날짜: 2026-08-20
- 상태: 결정됨
- 관련: 이슈 #57(실험 02 Step 3, Valve Tuning), [실험 02 결과 §12~17](../experiment/02-결과.md), [트러블슈팅 07](../troubleshooting/07-대기열-지속-폴링-부하에서-nginx-업스트림-병목.md), [트러블슈팅 08](../troubleshooting/08-validate3k-잔여노이즈-원인-docker-desktop-cpu-캡.md), ADR-006(실시간 수강신청 설계) 1.1~1.4

## 상황 (Context)

Step 3(Valve Tuning) Round 1(`ACTIVE_GATE_LIMIT=300`, `VUS=12,000`)을 nginx 병목 2건([트러블슈팅 07](../troubleshooting/07-대기열-지속-폴링-부하에서-nginx-업스트림-병목.md))과 로컬 Docker Desktop CPU 캡([트러블슈팅 08](../troubleshooting/08-validate3k-잔여노이즈-원인-docker-desktop-cpu-캡.md))까지 다 정리한 뒤 실행했는데도 크게 붕괴했다.

- `http_req_failed` 4.89%, `registration_duration` p95 11.1초(목표 0.5초의 22배)
- `queue_dropout`(TTL 30분 초과 이탈) 4,005명(33.4%)
- `docker stats`로 확인한 원인: VM 전체 CPU는 최대 83%로 여유가 있었는데, `backend_1`/`backend_2`가 각각 110~116%(프로세스당 사실상 천장)에 머물러 있었다. Node 이벤트 루프가 프로세스당 코어 1개 남짓에서 한계를 맞는데, 11,700명이 3~5초 주기로 지속 폴링하는 총량(초당 약 1,100건, 30분 내내)이 이 2개 프로세스의 처리 한계를 넘어선 것으로 판단된다.

즉 이번 붕괴는 "Active 인원을 몇 명으로 둘 것인가"의 문제가 아니라 "대기 중인 사람들의 순번 조회 트래픽을 처리할 backend 용량"의 문제였다.

## 검토한 대안과 트레이드오프

| 대안 | 트레이드오프 |
|---|---|
| **A. Active 게이트 값을 더 낮춘다**(계획서 원안: 불만족 시 -1,000명 단위 조정) | 이미 300으로 "-1,000명 단위" 규칙이 기계적으로 적용 불가능한 값이다. 근본 원인이 Active 크기가 아니라 폴링 총량을 받아낼 처리 용량이라는 게 실측(CPU 프로파일)으로 확인됐으므로, Active를 낮춰도 폴링 트래픽 자체(대기 인원 수는 항상 11,700명 안팎으로 거의 안 바뀜)는 줄지 않는다. 문제의 원인을 다루지 못하는 대안 |
| **B. 폴링 주기(3~5초)를 늘린다** | 폴링 요청 총량을 직접 줄이는 가장 확실한 레버이긴 하다. 하지만 이 값은 실제 프론트엔드(`RegistrationPractice.tsx`)의 폴링 주기와 통제변수로 반드시 일치시켜야 하는 값(ADR-006 1.4, 실험계획서 02 §5) — 부하테스트에서만 늘리면 더 이상 실제 서비스 조건을 대표하지 못한다. 실제로 늘리려면 "학생이 순번 갱신을 덜 자주 본다"는 UX 트레이드오프를 동반하는 제품 결정이 되어, 인프라 튜닝 범위를 벗어난다 |
| **C. 지금 바로 K8s(HPA/Ingress)로 전환해 처리** | K8s의 Deployment replica + HPA가 구조적으로 이 문제(수평 확장)에 맞는 도구인 건 맞지만, `doc/portfolio-roadmap.md`가 정한 Phase 순서(Phase 2 동시성 완료 후 Phase 3 K8s 운영화, `CLAUDE.md`에 "앞 Phase를 건너뛰고 뒤 Phase를 진행하지 않는다"고 명시)를 어기게 된다. 또한 docker-compose→K8s 전환은 네트워크 스택·로드밸런싱 방식·리소스 격리 방식이 한꺼번에 바뀌어, "인스턴스를 늘려서 좋아진 것"과 "K8s 자체 특성 때문에 좋아진 것"을 분리할 수 없어 지금 검증하려는 가설(프로세스당 CPU 천장)이 오염된다 |
| **D. backend 인스턴스를 2→4대로 수평 확장(docker-compose 내에서)** | 트러블슈팅 05가 이미 확립한 패턴(backend_1/backend_2 이중화)의 자연스러운 연장이라 리스크가 작다. 바뀌는 변수가 "인스턴스 개수" 하나뿐이라 가설을 가장 깨끗하게 검증할 수 있다. DB 커넥션 풀(`backend/src/config/database.js`의 `pool.max=5`) 기준으로 4개 인스턴스+워커 2개=6프로세스×5=30개 커넥션이라 MySQL 기본 `max_connections`(151) 대비 여유가 충분해 부작용이 사실상 없다 |

## 결정과 이유

**D안(backend 인스턴스 2→4대 수평 확장)을 채택한다.** Active 게이트 크기 조정(A)은 원인을 다루지 못하고, 폴링 주기 조정(B)은 제품 결정이 얽혀 있어 이번 범위 밖이며, K8s 전환(C)은 로드맵 Phase 순서를 어기고 실험을 오염시킨다. D안만이 "지금 이 붕괴의 원인이 정말 backend 처리 용량인가"를 다른 변수 없이 직접 검증할 수 있었다.

`docker-compose.yml`에 `backend_3`/`backend_4`를 `backend_2`와 동일한 구성으로 추가하고(`seedData.js`는 여전히 `backend_1`만 실행 — findOrCreate 기반이라 동시 실행 시 레이스 위험), `nginx/default.conf`의 `upstream backend_pool`에 두 서버를 추가했다.

## 결과 (정량)

Round 1(backend 2대) → Round 1b(backend 4대), 동일 조건(`ACTIVE_GATE_LIMIT=300`, `VUS=12,000`)에서 재실행:

| 지표 | Round 1 (2대) | Round 1b (4대) |
|---|---|---|
| 총 소요시간 | 30분 56초 | 23분 46초(-23%) |
| `http_req_failed` | 4.89% | **0.06%**(목표 0.1% 미만 달성) |
| `registration_success` | 7,090명(59.1%) | 11,935명(99.5%) |
| `queue_dropout` | 4,005명(33.4%) | **0명** |
| `registration_duration` p95 | 11.1초 | 4.4초(2.5배 개선) |
| 부하 시점 VM CPU 합계 최댓값 | 667%/800%(83%) | 684%/800%(85%) |

가설이 확인됐다 — 인스턴스를 늘린 만큼 처리 용량이 정확히 늘어 TTL 이탈이 완전히 사라지고 전체 에러율도 목표 안으로 들어왔다. 다만 backend 4대 상태에서 VM CPU 여유가 15%로 줄어, 로컬 Docker Desktop 환경에서 추가 확장은 물리적 한계에 가깝다고 판단해 여기서 멈췄다(§ 실험 02 결과 §15). 그 결과 등록 API p95(4.4초)는 목표(500ms)에 못 미친 상태로 실험을 마쳤다 — **이 잔여 격차는 정직하게 미달로 기록하고, 완전한 달성은 Phase 3(K8s 운영화, HPA 기반 동적 확장)로 명시적으로 이월한다.**

`N*`(Active 게이트 최종 인원)은 300으로 유지한다 — Round 1/1b 모두 붕괴·개선의 원인이 Active 크기가 아니라 backend 처리 용량이었다는 게 실측으로 확인됐으므로, Active 값을 조정할 근거가 없었다.
