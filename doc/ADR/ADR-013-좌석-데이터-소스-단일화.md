# ADR-013: 좌석 데이터 소스 단일화 — 챗봇/개설과목 API가 실시간 좌석(Redis)을 진실로 삼는다

- 날짜: 2026-08-27
- 상태: 결정됨
- 관련: 이슈 #86, [ADR-010](ADR-010-AI-에이전트-챗봇-설계.md) §8, [ADR-006](ADR-006-실시간-수강신청-설계.md), [구현계획](../AI-에이전트-구현계획.md) Stage 3-1, [실험 03 프롬프트개선](../experiment/03-프롬프트개선-before-after.md)

## 상황 (Context)

실사용 중 AI 챗봇이 "잔여석"을 잘못 답하는 것이 발견됐다.

- "독일어Ⅰ 자리 있어?" → 챗봇 "자리 없습니다(잔여석 0)". **실제로는 40석 전부 비어 있음.**
- "데이터베이스 관련 수업 잔여석" 등 잔여석을 묻는 질의 전반이 실제 값과 무관한 숫자를 답함.

### 근본 원인 — 이 앱에는 "수강 인원"을 뜻하는 값이 3개 있고 서로 다른 저장소에 산다

| 개념 | 저장소 | 갱신 주체 | 챗봇이 쓰던 값 |
|---|---|---|---|
| 실시간 잔여석 | Redis `class:{id}:seats` | Group C 원자 연산(등록/취소) | ❌ 안 씀 |
| 관심 등록(하트) 수 | MySQL `course_interests` 테이블 행 수 | `POST /api/courses/:id/interest` | ❌ 안 씀 |
| 데모용 수강 현황 | MySQL `Class.enrolled` | 시드값(하드코딩) + 하트 토글이 `+1/−1` | ✅ `capacity - enrolled`로 잔여석 계산 |
| (실험용) Group A/B 카운터 | MySQL `Class.remainingSeats` | naive/pessimistic 경로만 `decrement` | — (응답엔 있으나 stale) |

챗봇 `chat/tools.py`의 `_remaining_seats()`가 `capacity - enrolled`로 잔여석을 계산했다. `enrolled`는:

1. `seedData.js`에서 **가짜 초기 수강 인원**으로 하드코딩됨(44, 50, 88, …)
2. 그 위에 `courseController.toggleInterest`가 하트마다 `Class.increment('enrolled')` / `decrement`

→ `enrolled` = **데모용 가짜 수강생 + 하트 delta**. 어느 질문에도 깨끗하게 대응하지 않는 하이브리드 값이고, Group C(실시간 수강신청 연습)의 등록/취소는 이 값을 **전혀 건드리지 않는다**(코드 주석에 명시). Group C 좌석의 유일한 진실은 Redis `class:{id}:seats`다.

`Class.remainingSeats`(MySQL 컬럼)도 `/api/courses` 응답에 있지만 Group C 경로에서 갱신되지 않아 마찬가지로 stale하다(실측: 알고리즘 21000549-1 → MySQL 90, Redis 89).

### 챗봇이 호출하는 API가 실시간 좌석을 응답에 안 준다

`GET /api/courses`, `GET /api/courses/:code`(ADR-010 §8 Tool 대상)는 `Class` 테이블만 반환한다. 프론트 "실시간 수강신청 연습" 탭은 별도로 `GET /api/registrations/redis/seats`를 폴링해 여석을 표시하지만(이슈 #54), 챗봇은 그 경로를 안 쓴다.

## 검토한 대안과 트레이드오프

### 좌석 데이터를 챗봇에 전달하는 방법

| 대안 | 방법 | 트레이드오프 |
|---|---|---|
| A. `/api/courses` 응답에 실시간 좌석을 실어준다 | `courseController`가 Redis `class:{id}:seats`를 읽어 응답에 병합 | 공개 API 계약 변경(필드 추가·의미 변경). Node↔Redis는 이미 연결돼 있음. 챗봇·프론트 개설과목 표시 모두 한 소스로 정리됨 |
| B. 공개 엔드포인트 신설 `GET /api/courses/seats?classIds=` | 무인증 조회 엔드포인트 추가, 챗봇이 2차 호출로 병합 | 기존 엔드포인트 안 건드림. 챗봇 Tool이 매 검색마다 요청 2회. 좌석 표시 로직이 또 하나 생김 |
| C. 챗봇이 `/api/registrations/redis/seats`를 서비스 토큰으로 호출 | 기존 엔드포인트 재사용 | "Tool은 공개 데이터만"(ADR-010 §8) 원칙 깨짐. 인증 배관 필요 |

**A 채택.** 챗봇이 쓰는 공개 과목 API가 좌석에 대해 진실을 말하지 않는 것 자체가 문제다. Node는 이미 Group C용 ioredis 클라이언트를 갖고 있어 추가 인프라가 없다.

### 응답 필드 이름·형태

`/api/courses` 응답엔 이미 `remainingSeats`(MySQL 컬럼값, Group A/B 카운터)가 있다.

| 대안 | 방법 | 트레이드오프 |
|---|---|---|
| 1-a | 기존 `remainingSeats`를 컨트롤러에서 Redis 값으로 덮어씀 | 새 필드 불필요. "MySQL 컬럼"이라는 기존 의미와 겹쳐 코드 읽는 사람 혼란 |
| **1-b** | 응답의 `remainingSeats` = Redis 값으로 의미 통일, MySQL 컬럼값은 응답에서 제거 | 이름이 의미와 일치. MySQL 컬럼은 naive/pessimistic 서비스 내부용으로 격리. `remainingSeats`를 읽는 프론트 코드는 없음(확인 완료) |
| 1-c | 새 키(`liveRemainingSeats`) 추가하고 stale한 `remainingSeats`도 유지 | 계약 하위호환이지만 stale 필드가 계속 노출돼 오용 위험 |

**1-b 채택.** `remainingSeats`(응답) = "실시간 잔여석" 하나의 의미만 남긴다.

### `enrolled`(데모용 수강 현황)을 챗봇이 다룰 범위

| 대안 | 챗봇 동작 | 트레이드오프 |
|---|---|---|
| **2-a** | 챗봇 Tool 출력에서 `enrolled` 제거. 챗봇은 실시간 잔여석·실시간 신청자 수·관심 등록 수만 답 | "수업 목록" 탭은 여전히 `enrolled/capacity`로 "정원 초과" 표시 → 화면과 챗봇이 다른 값을 말하는 불일치가 남음. 단, 이는 화면 쪽 표시 문제로 별도 이슈 |
| 2-b | 2-a + "수업 목록" 탭도 실시간 좌석 기준으로 표시하도록 수정, `toggleInterest`의 하트 `enrolled` 증감 제거 | 범위가 커짐. 하트 증감 로직·시드 데이터·프론트 진행바까지 정리 필요 |
| 2-c | 챗봇이 `enrolled`도 "수업 목록 화면 기준 수강 현황"으로 별도 필드로 답 | 하이브리드 가짜 값을 사실처럼 답하게 됨 |

**2-a 채택.** 이번 이슈는 "챗봇이 잘못된 좌석을 답한다 + API가 실시간 좌석을 안 준다"에 집중한다. "수업 목록" 탭 표시 정리(2-b)는 별도 이슈로 분리한다.

### 관심 등록(하트) 수의 소스

`Class.enrolled`는 시드값이 섞여 순수 하트 수가 아니다. 순수 하트 수는 `course_interests` 테이블 행 수다.

- 목록(`/api/courses`): `course_interests`를 `class_id`로 `GROUP BY COUNT` 1회 → 응답 각 과목에 `interestCount` 주입
- 단건(`/api/courses/:code`): 해당 `class_id`로 `COUNT` 1회

### Redis에 좌석 키가 없는 과목 (3-a 채택)

과목이 나중에 추가되면 `class:{id}:seats` 키가 없을 수 있다.

- **3-a**: `remainingSeats: null` 반환. 챗봇은 "실시간 좌석 정보를 확인할 수 없습니다"로 답하고 신청자 수도 계산하지 않음 — 없는 데이터를 지어내지 않는다.
- 3-b(`capacity`로 폴백): "전부 비어있음"으로 오인됨 → 기각.

### API가 Redis를 읽는 방식 (4-a 채택)

- 목록: `MGET class:{id}:seats …`(과목 수만큼 키, 1회 왕복). 단건: `GET` 1회.
- **Redis 장애 시 좌석 필드만 `null`로 두고 200 응답** — 과목 메타데이터 조회까지 막지 않는다(500 금지).
- 별도 캐싱 레이어는 두지 않음(오버엔지니어링).

## 결정과 이유

**`GET /api/courses`·`GET /api/courses/:code` 응답이 실시간 좌석(Redis)과 관심 등록 수(course_interests)를 진실로 삼는다. 챗봇 Tool은 이 값에서 3개 숫자를 분리해 답한다.**

### API 응답 변경 (`courseController`)

각 과목 객체에:

- `remainingSeats`: Redis `class:{id}:seats` 값(정수) 또는 `null`. **의미 변경** — 기존 MySQL 컬럼값에서 실시간 좌석으로.
- `interestCount`: `course_interests` 행 수(정수).
- `enrolled`, `capacity`, `demandStatus` 등 나머지 필드는 유지(프론트 "수업 목록" 탭이 사용).
- MySQL `Class.remainingSeats` 컬럼값은 응답에서 제거(직렬화 시 override). 컬럼 자체와 naive/pessimistic 서비스 로직은 유지.

### 챗봇 Tool 출력 변경 (`chat/tools.py` `_summarize`)

`enrolled` 키 제거. 대신:

| 키 | 값 | 답하는 질문 |
|---|---|---|
| `capacity` | 정원 | "정원 몇 명이야?" |
| `remaining_seats` | `remainingSeats`(Redis) 또는 `null` | "자리 남았어?" |
| `registered_count` | `capacity - remainingSeats` (Redis 값 있을 때만, `null` 가능) | "몇 명 신청했어?" |
| `interest_count` | `interestCount` | "좋아요 몇 개야? / 인기 많아?" |

`search_courses`/`get_course_by_code` docstring과 시스템 프롬프트에 "실시간 신청자 수와 관심 등록 수는 다른 값이다"를 명시한다.

## 결과 (정량·정성)

`gemini-3.1-flash-lite`, 74문항 × 5회, 같은 하네스. 상세: [실험 03 §8](../experiment/03-프롬프트개선-before-after.md).

| 지표 | Before | After |
|---|---|---|
| 답변 포함 검사 | 73.7% (70/95) | **100%** |
| 답변 제외 검사 | 80.0% (20/25) | **100%** |
| Tool 선택 정확도 | 98.7% | **100%** |
| 과소 호출률 | 1.5% (5/330) | **0%** |
| 전 rep 통과 | 72/73 | **73/73** |
| 1,000 turn 비용 | $0.47 | $0.55 (+17%) |

- **오차 규모(Before)**: 85개 실과목 전부 `capacity - enrolled` ≠ 실시간 잔여석, 평균 절대 오차 48.6석, 84/85가 "실제보다 빡빡하게"(마감 오답 위험).
- **Before 실패 6개 시나리오**(전부 5/5 rep): `seats-02`(독일어Ⅰ "0석/신청 불가" → 실제 15) `seats-05`(9→60) `seats-07`(14→23) `seats-09`(3→17) `seats-11`(신청자 수를 `enrolled`로 답) `seats-12`(관심 등록 수 질문 자체를 거부).
- **회귀 1건**: `multiturn-06` 2턴 tool 선택이 `search_courses` 재검색 → 1턴 결과 코드로 `get_course_by_code`로 이동. 답변 정확, 두 경로 다 유효 → 라벨 `any`로 완화.
- **벤치마크**: 72 → 74(`seats-11`/`seats-12` = 신청자 수 vs 관심 등록 수 분리 검증). 결정적 좌석 픽스처 `backend/scripts/seedBenchmarkSeats.js` 추가.
- 정성: 챗봇이 "실시간 수강신청 잔여석"·"실시간 신청자 수"·"관심 등록 수"를 서로 다른 소스에서 분리해 답한다. `enrolled`(데모 하이브리드 값)를 사실처럼 노출하지 않는다.

### 남은 일 (이 ADR 범위 밖)

- "수업 목록" 탭이 `enrolled/capacity`로 "정원 초과"를 표시하는 것 → 실시간 좌석 기준으로 정리(별도 이슈, 2-b).

## 재검토 — 관심 등록 수 소스 (2026-08-27, 이슈 #93)

**정정: `interest_count`(챗봇)의 소스를 `course_interests` `COUNT` → `Class.enrolled`로 되돌린다.**

이 ADR은 `Class.enrolled`를 "시드 가짜 수강생 + 하트 delta가 섞인 하이브리드"로 보고 순수 하트 수를 얻으려 `course_interests` 행 수를 별도로 셌다. 그러나:

- `Class.enrolled`는 이 앱의 **정식 관심 등록 수 카운터**다 — `courseController.toggleInterest`가 `+1/−1`로 즉시 유지하고, `demandController.aggregateDemand`(수요 체커 CronJob, 매분)가 `CourseInterest.count()` 실측으로 재조정하며, `demandStatus`(NORMAL/NEAR/FULL)도 이 값 기준으로 계산한다.
- **수업 목록 UI가 표시하는 "n / M명"의 n이 바로 `enrolled`다.** 챗봇이 `course_interests` COUNT를 쓰면 UI와 다른 숫자를 답한다(로컬은 시드값이 재조정 안 돼 더 크게 벌어짐 — "화면 75명, 챗봇 0명").
- 시드값이 임의값인 건 맞지만, 그건 재시딩(Stage 1)에서 정리할 문제이고 `enrolled` = "관심 등록 수"라는 의미 자체는 설계대로다.

변경: `chat/tools.py` `_summarize`의 `interest_count` 소스를 `enrolled`로, `courseController`의 `course_interests` `GROUP BY COUNT`(응답 `interestCount` 필드)는 제거. `remaining_seats`/`registered_count`(Redis 실시간 좌석 기준)는 이 ADR 그대로 유지 — 그게 원래 버그의 핵심이었다.

수업 목록 UI에 "실시간 신청자 수"를 추가하는 건 이번에도 보류(별도 논의).
