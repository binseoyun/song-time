# ADR-011: CronHPA + HPA 병행 확장 — 스케줄은 `minReplicas`만 조정한다

- 날짜: 2026-08-24
- 상태: 결정됨 (일부 파라미터는 Phase 3 실측 후 확정)
- 관련: 이슈 #72, [ADR-006 §4.1](ADR-006-실시간-수강신청-설계.md), [ADR-007](ADR-007-대기열-부하-backend-인스턴스-수평-확장.md), [실험 02 결과](../experiment/02-결과.md) §12~17, 구현계획 3-2, 로드맵 P12, 이슈 #61

## 상황 (Context)

### 발단 — 문서 간 표기가 어긋나 있었다

[ADR-006 §4.1](ADR-006-실시간-수강신청-설계.md)은 설계 시점에 일반 HPA(반응형 확장)를 **명시적으로 기각**하고 **CronHPA(예측형 사전 확장)**를 채택했다. 근거는 "지표 수집과 새 파드 기동에 최소 1~2분이 걸려, 오전 9시 정각의 트래픽 폭증에는 이미 늦다"였다.

그런데 이후 작성된 문서들은 이 결정을 반영하지 않고 "HPA 기반 동적 확장"으로만 적었다 — ADR-006 §1.5 최종 확정(153행), ADR-007(45행), 실험 02 결과(204/210/216행), `portfolio-roadmap.md`(35행), 이슈 #61 제목. `CronHPA`라는 단어는 ADR-006 §4.1과 구현계획 3-2에만 남아 있었다.

**결정이 뒤집힌 적은 없다.** 실험 02를 쓰던 시점에 ADR-006 §4.1을 다시 열지 않고 "K8s 오토스케일링 = HPA"로 관성적으로 적은 표기 오류다. 이 ADR이 그 표기를 정정하는 근거 문서가 된다.

> 이 어긋남 자체가 남길 가치가 있는 기록이다. ADR을 써두는 것만으로는 부족하고, **후속 문서를 쓸 때 관련 ADR을 다시 여는 습관**이 없으면 결정은 조용히 유실된다. Stage 1에서 "좌석 수를 여러 곳에 중복 관리하면 어긋난다"(P1, TOCTOU)를 배웠는데, 같은 일이 문서 계층에서 반복된 셈이다.

### 표기 정정에서 멈추지 않은 이유

정정하려고 ADR-006 §4.1을 다시 읽으면서, 원래 결정("CronHPA 단독")이 실제로 최선인지가 다시 문제가 됐다. CronHPA는 정해진 시각의 폭증은 막지만, **예상을 벗어난 트래픽**(오픈 시각 변경, 공지 지연, 재수강 신청 폭주 등)에는 대응 수단이 없다. 반대로 HPA 단독은 ADR-006이 지적한 대로 정각 폭증에 늦는다.

둘은 배타적이지 않다. 구현계획 3-2도 이미 *"resource requests/limits+HPA(Phase 3 나머지)가 먼저 확정돼야 의미가 생긴다. 그때 통합해서 진행"*이라고 적어, 병행을 염두에 둔 흔적이 있었다. 이 ADR에서 그 "통합"의 구체적 형태를 확정한다.

## 검토한 대안과 트레이드오프

### (1) 병행 방식 — 두 컨트롤러를 각각 걸 것인가

| 대안 | 트레이드오프 |
|---|---|
| **A. CronHPA와 HPA를 같은 Deployment에 각각 건다** | 설정이 직관적이다("스케줄러 하나, 오토스케일러 하나"). 그러나 HPA는 Deployment의 `spec.replicas`를 직접 쓰고, Deployment를 직접 스케일하는 계열의 CronHPA 컨트롤러도 같은 필드를 쓴다 — **두 컨트롤러가 번갈아 값을 덮어써 파드 수가 진동한다.** 사전 확장으로 파드를 늘려놨는데 다음 HPA 주기에 CPU 지표가 아직 안 올라와 곧바로 축소되는, **정확히 막으려던 상황**이 발생한다 |
| **B. 스케줄은 HPA의 `minReplicas`만 조정하고, `replicas` 기록자는 HPA 하나로 유지한다** | 설정이 한 겹 간접적이다(스케줄러가 Deployment가 아니라 HPA 오브젝트를 건드린다). 대신 쓰기 주체가 하나뿐이라 충돌이 **구조적으로** 불가능하다. HPA의 계산식이 `clamp(계산값, minReplicas, maxReplicas)`이므로, `minReplicas`를 올리는 것만으로 즉시 사전 확장이 되고 그 위에서 반응형 확장도 그대로 동작한다 |

### (2) 구현 도구

| 대안 | 트레이드오프 |
|---|---|
| **C. CronJob + `kubectl patch`** | 스케줄 시각에 HPA 오브젝트의 `minReplicas`만 patch한다. 새 컨트롤러·CRD가 필요 없고, 이 저장소엔 이미 CronJob 운영 선례(`K8s/50-cronjob-checker.yaml`)와 서비스 계정 이슈 경험(로드맵 P9)이 있다. 단점: 스케줄 로직이 셸 명령으로 흩어지고, RBAC(HPA patch 권한)를 직접 설계해야 한다 |
| D. KEDA | `ScaledObject` 하나에 `cron` trigger와 CPU trigger를 함께 선언하고 여러 trigger 중 최댓값을 취한다. KEDA가 내부 HPA를 직접 생성·관리하므로 (1)의 충돌 문제가 애초에 발생하지 않는다 — "스케줄 + 반응형 병행"을 표현하는 가장 정석적인 도구다. 단점: 클러스터에 컨트롤러와 CRD가 추가되고, 이 프로젝트가 아직 겪지 않은 운영 부담(버전 업그레이드, 장애 시 스케일링 전면 중단)이 생긴다 |
| E. Deployment 직접 스케일형 CronHPA 컨트롤러 | ADR-006 §4.1이 "CronHPA"로 지칭한 계열. HPA와 병행할 때 (1)-A의 충돌을 별도로 회피해야 해서, 병행을 전제하면 이점이 사라진다 |

## 결정과 이유

1. **병행 구조를 채택한다 — ADR-006 §4.1의 CronHPA 결정을 폐기하는 게 아니라 확장한다.** 사전 확장은 여전히 이 도메인의 1순위 수단이고(트래픽 시각이 예정되어 있다), HPA는 그 예측을 벗어난 초과분을 흡수하는 안전망으로 얹는다.

2. **(1)-B를 채택한다: 스케줄은 `minReplicas`만 조정하고, `replicas`를 쓰는 주체는 HPA 하나로 유지한다.** A안의 진동은 튜닝으로 완화할 수 있는 종류가 아니라 "쓰기 주체가 둘"이라는 구조에서 나오는 문제다. 이 프로젝트가 Stage 1에서 얻은 교훈(상태를 여러 곳에서 관리하면 어긋난다)과 같은 판단이다.

   동작 예시:
   ```
   08:50  minReplicas 2 → 20 patch   HPA가 즉시 20개로 확장          (예측형 사전 확장)
   09:00  트래픽 폭증                 예측 초과분은 HPA가 CPU 기준 추가 확장  (반응형)
   10:00  minReplicas 20 → 2 patch   HPA가 stabilization window를 거쳐 축소
   ```

3. **(2)-C(CronJob + `kubectl patch`)를 채택한다.** [ADR-009](ADR-009-DLQ-보상-Circuit-Breaker-범위-재평가.md)에서 Circuit Breaker를 보류한 것과 같은 기준이다 — 이 프로젝트 규모에서 컨트롤러 하나를 새로 들이는 비용이 얻는 것보다 크다. KEDA가 더 정석적인 도구인 것은 맞으므로, **아래 재검토 조건에 걸어둔다.**

4. **표기를 정정한다.** "HPA 기반 동적 확장"으로만 적힌 5개 위치를 이 ADR 참조로 바꾸고, 어긋난 경위를 남긴다.

## 결과

### 정성

- ADR-006 §4.1의 결정이 문서 전체에서 일관되게 추적 가능해진다.
- Phase 3 착수 시 "무엇을 만들지"가 아니라 "어떤 파라미터를 실측할지"만 남는다.

### 이 ADR이 닫지 못한 것 (Phase 3 실측 후 확정)

의도적으로 열어둔다. 지금 정하면 근거 없는 숫자가 된다.

| 항목 | 왜 지금 못 정하는가 |
|---|---|
| `resources.requests/limits` | `K8s/30-backend.yaml:21`이 `replicas: 2 # 부하 분산을 위해 2개 실행`이고 backend에 `resources:` 블록 자체가 없다(로드맵 P12). 다만 출발점은 있다 — 실험 02 §13에서 **Node 프로세스당 CPU 110~116%(코어 1개 남짓)가 천장**임을 실측했다 |
| HPA 임계값 / `maxReplicas` | requests가 정해져야 "CPU 몇 %"가 의미를 갖는다 |
| 스케줄 시각(사전 확장 리드타임) | 파드가 Ready가 되기까지 걸리는 시간을 재야 정할 수 있고, 이는 Probe 재설계(Phase 3)와 맞물린다 |
| Redis/RabbitMQ 커넥션 풀 사이징 | 구현계획 3-3 — `maxReplicas`가 정해져야 총 커넥션 상한을 역산할 수 있다 |

### 검증 환경에 대한 한계 인식

로컬 kind는 Docker Desktop VM(8 vCPU) 위에 있어, 파드를 늘려도 실험 02에서 이미 부딪힌 물리 한계(VM 여유 15%)를 그대로 만난다. 이 병행 구조가 **실제로 p95 500ms를 달성하는지는 로컬에서 검증할 수 없다** — 로드맵이 2026-08-19에 "실제 AWS 환경에 K8s로 배포하는 것으로 스코프를 확정"한 이유가 이것이고, 최종 검증은 거기서 이뤄진다. 로컬에서 확인 가능한 것은 "스케줄 patch가 실제로 `minReplicas`를 바꾸고 파드가 진동 없이 늘어나는가"라는 **메커니즘의 동작 여부**까지다.

### 재검토 조건

- 스케줄 조건이 늘어나(학기별 오픈 시각, 학년별 분산 신청 등) CronJob 셸 로직이 감당하기 어려워지면 → KEDA(D안) 재검토
- 사전 확장 리드타임 안에 파드가 Ready가 되지 못하는 것이 관측되면 → Probe 재설계 및 이미지 기동 시간 최적화를 선행 과제로 승격
