# ADR-005: 회원 탈퇴 기능 추가 — 하드 삭제 + enrolled 카운터 정합성 처리

- 날짜: 2026-08-04
- 상태: 승인됨
- 관련: `backend/src/controllers/authController.js`, `backend/src/routes/authRoutes.js`, `frontend/Course Registration Platform/src/App.tsx`, `frontend/Course Registration Platform/src/components/MyPage.tsx`, `K8s/30-backend.yaml`, `K8s/40-frontend.yaml`

## 상황 (Context)

회원 탈퇴 기능이 아예 없었다. `Users` 테이블에서 계정 행을 지우는 것 자체는 단순해 보이지만, 실제로는 (1) 탈퇴 시 남은 개인 데이터(저장된 시간표, 관심 과목)를 어떻게 처리할지, (2) 그 데이터가 다른 테이블의 정합성(예: 과목의 `enrolled` 카운터)에 미치는 영향까지 같이 설계해야 하는 문제였다.

## 검토한 대안과 트레이드오프

### 1안: 소프트 삭제 (`deletedAt` 컬럼, 논리적 삭제) — 기각
- 장점: 실수 복구, 유예기간 후 재가입 등 지원 가능
- 단점: 모든 조회 쿼리에서 삭제된 유저를 걸러내야 함(빠뜨리면 버그). `studentId`의 `unique: true` 제약과 충돌 — 탈퇴한 학번으로 동일 인물이 재가입하려 해도 그 값이 여전히 "사용 중"으로 막혀버림. 이 프로젝트엔 법적으로 데이터를 보관해야 할 이유(전자상거래 기록 등)가 없어서, 이 복잡도를 감수할 이유가 없다.

### 2안: 하드 삭제 (`DELETE`, 물리적 삭제) — 채택
- 장점: 개인정보보호법의 "즉시파기" 원칙에 부합, 구현이 단순, 탈퇴 후 같은 학번으로 재가입도 자연스럽게 가능(UNIQUE 제약에 걸릴 값 자체가 사라지므로)
- 단점: 되돌릴 수 없음 → 그래서 실행 전 본인확인(비밀번호 재확인)을 반드시 거치게 설계

**결정: 2안(하드 삭제).** 커머스/금융 앱처럼 법정 보관 의무가 없는 수강신청 서비스이므로, "탈퇴하면 즉시 완전히 지운다"는 단순하고 정직한 방식이 더 적합하다.

## 삭제 범위 확인: 무엇이 같이 지워지는가

구현에 앞서 `Users`를 참조하는 외래키를 실제 DB에서 확인했다.

```sql
SELECT TABLE_NAME, CONSTRAINT_NAME, DELETE_RULE
FROM information_schema.REFERENTIAL_CONSTRAINTS
WHERE REFERENCED_TABLE_NAME = 'Users';
```

```
course_interests.user_id → Users.id  (ON DELETE CASCADE)
timetables.user_id       → Users.id  (ON DELETE CASCADE)
```

둘 다 이미 `CASCADE`로 걸려 있어서, `Users` 행 하나를 지우면 그 사람의 관심 과목·저장된 시간표는 DB가 알아서 같이 지운다. 여기까지는 추가 코드가 필요 없었다.

## 발견한 함정: CASCADE는 `enrolled` 카운터를 모른다

`courseController.js`의 `toggleInterest`는 관심 과목을 등록/해제할 때 `Class.enrolled`를 `increment`/`decrement`로 같이 관리한다:

```js
// backend/src/controllers/courseController.js (기존 코드)
await course.decrement('enrolled', { by: 1, transaction: t, lock: t.LOCK.UPDATE });  // 관심 취소 시
await course.increment('enrolled', { by: 1, transaction: t, lock: t.LOCK.UPDATE });  // 관심 등록 시
```

문제는 `ON DELETE CASCADE`가 **DB 레벨에서** 일어난다는 점이다. `Users` 행을 지우면 `course_interests` 행도 같이 지워지지만, 이건 이 컨트롤러 코드를 전혀 거치지 않는다. 그래서 순진하게 `user.destroy()`만 호출하면, 그 유저가 관심 등록해뒀던 과목들의 `enrolled`는 감소되지 않고 그대로 남는다 — 탈퇴한 유저의 "유령 관심"이 카운터에 계속 잡히는 데이터 정합성 버그가 생긴다. (`portfolio-roadmap.md`의 P1 "enrolled 카운터 정합성 문제"와 같은 계열의 이슈다.)

## 구현

### 백엔드: `authController.js`

```js
exports.deleteAccount = async (req, res) => {
    try {
        const userId = req.user?.id;
        const { password } = req.body;

        if (!userId) return res.status(401).json({ message: '인증이 필요합니다.' });
        if (!password) return res.status(400).json({ message: '비밀번호를 입력해주세요.' });

        const user = await User.findByPk(userId);
        if (!user) return res.status(404).json({ message: '사용자 정보를 찾을 수 없습니다.' });

        const isMatch = await bcrypt.compare(password, user.password);
        if (!isMatch) return res.status(400).json({ message: '비밀번호가 올바르지 않습니다.' });

        await sequelize.transaction(async (t) => {
            // 탈퇴 전, 이 유저가 관심 등록해둔 과목들의 enrolled 카운터를 먼저 되돌려놓는다.
            const interests = await CourseInterest.findAll({
                where: { user_id: userId },
                transaction: t,
                lock: t.LOCK.UPDATE,
            });

            for (const interest of interests) {
                await Class.decrement('enrolled', {
                    by: 1,
                    where: { id: interest.class_id },
                    transaction: t,
                    lock: t.LOCK.UPDATE,
                });
            }

            // Users 행 삭제 — course_interests, timetables는 ON DELETE CASCADE로 함께 정리됨
            await user.destroy({ transaction: t });
        });

        res.status(200).json({ message: '회원 탈퇴가 완료되었습니다.' });
    } catch (error) {
        console.error('회원 탈퇴 오류:', error);
        res.status(500).json({ message: '서버 오류가 발생했습니다.' });
    }
};
```

- **본인확인은 이미 로그인된 상태여도 현재 비밀번호를 다시 요구한다.** JWT로 이미 인증된 요청이지만, 되돌릴 수 없는 파괴적 작업이라 세션 탈취 등에 대비해 한 번 더 확인하는 관례를 따랐다(많은 서비스가 계정 삭제·이메일 변경 같은 민감한 작업 전에 비밀번호 재확인을 요구).
- `enrolled` 감소 → `user.destroy()`(CASCADE로 나머지 정리)를 **하나의 트랜잭션**으로 묶었다. 카운터만 줄이고 유저 삭제가 실패하는 상황(혹은 그 반대)이 생기지 않도록.
- `toggleInterest`와 동일하게 `lock: t.LOCK.UPDATE`로 행을 잠가서, 동시에 같은 과목에 대한 관심 등록/해제가 일어나도 카운터가 어긋나지 않게 했다.

```js
// backend/src/routes/authRoutes.js
router.delete('/account', authMiddleware, authController.deleteAccount);
```

### 프론트엔드: `App.tsx`, `MyPage.tsx`

- `App.tsx`: `handleDeleteAccount(password)` 추가 — `DELETE /api/auth/account`를 `Authorization` 헤더+`password` 바디로 호출, 성공 시 `handleLogout`과 동일하게 토큰/상태 정리 후 로그인 화면으로 전환
- `MyPage.tsx`: "회원 탈퇴" 버튼 → 클릭 시 비밀번호 입력 폼이 펼쳐짐(`showDeleteConfirm` 상태) → "정말 탈퇴합니다" 클릭 시 `onDeleteAccount` 호출. 실패하면 에러 메시지를 폼 위에 표시하고 폼은 유지(재시도 가능)

## K8s / docker-compose 배포 반영

이번에도 frontend+backend 코드가 둘 다 바뀌어서 양쪽 이미지를 재빌드했다.

| 구성요소 | docker-compose | K8s(kind) |
|---|---|---|
| backend | `docker compose build backend` | `binseoyun/backend:v2 → v3` push, `K8s/30-backend.yaml` 갱신, `kubectl apply` |
| frontend | `docker compose build frontend` | `binseoyun/frontend:v4 → v5` push, `K8s/40-frontend.yaml` 갱신, `kubectl apply` |

이 반복 작업(빌드→푸시→태그 수정→apply를 이미지마다 손으로) 도중에 "이거 매번 수동으로 해야 하냐"는 질문이 나왔고, 이건 정확히 로드맵 Phase 4(CI/CD)가 해결하려는 문제라는 걸 확인했다 — 지금 당장 착수하지는 않고, 별도 논의로 남겨둔다.

## 결과 (정량·정성)

**curl 기반 시나리오 검증** (docker-compose `8090`, K8s `18080` 양쪽 모두 통과):
1. 회원가입 → 관심 과목 등록 → `Class.enrolled` 30 → 31 증가 확인
2. 틀린 비밀번호로 탈퇴 시도 → `400` 거부
3. 정확한 비밀번호로 탈퇴 → `200` 성공
4. **`Class.enrolled`가 31 → 30으로 정확히 복원됨** (CASCADE만 믿었다면 31에 그대로 남았을 부분)
5. 탈퇴 후 같은 학번으로 로그인 시도 → `400 존재하지 않는 학번입니다` (계정 완전히 사라짐)
6. DB 직접 조회로 `Users`, `course_interests` 행이 모두 0건임을 재확인

## 한계 (실제 운영 환경이라면)

- 탈퇴는 즉시·비가역적으로 처리된다. 실수로 탈퇴 버튼을 누른 사용자를 위한 유예기간(예: "7일 내 재로그인 시 복구")은 지원하지 않는다 — 이 프로젝트 규모에서는 소프트 삭제의 복잡도(모든 쿼리에 삭제 필터 추가, UNIQUE 제약 재설계)가 이득보다 크다고 판단했지만, 사용자 수가 늘어나는 실제 서비스라면 재고할 부분이다.
- 탈퇴 사유 수집, 관리자용 탈퇴 통계 같은 것도 없다 — 완전 삭제라 탈퇴 이력 자체가 남지 않는다.
