# ADR-002: 통합 테스트용 DB 전략 — Docker MySQL 선택

- 날짜: 2026-07-16
- 상태: 승인됨
- 관련: Phase 1 (안전망), `doc/refactoring/01-app-server-분리와-테스트-환경.md`

## 상황 (Context)

Phase 2(동시성 개선)에서 수강신청 로직을 뜯어고치기 전에, "기존 기능이 안 깨졌다"를 증명할 통합 테스트가 필요하다. 테스트가 붙을 DB를 무엇으로 할지 결정해야 한다. 프로덕션 DB는 MySQL 8.0 (Sequelize ORM 사용).

## 검토한 대안과 트레이드오프

### 1안: SQLite 인메모리
- 장점: 외부 의존성 없음, 가장 빠른 실행, CI에서 설정 불필요
- 단점: **Phase 2에서 검증해야 할 것이 정확히 MySQL(InnoDB)의 락 동작이다.** `SELECT ... FOR UPDATE`, 트랜잭션 격리 수준, 데드락 등은 SQLite와 MySQL이 다르게 동작한다. 테스트는 통과하는데 실제 MySQL에서는 깨지는(혹은 그 반대) 거짓 신호 위험. 방언 차이(타입, 인덱스)도 존재.

### 2안: Docker로 실제 MySQL 8.0 테스트 인스턴스 (선택)
- 장점: 프로덕션과 동일한 엔진 — 트랜잭션/락 테스트 결과를 신뢰할 수 있음. Docker가 이미 개발 환경 필수 도구라 추가 진입장벽 없음.
- 단점: 테스트 전 컨테이너 기동 필요(±10초), CI에서 서비스 컨테이너 설정 필요 → GitHub Actions의 service container로 해결 가능(Phase 4).

### 3안: 개발용 DB(루트 compose, 3310) 공유
- 장점: 별도 컨테이너 불필요
- 단점: 테스트가 `sync({ force: true })`로 **개발 데이터를 전부 날려버림**. 테스트와 개발 상태가 서로 오염. 탈락.

## 결정과 이유

**2안. 전용 Docker MySQL(`backend/docker-compose.test.yml`, 포트 3311)을 사용한다.**

Phase 2의 핵심 검증 대상이 MySQL 고유의 동시성 동작이므로, 테스트 DB와 프로덕션 DB의 엔진 일치가 속도보다 중요하다고 판단했다. 부가 결정:

- **tmpfs 볼륨**: 데이터를 메모리에만 둬서 I/O를 줄이고, 컨테이너 종료 시 완전히 사라지는 일회용 DB로 만든다.
- **`.env.test`를 커밋**: 일회용 로컬 DB의 계정(test/test)은 시크릿이 아니므로, 클론 후 바로 테스트 가능하도록 저장소에 포함한다.
- **`--runInBand` 직렬 실행**: Jest는 기본적으로 테스트 파일을 병렬 실행하는데, 파일마다 `sync({ force: true })`로 같은 스키마를 초기화하므로 병렬이면 서로 테이블을 지운다. 테스트 수가 적어 직렬 비용은 미미(전체 ~7초).
- **안전장치**: 테스트 헬퍼가 `NODE_ENV !== 'test'`면 즉시 throw — 실수로 개발 DB에 `force: true`가 나가는 사고 방지.

## 결과 (정량·정성)

- 테스트 스위트 3개 / 테스트 19개, 전체 실행 6.8초 (DB 기동 제외)
- 실행 방법: `npm run test:db:up` → `npm test` (종료 시 `npm run test:db:down`)
- 정성: Phase 2에서 작성할 동시성 테스트(FOR UPDATE, 트랜잭션 경합)를 프로덕션과 같은 엔진에서 검증할 기반 확보
