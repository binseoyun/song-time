## 상황 (Context)

로드맵 P1: 기존 `courseController.js`의 `toggleInterest`에 정원 초과 방지 로직 자체가 없고, `enrolled` 카운터가 비정규화돼 있어 동시 요청 시 정합성이 깨질 수 있다. 그리고 이 프로젝트의 로드맵 외 작업인 **실시간 수강신청(선착순)**은 정원 50석 과목에 동시 수천 명이 신청 버튼을 누르는 시나리오를 정면으로 다뤄야 한다.

로드맵 원칙: "동시성 제어가 없는 naive 버전을 먼저 구현해 k6로 '정원 초과 발생'을 증명(Before)하고, 개선안 적용 후 재측정(After)한다." 그래서 세 그룹을 **같은 조건**(정원 50석, k6 `per-vu-iterations` 스파이크, 동일 동시성 레벨 50~12,000, 각 5회 반복)으로 구현·측정해 동시성 제어 방식의 차이만 순수 비교했다.

- **Group A** — 무방비. 서버 코드에서 `SELECT` 후 조건 검사 후 `UPDATE` (Check-Then-Act).
- **Group B** — 비관적 락. `SELECT ... FOR UPDATE`로 행 잠금.
- **Group C** — Redis 원자 연산. `SISMEMBER`(중복) → `SINTER`(시간표 겹침) → `DECR`(좌석) → `SADD`(등록)를 **하나의 Lua Script**로 원자 처리하고, 성공분을 RabbitMQ로 비동기 전송해 워커가 MySQL에 반영.

## 검토한 대안과 트레이드오프

ADR-006 §2.1의 5개 후보 중 3개는 실험 전에 배제됐다:

| 후보 | 배제 이유 (설계 시점) |
|---|---|
| DB 낙관적 락 (Version 컬럼) | 충돌 극심 시 1명 성공에 N명 실패 → 재시도 폭주가 WAS CPU/스레드 고갈 |
| Redis 분산 락 (Redisson Pub/Sub) | `락 획득 → DB 조회 → DB 업데이트 → 락 반납` 4단계 네트워크 I/O 직렬화. 초당 ~20건 한계, 1,000명이면 마지막 사용자 ~50초 대기 |
| — | (위 둘은 실험하지 않음) |

실험한 3개:

| 그룹 | 정합성 | 처리량 | 복잡도 | 구조적 리스크 |
|---|---|---|---|---|
| **A (무방비)** | ❌ Check-Then-Act 틈으로 정원 초과 | 저동시성(≤500)에서만 높음 | 최소 | 없음 (그냥 틀림) |
| **B (비관적 락)** | ✅ 완벽 | 커넥션 풀 고갈 — 락 대기 중 DB 커넥션 점유 | 낮음 (SQL 한 줄) | 데드락 |
| **C (Redis 원자 + 비동기)** | ✅ 완벽 (Lua 단일 스크립트로 Check-Act 틈 원천 차단) | DB 트랜잭션 왕복 없음 — 메모리 연산만 | 높음 (Lua + MQ + 워커 + 멱등성 + DLQ) | "Redis 성공 후 DB 반영 실패"(Ghost Decrement), republish 무백오프 |

## 결정과 이유

**Group C (Redis 원자 연산 + Lua Script + RabbitMQ 비동기 DB 반영)를 채택한다.**

1. **RDBMS 락(A의 무방비, B의 비관적 락)은 물리적 병목으로 이어진다.** A는 정합성이 깨지고, B는 커넥션 풀 고갈. 둘 다 "DB에 부하가 직접 닿는" 구조라 트래픽이 커지면 서버가 다운된다.
2. **DB 물리 병목으로 서버가 다운되는 것보다, 통제 가능한 엔지니어링 과제(정합성 리스크 관리)를 푸는 게 합리적이다.** C의 치명적 단점(데이터 동기화 실패)은 **3중 안전망**으로 통제한다: ① 성공분을 RabbitMQ 전송 ② 워커 수동 ACK로 메시지 영속성 ③ DB 복합 유니크 키 + `INSERT IGNORE`로 멱등성 ④ 반복 실패 메시지 DLQ 격리.
3. **좌석 차감과 검증을 하나의 Lua Script로 통합**한다(§2.2). 검증(서버)과 차감(Redis)을 두 요청으로 분리하면 Check-Then-Act 틈이 부활해 A의 Race Condition이 그대로 돌아온다.
4. **좌석 카운터 시딩**: 수강신청 오픈 전 배치 스크립트(`seedAllClassSeats.js`)가 `Class`에서 Redis `class:{id}:seats`로 채워 넣는다. 이 시점 이후 실시간 잔여석의 source of truth는 Redis다 (ADR-013).

### 처리량 — 3,000명 이상에서 A/B/C 셋 다 비슷하게 붕괴

12,000명 기준 handled_rate: A 8.1% · B 9.1% · **C 12.1%** (C 근소 우위). p50/p95 latency는 C가 전 구간 최저(예: 1,000명에서 A 3,355/3,977 · B 2,482/3,690 · **C 1,350/1,683 ms**).

**3,000명↑ 붕괴는 락 경합이 아니다.** 세 그룹 모두에서 동일하게 나타났고, 원인은 **로컬 Docker Desktop 단일 호스트 인프라 한계**로 특정됐다:
- [ADR-007](ADR-007-대기열-부하-backend-인스턴스-수평-확장.md): `docker stats`로 VM 전체 CPU는 83%로 여유가 있는데 `backend_1`/`backend_2`가 각각 110~116%(**Node 프로세스당 코어 1개 남짓이 사실상 천장**)에 머물러 있음을 확인. backend를 2대→4대로 늘려 TTL 이탈 33.4%→0%, 에러율 4.89%→0.06%로 개선.
- [트러블슈팅 08](../troubleshooting/08-validate3k-잔여노이즈-원인-docker-desktop-cpu-캡.md): 로컬 환경이 실제로 **CPU 2코어**.

→ **"정확한 병목 지점 특정"이라는 로드맵 항목은 이미 답이 나왔다** — 로컬 단일 호스트의 backend 프로세스 CPU 천장이다. 그 위(관리형 로드밸런서 + 다중 노드 + HPA)에서의 실제 처리량 상한 측정은 **인프라 트랙 순서 ④(AWS 실배포 후 부하테스트)로 이관**한다. 로컬에서 커넥션 한도를 1-variable로 스윕해봤자 "노트북의 한계"를 재는 것이고, 고치는 방법(read replica·커넥션 풀러·수평 확장)도 로컬에서 검증이 안 된다.

## 결과 (정성)

1. **정합성 계약은 최종적으로 신뢰할 수 있다.** 스윕 105회차 + 어뷰징 재검증 + 카오스 3종에서 오버셀·중복 등록이 단 한 번도 발생하지 않았다. Redis Lua Script의 원자성은 정상 조건은 물론 워커 kill·API 서버 kill 상황에서도 흔들리지 않았다.
2. **비동기 반영 경로의 두 리스크(Ghost Decrement, republish 무백오프)는 "가능성"에서 "실측·영구적"으로 격상됐다.** 대응은 별도 ADR로 이미 정리:
   - [ADR-009](ADR-009-DLQ-보상-Circuit-Breaker-범위-재평가.md): DLQ 완전 보상 로직은 범위 축소, Circuit Breaker는 보류 (연습 도구 특성상 일시적 처리량 저하는 감내 가능).
   - [ADR-008](ADR-008-DLX-TTL-지연-재시도-전환-보류.md): DLX+TTL 지연 재시도 전환은 현행 유지.
   - Ghost Decrement는 주기적 리컨실리에이션 스캔으로 탐지 (1-9에서 오탐 없이 탐지됨을 확인).
3. **이 아키텍처로 계속 간다.** Stage 2(대기열 + UI)·Stage 3(운영 고도화) 어디에서도 이 결정을 재검토할 근거가 나오지 않았다.
