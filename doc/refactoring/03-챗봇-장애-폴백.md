# 챗봇 장애 폴백 — Gemini / Qdrant / Node 장애 시 친절한 degrade

- 작성일: 2026-08-31
- 관련: 이슈 #106, ADR-010 §11/§17, `doc/AI-에이전트-구현계획.md` Stage 3-2
- 대상: `backend/ai-server/chat/` (errors.py 신설, agent.py / router.py / tools.py / syllabus_tools.py)

## 문제

챗봇의 외부 의존성 장애 처리가 미흡했다.

| 구간 | 기존 동작 |
|---|---|
| Gemini LLM (429/503/timeout/인증 오류) | `router._stream_chat`가 `except Exception` → **raw 예외 문자열을 그대로 SSE `error` 이벤트로 프론트에 전송** (`"...오류: {exc}"`). API 키 관련 메시지·내부 스택이 클라이언트로 샐 수 있음. 재시도 없음 |
| 스트림 도중 실패 | 부분 답변 유실, **사용자 메시지도 db-chat에 저장 안 됨** → 다음 턴 히스토리에서 그 발화가 사라짐 |
| Tool 인프라 (Qdrant / Node 과목 API / 임베딩 API) | Tool이 `raise_for_status()` / `RuntimeError`로 던짐 → `create_agent`의 ToolNode가 잡아 raw 에러 문자열을 에이전트에 전달 → 에이전트가 그걸 사용자에게 relay할 수 있음 |
| redis-chat | ✅ 이미 `cache.py`가 예외 삼키고 MySQL 웜업으로 폴백 |

## 결정

사용자와 4개 논의점을 정리해 확정:

1. **LLM 재시도 = A안**: `ChatGoogleGenerativeAI(max_retries=2)` — 429/503만 LangChain 내장 지수 백오프. 스트리밍이라 사용자가 기다리는 중이므로 2회로 제한. 그래도 실패하면 router가 친절 메시지로 degrade.
2. **스트림 도중 실패**: 부분 답변에 `"\n\n[응답이 중간에 끊겼습니다]"` 꼬리표를 붙여 저장. 사용자가 이어서 물을 수 있게.
3. **에러 메시지 = 3종 분류** (`chat/errors.py`):
   - `transient` (429 rate / 503 / timeout): "지금 AI 응답 요청이 몰려 있어요. 잠시 후 다시 시도해 주세요."
   - `quota` (일일 한도 소진): "오늘 AI 사용량 한도에 도달했어요. 잠시 후 다시 이용해 주세요."
   - `unknown`: "AI 응답 생성에 문제가 발생했어요. 잠시 후 다시 시도해 주세요."
   - **raw 예외는 `logging`으로 서버에만.** SSE `error` 이벤트에는 `{message, kind, phase}`만.
4. **측정 = 수동 장애 주입** (정식 카오스 테스트는 이 챗봇엔 과함).

### quota vs transient 구분의 함정

둘 다 HTTP 429 / `ResourceExhausted`라 예외 텍스트로만 나뉜다. Gemini의 **순간 rate limit** 메시지도 `"Resource has been exhausted (e.g. check quota)"`처럼 "quota"를 포함한다 — 그래서 바 `"quota"`는 마커로 못 쓴다. 한도 소진에만 나오는 구체 문구(`"exceeded your current quota"`, `"quota exceeded for"`, `"per day"`, `"plan and billing"` 등)로 좁히고, 애매하면 `transient`(재시도 여지가 있는 쪽)로 본다.

## 구현

| 파일 | 변경 |
|---|---|
| `chat/errors.py` (신설) | `classify_llm_error(exc) → (kind, user_message)`, Tool 장애 문구 상수, `STREAM_CUT_SUFFIX` |
| `chat/agent.py` | `build_llm`에 `max_retries=2`. SYSTEM_PROMPT +1문장 ("Tool 결과에 error가 있으면 그 안내를 전달하고 지어내지 않는다") |
| `chat/router.py` | `_persist_turn` 헬퍼 추출 — 성공·부분·실패 전 경로에서 호출해 사용자 메시지 유실 방지. 스트림 예외 시 `classify_llm_error` + `logger.exception` + 분류 메시지 SSE + 부분 답변 저장. db-chat 장애도 삼킴 |
| `chat/tools.py` | `search_courses` / `get_course_by_code`: `requests.RequestException` → `{"error": TOOL_ERROR_COURSES}` |
| `chat/syllabus_tools.py` | `search_syllabus` / `get_syllabus`: 임베딩·Qdrant 예외 → `{"error": TOOL_ERROR_SYLLABUS}` |
| `main.py` | `logging.basicConfig` |
| 프론트 `AIChat.tsx` | `error` 이벤트에서 `payload.message`(신) 우선, `payload.detail`(구) 폴백 |

## 검증 (수동 장애 주입)

| 시나리오 | 방법 | 결과 |
|---|---|---|
| Qdrant 다운 | `docker compose stop qdrant` → "동적 계획법 배우는 수업?" | Tool: `{"error": "지금 강의계획서 검색을 사용할 수 없어요..."}` → 에이전트: *"현재 강의계획서 검색 기능을 사용할 수 없어 관련 과목을 찾아드리기 어렵습니다. 잠시 후 다시 시도해 주시겠어요?"* — raw 없음, 할루시네이션 없음 |
| Node 과목 API 다운 | `docker compose stop backend_1` → "알고리즘 잔여석?" | 에이전트: *"지금 과목 정보를 조회할 수 없어요. 잠시 후 다시 시도해 주세요."* |
| Gemini 인증 오류 | `-e GEMINI_API_KEY=invalid` 로 `_stream_chat` 실행 | SSE: `event: meta` → `event: error` `{"message": "AI 응답 생성에 문제가 발생했어요...", "kind": "unknown", "phase": "start"}`. **raw 400 INVALID_ARGUMENT 스택은 서버 로그에만.** db-chat 미가용 상황(테스트 컨테이너)에서도 `_persist_turn`이 예외를 삼켜 스트림 정상 종료 |

## 남은 것

- 인증 오류(`API_KEY_INVALID`)는 현재 `unknown`으로 분류돼 "잠시 후 다시 시도" 안내가 나간다 — 사실은 ops 설정 문제라 사용자가 아무리 재시도해도 안 풀린다. 모니터링/로그로 잡을 문제라 사용자 메시지는 그대로 두되, 필요 시 `auth` 종류 추가 검토.
- E2E(nginx→Node→ai-server) SSE 경로에서 `error` 이벤트 렌더링은 Stage 2에서 이미 확인됨. 3-2는 페이로드 형태만 바꿈(`detail`→`message`, 프론트 폴백 처리).
